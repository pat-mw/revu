## Goal

Deliver the one genuinely net-new UI in the milestone: a way to *make* a local review, and a place in the
inbox where local reviews live. `LOCAL_REVIEWS.md §7` says it plainly — everything else in M8 is a variant of
something that already exists, but "a branch picker (local branches + remote-tracking refs for the base), a
base picker, and a create action" has no precedent to copy. This ticket implements the creation flow, the
`Local reviews` inbox section above `Waiting on you`, a row variant that reads `base ← head` instead of
`#number`, and the entry points (header button beside the List/Tree control, one command-palette entry in the
**Go** group, and — if a chord is taken — a `SHORTCUT_CATALOG` entry to document it).

It implements **D2** (`§3`): the reserved high-number identity is what lets all of this reuse the `/pr/:n`
route family, both `matchPrNumber` regexes, and every existing React Query key untouched. It also carries
`§8` edge case 6 into the UI — creating the same `(repo, base, head)` twice **returns the existing review**
rather than minting a second, so the app must treat a returned pre-existing id as success and navigate to it.

Because the mock is the spec (**D6**), this ticket is completable against **M8.1 alone**: no daemon, no git,
no network. `?mock=1` is the acceptance surface. Local-mode *chrome* inside `/pr/:n` — tab omission, header
seal, copy sweep — is **M8.7** and is deliberately out of scope here.

## Units

independent of M8.6.1** and can run in parallel (it touches only the query layer). **M8.6.3 and M8.6.4 are

### M8.6.1 — Pure view-model: identity, partition, label, validation
**Do:** A pure module the rest of the ticket derives from, so the UI holds no ad-hoc branching:
- `isLocalReviewItem(item)` and the raw `isLocal(n)` predicate — **the single app-side call to
  `isLocalReviewId`** (M8.1). Nothing else in the app compares a number to a base constant, and nothing else
  imports `isLocalReviewId` from `@revu/shared`. M8.7.1's `lib/review-mode.ts` derives `reviewMode(n)` by
  importing the predicate **from this module** rather than calling the shared one a second time; M8.7.4's grep
  check allows exactly this file. Say so in the docstring — the two tickets are parallel-eligible on paper and
  this is the sentence that keeps whichever lands second from growing a duplicate.
- `partitionInbox(items) → { local, github }` — preserves input order within each side.
- `localReviewLabel(pull) → { head, base }` — the `base ← head` pair the row and the palette render **instead
  of** `#{number}`. `§3.1`: "`#1000000001` is never rendered."
- `createReviewIssue({ base, head }) → string | null` — the client-side pre-flight for `§8` edge cases 1 and 7:
  same base and head, an empty ref, and a ref beginning with `-`. It is a *fast fail for the user*, never the
  security boundary — the authoritative validation is `git check-ref-format` on the daemon side (M8.3) and the
  shared validator (M8.1). Say that in the docstring so nobody later deletes the server check.

**Files:** `packages/app/src/lib/local-reviews.ts` (new), `packages/app/src/lib/local-reviews.test.ts` (new).
**Check:** `bun test packages/app/src/lib/local-reviews.test.ts` green, asserting: a `PullListItem` at
`LOCAL_REVIEW_ID_BASE` partitions local and one at `482` does not; `partitionInbox` is order-preserving and
total (every input appears exactly once across the two arrays); `localReviewLabel` never returns a string
containing `#`; `createReviewIssue({ base: 'main', head: 'main' })` is non-null, and so is
`{ base: '--upload-pack=x', head: 'f' }`.

### M8.6.2 — Query layer: branches, create, and the list invalidation
**Do:** Add `qk.branches` **and** `qk.localReviews` to the key factory at `state/queries.ts:35-44` — never an
inline key. Add `packages/app/src/state/local-reviews.ts`
with `useBranches()` (`staleTime` in the seconds, refetched when the create dialog opens — branches change
under the user constantly), `useLocalReviewAnnotations()` over `listLocalReviews`, and
`useCreateLocalReview()`.

The two query sources have a strict, non-overlapping division of labour, fixed by M8.1's decision D-c:
**`usePullList` is the row source** for every rendered row (D-a merges local reviews into `listPulls`, and
`PrLayout` can resolve a review only from there), and `listLocalReviews` supplies **only** the two local-only
annotations `LocalReviewSummary` carries and `BrokerPullMeta` cannot — `dirty` (D3) and `archivedPr` (D1).
Nothing renders a row, a title, a ref pair or a `broker.*` field from the annotation query; that is the "two
truths" hazard, and keeping the annotation query keyed separately and read only for badges is what avoids it.
Invalidate `qk.localReviews` alongside `qk.pulls` on create.

The mutation's `onSuccess` must **invalidate `qk.pulls` and await the refetch before the caller navigates**.
`PrLayout` resolves its PR by searching `usePullList()` (`pr-layout.tsx:280-282`); navigating to `/pr/<newId>`
before the list carries it lands the user on the "isn't in this installation" empty state
(`pr-layout.tsx:349`) — the exact screen `§7` calls out as actively harmful copy. Return the created (or
pre-existing) review from the mutation so the caller navigates by its id rather than re-deriving it.

**Files:** `packages/app/src/state/queries.ts` (key factory only), `packages/app/src/state/local-reviews.ts` (new),
`packages/app/src/state/local-reviews.test.ts` (new).
**Check:** A test against `createMockApi()` with `mockDev.reset()` in `beforeAll` (the shared-mock-store rule):
create `(main, feature/x)`, then create it again — assert **the same id both times** and that
`listPulls()` contains exactly one item with that number. A second assertion: the returned id satisfies
`isLocalReviewId`.

### M8.6.3 — The create dialog
**Do:** A Radix `Dialog` (`components/ui/dialog.tsx:30-54`) with a filterable head picker, a filterable base
picker, a title field, and a create action. Model the pickers on the palette's embedded `cmdk` list
(`components/ui/command.tsx:88`/`:115`) — a repo can have hundreds of branches and a bare `<select>` is
unusable at that size. The **base picker offers local branches *and* remote-tracking refs** (`§8` edge case 3:
`origin/main` is a legal base); the head picker offers local branches only.

Title defaults to the head branch name (`§4.1`) and is editable. A failed create **keeps the dialog open with
every field intact** — never discard user-written text on failure (hard-constraints). Surface M8.1's typed
errors as their own sentences: unrelated histories naming both refs (`§8` edge case 4), shallow clone
(edge case 5), ref not found, `base == head` (edge case 1). A duplicate is **not** an error path: it resolves,
and the dialog closes onto the existing review.

**Files:** `packages/app/src/components/create-local-review.tsx` (new — flat beside `palette.tsx` and
`shortcut-sheet.tsx`, the app's other two global overlays).
**Check:** `bunx tsc -b` clean and, in a `?mock=1` build: open the dialog, pick a head and a base, create,

### M8.6.6 — Tree arrangement and filter correctness
**Do:** Two rearrangement surfaces that read the same list and would otherwise treat a local review as a PR:
- **Tree** (`inbox.tsx:174-178` → `lib/pull-tree.ts:44`). Decide and implement deliberately (see
  **Open questions**). The default reading: exclude local reviews from `buildPullTree`'s input and render them
  as their own group above the roots, because a local review is not part of anyone's PR stack. The concrete
  hazard if they are left in: `byHead` (`pull-tree.ts:51-55`) keeps the **lowest-numbered** pull per head ref,
  so a local review (id ≥ 1e9) can never win a collision but *can* become the parent of a real PR whose base
  equals its head ref — a GitHub PR nested under something that does not exist on GitHub.
- **Filter** (`inbox.tsx:64-77`). The haystack is `title #number authorName`. A local review's number is
  never rendered and its author is a sentinel, so the only useful token is the title — which the user may have
  edited away from the branch name. Add `head.ref` and `base.ref` to the haystack. Note this changes GitHub PR
  filtering too (branch refs become searchable there as well); that is a small, defensible widening, not a
  local-only branch in the code.

**Files:** `packages/app/src/pages/inbox.tsx`, `packages/app/src/lib/local-reviews.ts`,
`packages/app/src/lib/local-reviews.test.ts`.
**Check:** A test asserting `buildPullTree(partitionInbox(items).github)` produces a tree with no node whose
`item` is local, given a fixture where a real PR's base ref equals a local review's head ref. A second test
asserting the filter helper matches a local review by its base ref and by its head ref. Then, in `?mock=1`,
switch to Tree and confirm no local review is nested under a PR and no PR is nested under a local review.

## Constraints that bind this ticket

- **D2 — the reserved band is what keeps the frontend unchanged** (`§3`, `§3.1`, `§7`). Both `matchPrNumber`
  regexes (`palette.tsx:51`, `app-shell.tsx:44`), the `/pr/:n` route family (`App.tsx:21-28`), and every
  `qk.*(n)` key must be left exactly as they are. If anything in this ticket needs one of them changed, the id
  design has been misread — stop and re-read `§3.1`.
- **`#1000000001` is never rendered** (`§3.1`). The local row shows `base ← head` and a `local` seal. This is a
  hard rendering rule, not a preference, and Verify step 4 tests it.
- **All data goes through `api` from `@/api`** (AGENTS.md). The dialog, the pickers, and the section derive
  from `api` and TanStack Query only — never from `@/fixtures` or `@/api/mock` (the dev panel is the one
  sanctioned exception, and this is not it).
- **Read-only inputs** (AGENTS.md): `packages/shared/src/api/client.ts`, `packages/shared/src/api/types.ts`,
  `packages/app/src/api/index.ts`, `packages/app/src/fixtures/contract.ts`, `packages/app/src/styles/globals.css`.
  Every contract addition this ticket consumes belongs to M8.1. If one looks wrong, report it — do not edit it.
- **Per-human UI state lives in preferences, not browser storage** (memories/known-landmines.md, M1.4: the
  split-mode `sessionStorage` was the last browser-side per-human state and was deliberately removed). A
  "remember my last base branch" affordance goes through `HumanPreferences` — which means it is an M8.1
  contract change, not a local `useState` persisted to `localStorage`.
- **Never discard user-written text on failure** (hard-constraints). A failed create keeps the dialog open with
  the title and both refs intact.
- **Visual system** (AGENTS.md): `globals.css` tokens only — raw hex is a defect; `text-sm` default density,
  gaps of 1–2 units, hairline separation, no `py-24`; `lucide-react` at 14–16px `strokeWidth={1.5}`; visible
  focus (never suppress the global `:focus-visible`); `aria-label` wherever text is not visible; skeletons that
  match the final layout; empty states that are invitations with a next action.
- **Violet is reserved for draft/pending state**; gold means "time moved"; red means destructive. A `local`
  seal is a provenance fact, not pending work — `outline` or neutral, not `draft`.
- **The mock is the permanent oracle and `?mock=1` stays reachable in production builds** (hard-constraints,
  D6). This ticket's whole acceptance path runs through it.
- **Test-harness discipline** (memories/known-landmines.md): one shared mock store across every `bun test`
  file in the process — any test here that drives `createMockApi`/`mockDev` calls `mockDev.reset()` in
  `beforeAll` and restores in `afterAll`. Prefer pure-lib tests where the logic can be extracted.
- **Code style** (AGENTS.md / hard-constraints): comments and docstrings are self-contained. Nothing in the
  code may reference M8.6, this board, a milestone, a PR number, or any tracking artifact. Complete output
  only — no stubs, no TODOs.
- **TDD** (hard-constraints): each unit lands with its tests; `bun run check` green before the PR.

## Landmines

- **An archived local review is `state: 'closed'` and the inbox only renders open items.** `§4.1` sets
  `pull.state` to `'closed'` once archived under D1, and `inbox.tsx:122` / `:175` / `:258` all filter on
  `pull.state === 'open'`. So the "superseded" badge M8.6's seed text asks for is, as the code stands,
  unreachable — the row is gone before it could carry it. Decide this with M8.9 rather than discovering it
  after building the badge (see **Open questions**).
- **Navigating before the list refetches lands on the 404 screen.** `PrLayout` resolves the review out of
  `usePullList()` (`pr-layout.tsx:280-282`); with no match it renders "PR #… isn't in this installation"
  (`:349`) — the exact copy `§7` flags as harmful, and the one a mis-keyed local review would hit. Await the
  invalidation, or seed the list cache from the create response.
- **The ETag short-circuit can hide a brand-new review.** `usePullList` holds the previous ETag in a ref
  (`queries.ts:54`, `:60`) and, on `notModified`, returns the **previous items** (`:63-71`). An invalidation
  that re-issues the same ETag and gets a 304 back leaves the new row invisible until something else changes
  the list. `§4.1` says the local ETag is a hash of the local reviews' compare keys, so it *should* move — but
  the app must not depend on that alone: assert the new row is present after create, not merely that a refetch
  fired.
- **`w-12` and a ten-digit number.** `inbox.tsx:543-545` reserves twelve units for `#482`. Restyling the slot
  is the wrong fix twice over — it would still render a number `§3.1` forbids.
- **A zero-total checks rollup reads as "Checks passed".** `pull-tooltip.ts:177-180` maps `total <= 0` to a
  countless phrasing per state, so `{ state:'success', total:0 }` claims CI passed on a branch that was never
  pushed. Only an **absent** `broker.checks` omits the line. Assert absence rather than trusting it.
- **`branchPair` will call a local review a fork** if the synthesized `head.repo.full_name` and
  `base.repo.full_name` differ (`pull-tooltip.ts:157`), rendering the `fork` badge at `inbox.tsx:626-630`.
  Nothing on GitHub is involved, so "fork" is meaningless there.
- **The tree can nest a real PR under a local review.** `pull-tree.ts:62-79` parents purely on
  `base.ref === parent.head.ref`, with no repo and no id-band awareness; `byHead` (`:51-55`) resolves ties by
  lowest number, which a ≥1e9 id always loses — so a local review never *steals* a parent, but it can *become*
  one. It also creates its own root (`:76-79`) and reorders the root list, which is sorted by subtree size
  (`:107-113`).
- **The inbox's bare keys fire behind a modal.** `inbox.tsx:216-221` registers `j`/`k`/`enter` with no
  `enabled` gate, and `isFromTextEntry` (`keyboard.tsx:176-181`) only exempts real text controls. Pressing
  `enter` on the dialog's create button while it is focused will *also* navigate the inbox behind it if the
  handler stack is not gated.
- **A catalog entry alone binds nothing, and a binding alone documents nothing.** `lib/shortcuts.ts:1-10` is
  explicit. And an entry whose `group` is not in `shortcut-sheet.tsx:16-22`'s `GROUP_ORDER` never renders in
  the `?` sheet at all — a silently invisible row.
- **The palette caps at ten open pulls** (`palette.tsx:88-97`). Local reviews merged into the same list either
  crowd PRs out or fall off themselves; and at `:146-151` each item renders `#{number}`. If local reviews are
  to be jumpable from the palette, they need their own rendering, not the PR item's.
- **The draft probe scales with the merged list.** `inbox.tsx:90-96` fires one `getDraft` per listed item. In
  HTTP mode, N local reviews are N more requests in the same burst — cheap, local, and journal-free, but not
  free, and worth watching if `§8` edge case 10's "very large" case ever means many reviews rather than many
  files.
- **The shared mock store leaks across `bun test` files** (memories/known-landmines.md). Green locally, red on
  a slower CI runner. `mockDev.reset()` in `beforeAll`, restore in `afterAll`, or avoid the mock entirely.
- **The e2e driver is a plain `bun run` script, never a `*.test.ts`** (memories/known-landmines.md) — the gate
  runs `bun test` before the app build, so a `*.test.ts` e2e would run with no `dist`. If this ticket adds an
  e2e step it belongs in `e2e/`, not beside the unit tests; the local-review e2e proper is **M8.11**.

## Open questions

1. ~~**Which call feeds the inbox's local section — `listPulls` or `listLocalReviews`?**~~ **Settled by M8.1's
   decisions D-a and D-c**: `listPulls` is the render source for rows; `listLocalReviews` is queried
   separately and read **only** for the `dirty` and `archivedPr` annotations that the frozen `BrokerPullMeta`
   cannot carry. See M8.6.2 for the division of labour and why it does not reintroduce the two-truths hazard.
2. **Is the `Local reviews` section shown when empty?** Two live precedents point opposite ways: `Waiting on
   you` is rendered empty as reassurance (`inbox.tsx:344-354`), and `§7` cites the dev-controls probe
   (`palette.tsx:213-240`) — "omit the group entirely rather than render it empty" — as the gating precedent
   for local mode. If it is omitted, the create entry point must be reachable from the header and the
   zero-state, not only from the section. **Owner call.**
3. **Can the superseded (D1) badge render at all?** Its *source* is settled — `LocalReviewSummary.archivedPr`
   via M8.6.2's annotation query (M8.1's decision D-c). What is not settled is reachability: see the first
   landmine — `§4.1` makes an archived review `state: 'closed'` and `inbox.tsx:122`/`:175` filter closed pulls
   out of every section and every tree, so the row is gone before it could carry the badge. Either the
   open-only filter becomes local-aware, or `§4.1` is amended so an archived local review stays `'open'`, or
   the superseded badge moves wholly into M8.7/M8.9's PR chrome and M8.6 renders only the dirty badge.
   **M8.9's open question 4 owns the answer** and M8.9 now depends on this ticket, so it is decided with
   M8.6's row in front of the decider rather than after it.
4. **Do local reviews appear in the Tree arrangement at all?** The seed text asks only that the tree "does not
   mis-parent" them. Excluding them and rendering a separate group is the safest reading; including them as
   their own roots is defensible (a local review *is* stacked on a base branch, and `§8` edge case 3 allows a
   remote-tracking base). Excluding them means the Tree arrangement shows strictly fewer rows than List, which
   `inbox.tsx:419` currently promises it does not ("Neither is a filter — both show the same PRs").
   **Implementer call, documented in `pull-tree` usage rather than in `pull-tree.ts` itself.**
5. **Which chord, and registered where?** `§7` calls the chord optional and the seed text says "if it gets a
   chord". `g` is already a prefix with `i`/`f`/`c` taken (`app-shell.tsx:225-233`). Registering shell-side
   makes it work from a PR page but forces the dialog up into the shell's overlay set
   (`app-shell.tsx:281-287`); registering inbox-side keeps the inbox self-contained but makes the key dead
   everywhere else. The two decisions are one decision. **Implementer call.**
6. **Is the title editable after creation?** `§4.1` allows "the head branch name (or a user-supplied title)",
   and `§4.2` stores `title` on `local_reviews` — but no contract verb renames a review. If M8.1 adds no
   update verb, the title is set once at creation and the dialog is the only place it can ever be chosen.
   Worth knowing before designing the field. **Confirm against M8.1.**
7. **What does the base picker default to?** Nothing in the app knows the repo's default branch — `PullSummary`
   carries no such field, and `useRepoContext` (`app-shell.tsx:37-40`) reads a repo name off the first list
   item, which is empty in a repo with no PRs. With no `origin` there may be no `origin/HEAD` either. Options:
   no default (the user must pick), or `BranchRef` carries a `default` marker. That is a **wire-shape**
   question, so it is answered once in **M8.1's open question 3** (which fixes `BranchRef` for both
   transports); M8.3.7 reads `refs/remotes/origin/HEAD` to populate it and degrades to no marker in a repo
   with no origin. This ticket consumes the answer; it does not invent one.
