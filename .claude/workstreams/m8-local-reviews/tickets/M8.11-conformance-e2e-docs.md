## Goal

The closing ticket: it does not add a feature, it *proves* the milestone. Three things ship. First, a
local-review leg in the conformance matrix — the assertions written once in `packages/shared/conformance/`
and run over all three in-gate transports (mock in-process, revud-mock over HTTP, and the direct engine
against a seeded local repo), which is how **D6** (`LOCAL_REVIEWS.md §3` — the mock's semantics *are* the
spec, revud conforms) stops being an intention and becomes a gate. Second, a browser-driven e2e that creates
a local review and walks create → sync → comment → submit with **zero outbound GitHub requests** recorded
for the whole flow: **D7**'s structural absence is proven statically by M8.4 (no GitHub client imported) and
dynamically here (nothing left the process). Third, docs — the user-facing local-review flow, the run-modes
page saying plainly that local reviews are a capability *inside* direct mode rather than a fourth mode
(**D5**), and `docs/security-review.md` gaining the statement that local reviews are deliberately invisible
to the audit trail because they are deliberately invisible to the client (**D4**, `§8` edge case 25). When
this ticket's Verify is green, every M8 exit criterion in `MILESTONES.md:428-434` has a run that proves it.

### M8.11.1 — The shared local-review conformance suite
**Do:** Add `runLocalReviewConformanceSuite(config)` as a sibling of `runConformanceSuite`
(`packages/shared/conformance/suite.ts:173`) and re-export it from the barrel
(`packages/shared/conformance/index.ts:10-21`). No packaging change is needed: `packages/shared/package.json`
already exports `"./conformance": "./conformance/index.ts"`, and `packages/shared/tsconfig.json` already has
`"include": ["src", "conformance"]`. The config mirrors `ConformanceConfig` (`suite.ts:135-153`) —
`label`, `makeApi`, `restart` — but replaces `ConformanceScenarios` (`suite.ts:42-55`), which names fixture
*PR numbers*: a local review has no number until it is created, so the runner instead declares the fixture
it can offer (repo identity, base ref, head ref, and a `path` + line that is known to be in the diff), and
the suite creates the review and reads the minted id back. One walk, asserting:

- `createLocalReview` returns an id for which `isLocalReviewId(id)` is true and `id >= LOCAL_REVIEW_ID_BASE`
  (`LOCAL_REVIEWS.md §3.1`), and `listLocalReviews` contains it;
- creating the same `(repo, base, head)` a second time returns the **same** id (`§8` edge case 6);
- `getSnapshot(id)` before any sync resolves **`null`**, never a thrown `not_found` — one of the three
  frozen semantics, asserted here on a *local* id;
- `syncPull(id)` resolves with `partial: null` present as a key (never omitted), a non-empty
  `immutable.files`, and `compareKey === \`${mergeBaseSha}...${headSha}\``;
- `getBlob` on a head sha taken from `immutable.blobIndex` returns non-empty content;
- `saveDraft` then `submitReview` with a deliberately wrong `expectedHeadSha` returns
  `{ status: 'head_moved' }` as a **resolved value**, and the draft is untouched afterward — the local
  analogue of `suite.ts:273-293`;
- `submitReview` with the true head returns `ok`; `(await api.getSnapshot(id))!.mutable.threads` gained a
  thread whose comment ids are **positive** and in the `LOCAL_ENTITY_ID_BASE` band (`§6`, `§8` edge case 17);
  the draft is gone. **Read threads from the snapshot's mutable half, never through `listReviewThreads`** —
  the existing suite already does exactly this (`suite.ts:242-268`), and `listReviewThreads` is not available
  on the local path in two of the three transports: M8.5's landmine keeps it a deliberate 501 ("local threads
  ride the snapshot's mutable half exactly as GitHub threads do … implementing it grows a second thread read
  that can disagree with the snapshot"), it sits in `NOT_IMPLEMENTED_ROUTES` (`direct-router.ts:92-94`), and
  `DirectApi` (`direct-api.ts:53`) has no such method at all. A suite line asserting it would either red the
  direct leg or force the daemon to implement the method the design forbids;
- per M8.1's decision **D-b**, `mutable.reviews` and `mutable.issueComments` are still `[]` after the submit —
  the assertion that keeps M8.7.4's threads-only Conversation tab honest across every transport. The submitted
  summary itself is asserted at the only wire moment it exists: the `ok` result's `review`
  (`SubmitResult`, `types.ts:495-498`) is a `ReviewSummary` whose id is positive and in the entity band.
  The contract deliberately has **no verb that re-reads a local submitted summary** — D-b routes it to a
  transport-internal record — so its *persistence* is owned transport-locally (M8.1.3 mock, M8.2.5 store,
  M8.4.3 sink) and this suite must not pretend to assert it; a suite line that tried would be unimplementable
  over `RevuApi` and the pressure would land on weakening the suite, which D6 forbids;
- `replyToThread` returns a complete comment (positive id) and the thread grows by exactly one;
- `resolveThread` returns a fully normalized thread with `isResolved: true` and a non-empty `resolvedBy`;
- `addReaction` returns a rollup with the bumped key actually bumped (`§6` — a returned-old-value stub makes
  the app's optimistic update silently revert);
- no comment body carries a stamped `**Name** (role)` prefix (`§6`, "No stamping");
- a draft written against the local id survives `config.restart()`.

Import discipline is the same as the existing suite: only `@revu/shared`'s own exports and `bun:test`
(`suite.ts:32-34`), so `shared` stays a leaf.

### M8.11.3 — Leg G: the direct engine, in-gate and hermetic

**First, the interface gap, because leg G is unexecutable without closing it.** `DirectApi`
(`direct-api.ts:53`) is **not** a `RevuApi`, and `ConformanceConfig.makeApi` (`suite.ts:139`) requires a
`RevuApi` — so `createDirectApi`'s return value cannot be handed to the suite and `tsc -b` fails. Three
verified divergences, not one: `getSnapshot(n)` is **synchronous** and returns `Snapshot | null`
(`direct-api.ts:98`) where `RevuApi` promises one (`client.ts:50`); `listPulls(ifNoneMatch: string | null)`
returns a `PullListResponse` synchronously (`direct-api.ts:78`) where `RevuApi` takes
`opts?: { etag?: string }` and returns a promise (`client.ts:44`); and `listReviewThreads` (`client.ts:56`)
does not exist on `DirectApi` at all. This is precisely why `conformance-reads.test.ts` is a hand-written
"reads subset" rather than a runner of the shared suite — the note is in its own docstring.

So this unit ships **two** files. The first is the bridge, named as a deliverable rather than assumed:
`packages/revud/src/direct/conformance-local-adapter.ts` — a thin `RevuApi` over a `DirectApi`, test-support
code imported only by `*.test.ts`, with a docstring in the shape `conformance-fakes.ts:29-37` uses. It wraps
the synchronous methods in `async`, translates the `listPulls` signature, and serves `listReviewThreads(n)`
from `(await getSnapshot(n))?.mutable.threads ?? []` — an adapter-local read that exists only to satisfy the
interface. It is not driven by the local suite (M8.11.1 reads threads off the snapshot for exactly this
reason) and it does **not** oblige the daemon to serve the route: `listReviewThreads` stays a 501 in direct
mode per M8.5's landmine. The adapter adds no behaviour; anything it cannot express by shape-shifting is a
finding about the daemon, not a thing to paper over here.

The alternative considered and not taken: run leg G against revud-over-HTTP in **direct** mode, reusing
M8.11.2's extracted spawn helper and the real fetch adapter. It needs no bridge, but it re-tests leg F's
transport with a different mode, it cannot inject `throwingGithubClient()`, and M8.5.7 already covers
revud-over-HTTP-in-direct as an integration suite. If the bridge turns out to hide a real divergence, this is
the fallback.

**Then the runner:** `packages/revud/src/direct/conformance-local.test.ts` — the same shared suite against the
real `createDirectApi` (`direct/direct-api.ts`) through that adapter, assembled as
`conformance-reads.test.ts:21-28` assembles it, but with five deliberate differences:

- the fixture is a real seeded git repo from M8.3's `packages/revud/src/direct/local-fixture-repo.ts`, torn
  down in `afterAll`;
- the store is `openDirectStore({ dataDir })` on an `mkdtempSync` directory, **not** `:memory:`
  (`conformance-reads.test.ts:32` uses `:memory:` because it never restarts) — the suite's `restart` hook
  must reopen the same file, or durability is asserted about nothing;
- `github: throwingGithubClient()` (`direct/github-write-stubs.ts:50`) is injected, so any GitHub touch on
  the local path throws a method-naming error and reds the leg instead of passing quietly;
- the session is `CONFORMANCE_SESSION` (`direct/conformance-fakes.ts:43`) and the repo identity is the local
  repo's, not `CONFORMANCE_REPO` (`:40`);
- **the `localReviews` surface is assembled and passed as `createDirectApi`'s dep** — M8.2's store slice +
  M8.3's builder + M8.4's write sink, wired the way M8.5.5 wires them at boot, over the fixture repo's
  discovered toplevel. Without it every local id hits M8.5.1's typed `not_found` and the whole leg reds on
  its first call; with `context.cwd` instead of the discovered root it would operate on the wrong repository.

This is the leg that makes "no skipped local leg" true. Leg C (`scripts/conformance-matrix.ts:172-200`)
skips without a token by design; a local review needs no token and no network, so this leg is **required and
in-gate** and must never be hung off C's token gate.
**Files:** `packages/revud/src/direct/conformance-local-adapter.ts` (new),
`packages/revud/src/direct/conformance-local.test.ts` (new).
**Check:** `bunx tsc -b --force` is clean — with the adapter, `makeApi` genuinely returns a `RevuApi` and the
compiler is the proof, which is the check the earlier shape of this unit could not have passed. That is
corroboration. The Check proper is three assertions **inside the runner**, all of which rerun on every future
gate:

- `env -u GH_TOKEN -u GITHUB_TOKEN bun test packages/revud/src/direct/conformance-local.test.ts` passes —
  the shared suite, green over the real engine.
- **A `fetch` tripwire**, which is what replaces "re-run it once with the machine offline". `beforeAll` swaps
  `globalThis.fetch` for a recorder that appends `{method, url}` and then throws; `afterAll` restores it; a
  final `it` asserts the recorded array is empty. `throwingGithubClient()` reds a call that goes through the
  client *interface*; the tripwire is what catches a raw `fetch` that does not, and unlike an offline run it
  is still true on a runner that happens to have a network.
- **The fixture repo has zero remotes**, asserted before the suite runs (`git remote` prints nothing). A
  wrapped `fetch` does not cover `git` subprocesses (`command-runner.ts:42-63`), so having no URL to reach is
  the only thing between this leg and the network — assert it rather than assume it.

Then the **negative control**, run once and reverted: make the local sync path call
`fetch('https://api.github.com/rate_limit')` and confirm the tripwire reds naming that URL. An offline re-run
of the whole leg is welcome corroboration, but it is a one-time observation; the tripwire is what still runs a
year from now. Record both observations in the Log.

### M8.11.6 — The local-review e2e and the zero-outbound-GitHub proof
**Do:** Two new runtime files, both **plain modules `bun` runs directly, never `*.test.ts`** (see Landmines) —
plus, third, the guard's own predicate test, which *is* a `*.test.ts` and is safely so precisely because of the
self-install rule below:

- `e2e/no-github-guard.ts` — a preload that wraps `globalThis.fetch` in the daemon process: for any request
  whose URL host is not loopback, append `{method, url}` as a JSON line to the file named by
  `REVU_E2E_NETLOG`, then reject it. Loopback stays allowed so same-origin behavior is unchanged. Wrapping
  the *global* is what makes the coverage total: `createGithubClient` defaults `fetchImpl` to the global
  `fetch` (`packages/revud/src/direct/github-client.ts:925`), so every REST and GraphQL tier goes through it.
  **Two shape constraints keep the guard testable and non-inert.** (1) The host decision is an exported pure
  predicate, `isOutboundUrl(url)`, and the module self-installs **only** when `REVU_E2E_NETLOG` is set — so a
  `*.test.ts` can import the predicate without wrapping the test process's own `fetch`. (2) On install it
  writes an `{"installed":true}` first line to the netlog, so "empty file" and "guard never loaded" stop being
  the same observation. Without that, dropping `preload:` from the harness call would leave the netlog empty
  and the driver passing for precisely the wrong reason. Say in the docstring what the guard does **not**
  cover — `git` subprocesses go around a wrapped global entirely.
- `e2e/local-review.ts` — seed a temp git repo (reuse M8.3's `local-fixture-repo.ts` if it is importable
  from a script; otherwise a small local seeder in the driver), assert the repo has **zero** remotes so no

## Landmines

- **The gate runs `bun test` before the app build**, so `packages/app/dist` does not exist during tests
  (`package.json:18`; `memories/known-landmines.md:24`). Any test that starts revud must point at a stub
  dist via `REVU_DIST_DIR` plus a temp `REVU_DATA_DIR`. *If missed:* leg F passes locally against a stale
  dist from an earlier build and fails on a fresh CI checkout — the classic green-here-red-there.
- **The e2e driver must never be a `*.test.ts`** (`known-landmines.md:31`). *If missed:* `bun test` sweeps
  it into the gate, launches Chrome against a nonexistent dist, and the whole gate reds for a reason that
  has nothing to do with the change under test.
- **One mock store for the entire `bun test` process.** `test/preload.ts:13` is a single `Map`, and the mock
  store debounce-flushes into it, so one file's mutations leak into another's `load()`. Every mock-driving
  file must `mockDev.reset()` in `beforeAll` (`mock/conformance.test.ts:24-28`). *If missed:* legs A and E
  interfere order-dependently — reliably green locally, intermittently red on the slower CI runner. This
  ticket adds a **second** mock-driving conformance file, which raises the odds materially.
- **"Zero GitHub requests" must be affirmative, not inferred.** A daemon booted with no token and no origin
  will *fail* a GitHub call — that is not the same as never making one, and a swallowed failure reads as
  success. Record at the `fetch` boundary and assert the log is empty. *If missed:* the exit criterion's
  structural proof degrades to an absence of visible symptoms.
- **The `fetch` guard does not cover `git` subprocesses.** `createBunCommandRunner`
  (`command-runner.ts:42-63`) spawns real processes; a `git fetch` or `git ls-remote` would go around a
  wrapped global `fetch` entirely. Mitigate with a fixture repo that has **zero** remotes plus
  `GIT_TERMINAL_PROMPT=0`, and say so in the driver's docstring rather than implying total coverage.
  *If missed:* the e2e claims more than it proves.
- **`e2e/` and `scripts/` are not typechecked.** The root `tsconfig.json` references only the four package
  configs, none of which includes those directories. *If missed:* "tsc is clean" is read as "the new e2e
  driver compiles", and a type error surfaces only when CI runs the script — after the gate has already gone
  green. M8.11.8 closes the `e2e/` + `test/` half of this **before** those files are written; `scripts/` stays
  out with a recorded reason (see Testing exceptions), so the landmine survives there. And note the second
  half of the trap: a project reference whose `include` matches nothing is silently green, so the new project
  is not coverage until a deliberate type error has been seen to red it.
- **`packages/docs` is outside the gate three ways**: excluded from the workspace (`package.json:6`),
  ignored by oxlint (`.oxlintrc.json:4`), and built only by `docs.yml` under a `paths:` filter
  (`docs.yml:10-17`). And `docs/security-review.md` lives at the repo root, matching *no* workflow filter at
  all. *If missed:* a broken MDX link, an unregistered nav page, or a malformed security-review edit lands
  fully green.
- **Fixture-count assertions are load-bearing in two places.** M8.1's decision D-a puts the fixture local
  review in `listPulls`, so `scripts/smoke.ts:54-61` **will** go red — and smoke.ts is in no gate, so the
  breakage is silent until someone runs it by hand. Its in-gate twin (`scenarios.test.ts:61`, `:64-67`) is
  M8.1's to move; the smoke script is this ticket's.
- **`DirectApi` is not a `RevuApi`, and the compiler is the only thing that says so early.** Three
  divergences (sync `getSnapshot`, a differently-signed `listPulls`, no `listReviewThreads` at all) mean leg G
  cannot call `runLocalReviewConformanceSuite` on `createDirectApi`'s return value. *If missed:* the unit
  reads as done, `tsc -b` reds at the end of the work, and the instinct is to weaken the suite — which would
  either drop assertions the mock legs do enforce or push the daemon into implementing the thread route M8.5
  deliberately 501s.
- **A leg-G api assembled without the local surface throws `not_found` on its first local call.** M8.5.1
  makes a local id with no `localReviews` dep a typed `not_found` by design (fail closed). *If missed:* the
  leg reds with an error that reads like a suite bug rather than a missing dep, and the fix looks like
  loosening an assertion.
- **Do not hang leg G off leg C's token gate.** Leg C skips without `GH_TOKEN`/`GITHUB_TOKEN` by design
  (`conformance-matrix.ts:172-179`). *If missed:* "conformance is green over a local-review leg in every
  transport" silently becomes "…unless the runner has no token", which is exactly the skipped leg the exit
  criterion forbids.
- **The restart hook is where durability is proven** (`suite.ts:412-444`). Leg G must reopen the same
  on-disk store; `:memory:` (as `conformance-reads.test.ts:32` uses, correctly, for a suite that never
  restarts) would make the assertion vacuous. *If missed:* the leg silently stops testing the single most
  important property in the product — drafts survive everything.
- **Every new runner runs twice**: once inside the plain `bun test` of `bun run check`, and once when
  `conformance-matrix.ts:123-127` spawns it in isolation. Temp dirs must be `mkdtempSync`-unique per run and
  daemons killed in `afterAll`. *If missed:* a leaked port or a shared data dir makes one leg fail and
  reports the *next* leg as broken.
- **The e2e job's 10-minute cap is shared** (`ci.yml:89`). The local driver adds a second full browser flow
  plus a git-repo seed to a job that today finishes in seconds. *If missed:* a slow runner turns a correct
  change into a red timeout, which reads as a flaky feature rather than a budget decision.

## Testing exceptions

Three things here carry no automated assertion. Each is named with what compensates — an acknowledged
exception is fine, a silent one is how a suite rots.

1. **Whether the prose says a true thing.** `local-review.mdx`, the two run-modes pages, the
   `compare-key.mdx` cross-link, `docs/security-review.md`, and the `ci.yml` step name and job comment are all
   English. No test asserts that the D8 paragraph describes D8 correctly, or that the step name now matches
   which legs are required. *Compensating:* `test/docs-nav.test.ts` proves the page is reachable,
   `packages/revud/src/security-review-claims.test.ts` proves every path a claim names still exists,
   `bun run docs:build` proves the MDX compiles and its links resolve, and the pre-merge fable-tier review
   reads the prose against D1 / D4 / D5 / D8 as part of its brief.
2. **The exit-criteria walk (Verify 7).** Judging that a criterion is *met* by a ticket's Verify is a call
   about coverage, not a runnable assertion. *Compensating:* every criterion in
   `docs/agent/MILESTONES.md:428-434` names the ticket that proves it in `BOARD.md`'s coverage table, and the
   mechanical half of most of them is the exit code of `conformance:matrix` or `test:e2e`.
3. **`scripts/` stays outside `tsc -b`** — M8.11.8 covers `e2e/` and `test/` only. The repo carries no
   `@types/bun` on purpose and hand-writes a minimal ambient surface per package, so type-checking all of
   `scripts/` means writing ambients for `gifs.ts`, `shots.ts` and the broker scripts too: an unrelated cleanup
   this ticket must not absorb (§5.8). *Compensating:* `test/smoke-script.test.ts` runs `scripts/smoke.ts`
   in-gate, `conformance:matrix`'s own exit code gates `scripts/conformance-matrix.ts` on every CI run, and
   oxlint already lints both (`.oxlintrc.json:4` ignores only `packages/docs`). Record the residue as a
   follow-up on the board.

## Open questions

1. **Leg ids and how the summary groups.** `E` / `F` / `G` is append-only and honest, but it separates
   "mock in-process (PRs)" from "mock in-process (local reviews)" in the printed summary rather than
   grouping by transport. The alternative — running both suites inside the existing A/B runner files —
   keeps the summary at four lines but makes a failure attributable only to a transport, not to a feature.
   Recommendation: E/F/G. The owner may prefer `A2`/`B2`/`C2` or a grouped two-column summary.
2. **Where leg G's runner lives.** M8.3 and M8.4 put `local-sync.ts` / `local-writes.ts` under
   `packages/revud/src/direct/`, so `direct/conformance-local.test.ts` is consistent — but "direct" is
   becoming a misleading name for a path with no GitHub in it. Renaming is out of scope here; the
   implementer should either accept the inconsistency deliberately or raise it as a follow-up.
3. **Whether M8.1.6's `local-scenario.test.ts` collapses into a runner of this ticket's shared suite.**
   Doctrine says one copy of the assertions (`conformance-matrix.ts:1-12`), which argues for reducing it to
   a thin runner exactly as `mock/conformance.test.ts` is. But that edits a file another ticket owns and
   may drop mock-specific assertions the shared suite cannot express. Decide before writing M8.11.1, which is
   where the mock runner now lands.
4. **How far the local e2e should walk.** The exit criterion names create → sync → comment → submit. A
   re-sync-after-a-new-commit leg would be far stronger evidence for drafts-surviving-everything, but it is
   M8.8's territory, it lengthens the browser flow, and the e2e job is capped at 10 minutes. The design does
   not settle this.
5. **Whether `bun run check` should absorb the matrix and/or the e2e.** Today they are separate CI jobs with
   `needs: check`, and the exit criterion's phrasing ("`bun run check` + e2e green") implies they stay
   separate. Confirm rather than assume — folding them in would add a browser launch and three daemon spawns
   to every local gate run.
6. **Whether the docs site needs local-review screenshots or GIFs.** `scripts/shots.ts` and `scripts/gifs.ts`
   exist and the rest of the docs site uses captured imagery. Nothing in the exit criteria requires it, but
   a text-only page beside illustrated siblings is a visible inconsistency. Owner call on scope.
7. **What the e2e asserts about M8.9's archived state.** Archive-on-PR-appearance needs a PR to exist, which
   a zero-GitHub e2e cannot produce. Either the archived state is proven only at the unit level (M8.9's own
   Verify) and the e2e stays silent about it, or the e2e drives a daemon-side injection of a fake PR listing
   — which would weaken the "no GitHub client in scope" story it exists to prove. The design does not
   resolve this; recommend the former and say so explicitly in the driver's docstring.
