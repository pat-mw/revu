## Goal

Give the direct-mode store its first eviction path: delete a local review completely (rows, snapshots,
pinned git refs) and prune the immutable halves and blob bytes that no live snapshot references any more.
This exists because of `LOCAL_REVIEWS.md §8` case 23 — the store has exactly one `DELETE` today
(`store.ts:464`, `deleteDraft`), the `immutables` and `blobs` tables are explicitly cache-forever with no
TTL, and a constantly rebased local branch mints a fresh `compareKey` on **every** sync and orphans the
previous immutable half forever. It also completes **D4** (`LOCAL_REVIEWS.md §3`): local state lives in its
own tables, so its deletion is scoped to those tables and must never reach into `snapshots`, `audit_log`, or
`pr_author`; and it discharges the retention half of `§5.1`'s object pinning — pinning objects under
`refs/revu/reviews/…` is only safe if something eventually drops those refs, so "retention becomes an
explicit delete rather than an accident of `git gc`". The danger this ticket is designed against is
**over-deletion**: removing an immutable half a live snapshot still points at does not degrade gracefully,
it turns `getSnapshot` into a 500 `persist_failed` (`store.ts:341-352` → `direct-router.ts:186-188`) and the
review becomes unopenable.

## Units

Default execution order. **M8.10.1, M8.10.2 and M8.10.3 are mutually independent** and can run in parallel:
the first is pure SQL on the local tables, the second is pure git via the injected `CommandRunner`, the
third is a read-only computation over existing tables. **M8.10.4 depends on M8.10.3**; **M8.10.5 depends on
M8.10.3 and M8.10.4** (it prunes over the *surviving* immutables, so the ordering is load-bearing);
**M8.10.6 depends on all five.** The shared edit across 1, 3, 4 and 5 is the append to the `DirectStore`
interface (`store.ts:172-249`) — expect a trivial conflict there and nowhere else.

**Why M8.5 is a dependency.** M8.10.6 puts `deleteLocalReview` on the api surface (`direct-api.ts`) — the
surface M8.5.1 builds and the local dispatch M8.5.1 defines — and it **takes over serving**
`DELETE /api/local-reviews/:n`, which M8.5.2 deliberately leaves on the honest known-route 501 because the
store method behind it is M8.10.1's. Without the dependency the two tickets were unordered and each assumed
the other had the route: M8.5.2 would have had to invent a bare row delete colliding with M8.10.1's
transactional counts contract, or leave the route failing its own check. M8.5.2's route table now pins the
501 explicitly, and this ticket rewrites that case rather than adding one.

### M8.10.1 — `deleteLocalReview`: the store's second `DELETE`
**Do:** Add `deleteLocalReview(localId: number): { … counts }` to `DirectStore`, removing the review's rows
from all six `local_*` tables in **one** `db.transaction` inside the existing `write()` wrapper
(`store.ts:291-297`) so a partial delete is impossible and a failed persist is a `StoreWriteError`, never a
silent success. Model it statement-for-statement on `purgeWorkingState` (`collector/host-store.ts:467-484`)
— the only other transactional delete in the repo — including returning per-table `.changes` counts, which
are what makes the unit's assertions evidence rather than hope. It deletes `local_drafts` / `local_viewed`
rows for **every** human, not just the session's, because the row key is the review (see Landmines and Open
questions). It touches no PR-keyed table, no `immutables` row, and no `blobs` row: those are M8.10.4 and
M8.10.5, under a reference rule, not a cascade.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** `bun test packages/revud/src/direct/store.test.ts` with cases asserting: after a delete,
`getLocalReview` / `getLocalSnapshot` / `getLocalDraft` / `getLocalViewed` / `listLocalThreads` /
`listLocalSubmittedReviews` all read back empty-or-null for that id, and a raw
`SELECT COUNT(*) FROM local_drafts WHERE local_id = ?` (repeated per local table) is `0`; a second, unrelated
local review's rows are untouched; the returned counts equal the rows that existed; deleting an id that was
never created is a no-op returning all-zero counts (idempotent, never a throw); and the delete extends
M8.2.6's trigger-guarded containment test — with `RAISE(ABORT)` triggers installed on
`snapshots`/`audit_log`/`pr_author`, the whole delete runs without firing one.

### M8.10.2 — Drop a deleted review's pinned refs
**Do:** Add a local-only retention module `packages/revud/src/direct/retention.ts` exporting
`dropPinnedRefs({ runner, cwd }, localId)`. **This unit is the milestone's only ref-deletion path** — M8.8.1
writes and lists pins and deliberately exports no delete, so there is exactly one implementation and it is
this one. **Discover** the refs — `git for-each-ref --format='%(refname)'
refs/revu/reviews/<id>/` — and delete each with `git update-ref -d <refname>`; do **not** reconstruct the
ref name from `<id>/<compareKey>`, because the compareKey contains `...` and a name with two consecutive
dots is rejected by git outright (see Landmines: verified). The prefix is safe under any encoding M8.8 picks:
M8.8.1's `pinRefsFor` keeps `<localId>` and `<pinKey>` in **directory** position (a ref *at*
`refs/revu/reviews/<id>` would make every child unwritable), so `refs/revu/reviews/<id>/` always names a
directory and never a ref. Every argument goes through the argv-array
`CommandRunner` (`command-runner.ts:31-33`) — no shell — and the id is stringified from a validated integer
so nothing user-supplied reaches an argv slot. Report a count and the refnames dropped. The function must be
correct **before M8.8 lands**: an empty namespace makes `for-each-ref` exit 0 with no output and
`update-ref -d` on an absent ref also exits 0, so "no refs pinned yet" is a clean zero, not an error. Do not
run `git gc` — reclaiming the objects is the user's or git's own call, and this module never mutates the
user's working tree.
**Files:** `packages/revud/src/direct/retention.ts`, `packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts` with (a) a fake `CommandRunner`
asserting the exact argv arrays and that nothing is spawned when discovery returns empty, and (b) a real
temp-repo test: `git init`, one empty commit, create two refs under `refs/revu/reviews/1000000001/`, run
the drop, then assert `git for-each-ref refs/revu/reviews/1000000001/` prints nothing while a ref under a
*different* local id survives. Run the drop twice and assert the second call is a zero-count no-op.

### M8.10.3 — The live `compareKey` set, computed fail-closed
**Do:** Add a store read that returns every `compareKey` referenced by a live snapshot — both
`snapshots` (PR) and `local_snapshots` — and a matching `listImmutableKeys()`. The key is **not a column**:
it lives inside the stored envelope JSON (`StoredSnapshotEnvelope.compareKey`, `store.ts:144`), so the read
either uses SQLite's `json_extract(data, '$.compareKey')` (verified available under `bun:sqlite`) or parses
each row through `parseRow` (`store.ts:252-258`). Whichever is chosen, the rule is **fail closed**: a row
whose JSON will not parse, or whose extracted key is null/empty, throws `StoreUnreadableError` and aborts
the caller — it is never silently skipped, because a skipped row reads as "references nothing" and every
immutable it pointed at becomes prune bait. This unit adds no delete.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** `bun test packages/revud/src/direct/store.test.ts`: a store holding one PR snapshot and one local
snapshot on distinct compares returns exactly those two keys; two snapshots sharing one compareKey return it
once; corrupting a `snapshots.data` row with `UPDATE snapshots SET data = 'not json'` makes the read throw
`StoreUnreadableError` (mirroring `store.test.ts:236-249`), and the same for `local_snapshots`; an envelope
whose `compareKey` is absent throws rather than returning a short set.

### M8.10.4 — Prune unreferenced immutable halves
**Do:** Add `deleteImmutables(keys: string[])` to the store and `pruneImmutables(store)` to
`retention.ts`. The rule is **reference-based, never age-based**: an immutable row is deletable iff its
`compare_key` appears in `listImmutableKeys()` and not in the live set from M8.10.3. Compute the set and
issue the deletes inside **one** `db.transaction`, so a snapshot written between the read and the delete
cannot be stranded. Return the count and the keys removed. Nothing here reads a timestamp, and no
`last_synced_at`, `updated_at` or row age may enter the predicate — "no TTL on the immutable store" is a
hard constraint, and reference-counting is what lets this ticket bound growth without breaking it.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/retention.ts`,
`packages/revud/src/direct/store.test.ts`, `packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts`: seed a store with a PR snapshot on
`A...B`, a local snapshot on `C...D`, and two orphans (`A...old`, `C...old`) written via `putImmutable`;
after the prune, `SELECT COUNT(*) FROM immutables` is 2 and the two live keys are the survivors. The
load-bearing assertion is the sweep: **for every `pr_number` in `snapshots` and every `local_id` in
`local_snapshots`, `getSnapshot`/`getLocalSnapshot` still returns a snapshot and throws nothing** — that is
the direct test for the over-deletion failure at `store.ts:341-352`. Plus: a prune over a store with a
corrupt snapshot row deletes **nothing** and propagates `StoreUnreadableError`; a prune on an
already-pruned store removes 0 rows.

### M8.10.5 — Blob retention under the same reference rule
**Do:** Add `listBlobShas()` + `deleteBlobs(shas: string[])` to the store and `pruneBlobs(store)` to
`retention.ts`, running **after** `pruneImmutables` and walking only the surviving immutables' `blobIndex`
(both sides per path — the same walk `collectShas` does at `blobs.ts:188-197`, and the same one the mock's
seed already performs at `packages/app/src/api/mock/store.ts:134-142`). A SHA referenced by no surviving
immutable is deletable; everything else stays. Blobs are content-addressed and **shared between PR and local
snapshots**, so this is strictly riskier than pruning immutables: one over-deletion breaks a review that has
nothing to do with the one being cleaned up. Encode the recovery asymmetry in the docstring — a PR's blob is
re-fetchable from GitHub on the next sync, a local review's blob may be the **only** copy once the branch is
rewritten and its pinned refs are gone. Ship the blob prune behind an explicit caller-supplied policy flag
rather than folding it into `pruneImmutables`, so the immutable prune (the one that actually bounds growth)
can land and run without carrying the blob risk (see Open questions).
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/retention.ts`,
`packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts`: a blob referenced only by an orphaned
immutable is removed; a blob referenced by a **live PR** snapshot survives a local-review delete + full
prune; a blob shared by a live PR snapshot and an orphaned local immutable survives; after any prune,
`store.getBlob(sha)` is non-null for every sha in every surviving immutable's `blobIndex` (the mirror of
M8.10.4's sweep, and the exact precondition `direct-api.ts:257-269` and `reconcile.ts:78-82` depend on).
Assert removal by `SELECT COUNT(*) FROM blobs`, never by file size.

### M8.10.6 — Where the prune runs, the churn bound, and the written policy
**Do:** Wire the pieces: `deleteLocalReview` on the api surface performs the row delete (M8.10.1), drops the
pinned refs (M8.10.2), then prunes (M8.10.4, and M8.10.5 per policy) — in that order, because dropping refs
after a prune leaves a window where objects are pinned for data that no longer exists, and pruning before
the rows are gone would see the doomed review's compareKey as live. **Take over serving
`DELETE /api/local-reviews/:n`** here: M8.5.2 leaves it on the known-route 501 fall-through
(`direct-router.ts:157-175`, `:495-516`) and pins that with an explicit test case, so this unit rewrites that
case rather than adding one, and the route is served through M8.5.1's local dispatch like every other id-keyed
surface. Decide and implement the prune cadence
(Open questions) and guard it against the in-flight-sync window described in Landmines. Then write the
policy down where operators and the next implementer will actually find it: extend the store module
docstring's table inventory (`store.ts:15-62`) with what is deletable and on what rule, and add a retention
subsection to `docs/operator-runbook.md` beside "Durable data directory" (`operator-runbook.md:150-157`)
stating plainly what a delete removes, what is never removed (`audit_log`, `pr_author`, and any PR-keyed
row), that reclaiming disk in the git object database is `git gc`'s job and revu does not run it, and that
the SQLite file does not shrink on delete. Keep every code comment self-contained — no ticket ids, no
milestone references (AGENTS.md).
**Files:** `packages/revud/src/direct/retention.ts`, `packages/revud/src/direct/store.ts`,
`packages/revud/src/direct/direct-api.ts`, `packages/revud/src/direct-router.ts`,
`packages/revud/src/direct-router.test.ts`, `docs/operator-runbook.md`, plus the tests for the wiring
**Check:** An end-to-end test in `retention.test.ts` over a temp data dir + temp git repo: create two local
reviews, sync-shaped writes for each (two compareKeys apiece so each has one orphan), pin refs for both,
delete the first — then assert in one pass that review one's rows are gone, its refs are gone, review two's
rows/refs/snapshot/threads/drafts are **untouched**, `getLocalSnapshot(two)` still returns a snapshot,
`immutables` holds exactly review two's live key, and a PR snapshot seeded alongside is byte-identical

## Constraints that bind this ticket

- **No TTL on the immutable store** (`memories/hard-constraints.md`; restated in the store's own docstring
  at `store.ts:27-34`). Eviction here is **reference-based only**. A `WHERE created_at < …` or
  `last_synced_at`-driven sweep would be a TTL by another name and is a defect even if every test passes.
  Nothing in the schema even records when an immutable row was written, which is the constraint made
  physical.
- **Drafts survive everything — a draft is deleted only on confirmed submit success**
  (`memories/hard-constraints.md`). The prune must therefore never delete a draft, and the review delete
  must be an explicit user act with a clear consequence, never a background sweep. This is the sharpest
  tension in the ticket: deleting a review deletes its drafts.
- **D4 — the local path never touches PR-keyed tables** (`LOCAL_REVIEWS.md §3`). `snapshots`, `audit_log`
  and `pr_author` are read by the host collector, the broker poll loop and the out-of-band-write detector
  as facts about the client repo. Deleting from them is worse than writing to them: `audit_log` has no
  delete counterpart *by design* (`store.ts:206-212`, `store.test.ts:405-414`) and must not grow one.
- **D1 — archiving is read-only, never destructive** (`LOCAL_REVIEWS.md §3`, `§8` case 22). A review that a
  PR superseded keeps its threads, drafts and history. Nothing in this ticket may auto-delete an archived
  review; `archived_pr` being set is not a retention signal.
- **D7 — no GitHub client in scope** (`LOCAL_REVIEWS.md §3`). The retention module's only dependencies are
  the store and the `CommandRunner`. Structural absence, not a conditional.
- **Absent ≠ unreadable** (`store.ts:56-61`). For reads this means a missing row is `null`; for the prune it
  means **fail closed** — an unparseable snapshot envelope aborts the whole operation, because the
  alternative (skip it) silently reclassifies everything it referenced as garbage.
- **No swallowed write failures** (`store.ts:85-100`, `:291-297`). Every delete goes through `write()` and
  surfaces `StoreWriteError`.
- **Migration doctrine: no table rebuilt** (`store.ts:616-630`). This ticket adds no schema and must not
  `VACUUM` — a `VACUUM` rewrites the entire database file, cannot run inside a transaction, and takes an
  exclusive lock on the file that holds every draft.
- **Two-half caching stays intact** (`memories/hard-constraints.md`). The prune may remove an immutable half
  only when no snapshot names its key; it may never remove one to "force a refresh", and it may never
  short-circuit the mutable fetch.
- **The frozen contract is read-only here.** `deleteLocalReview` as an API method and route belongs to M8.1
  and M8.5; this ticket owns the store semantics behind it. If the wire shape looks wrong, report it rather
  than editing `packages/shared/src/api/*`.
- **Ref-name hardening** (`LOCAL_REVIEWS.md §8` case 7). Even though this ticket only handles ids it minted
  itself, the ref path is still built and passed to git: argv array, no interpolation into a single string,
  ids validated as integers.
- **AGENTS.md code style**: self-contained comments — no ticket ids, no milestone numbers, no "phase" in any
  line of code, SQL, or docstring. `import type` for types; no unused bindings; no stubs or TODOs.

## Landmines

- **The pinning path from `§5.1` is not a legal git ref name.** `compareKey` is
  `<mergeBase>...<head>`, and git rejects any ref whose name contains two consecutive dots. Verified
  directly: `git check-ref-format refs/revu/reviews/1000000001/<sha>...<sha>` exits 1, and `git update-ref`
  answers `fatal: … refusing to update ref with bad name`. So M8.8 must encode the key (a single separator,
  or a hash) and **this ticket must not reconstruct ref names from the compareKey** — discover them with
  `for-each-ref` under the `refs/revu/reviews/<id>/` prefix. Miss it and the drop silently deletes nothing
  while reporting success, and every object stays pinned forever.
- **The in-flight-sync window.** `syncPull` writes the immutable half at `sync.ts:450` and the blobs at
  `blobs.ts:299`, but the snapshot envelope only at `sync.ts:506`, with network `await`s in between. A
  prune triggered by another request during that window sees the fresh immutable and its fresh blobs as
  unreferenced. The immutable damage self-heals (`putSnapshot` rewrites the row at `store.ts:403`); the
  **blob** damage does not — `putBlobs` already ran, so the sync completes with bytes missing and the file
  viewer 404s until a re-sync. Guard the prune against a concurrent sync (an in-flight counter is the
  honest fix) or accept and document the recovery.
- **Over-deleting an immutable is not a cache miss.** `getSnapshot` throws (`store.ts:341-352`) → the router
  answers 500 `persist_failed` (`direct-router.ts:186-188`). The review becomes unopenable, and because the
  immutable half is *derived* data the instinct is to assume a re-sync fixes it — for a local review whose
  branch was rewritten, it does not.
- **A corrupt snapshot row read as "references nothing" is the catastrophic bug.** The compareKey lives
  inside a JSON blob; `json_extract` on a malformed document returns NULL rather than raising. Treat NULL as
  fatal. One unreadable row must abort the prune, not shrink the live set.
- **`MAX(id)+1` re-mints a deleted review's id** (M8.2's open question 3). If any row survives the delete —
  another human's `local_viewed`, a stray `local_threads` row, a pinned ref — the next review created for a
  different branch pair silently adopts it. Either the delete provably removes every dependent row across
  every human, or M8.2 must switch to a monotonic high-water mark. Decide before writing the delete, not
  after.
- **`local_drafts` / `local_viewed` are keyed `(human_id, local_id)`**, so a delete by review id deletes
  **every** human's draft on that review and scans the table to do it (the PK indexes `human_id` first).
  One workspace has one human today, so this is latent — but it is a real cross-human deletion path and the
  docstring must say so plainly rather than letting a reader assume session scoping.
- **The database file does not shrink.** SQLite marks pages free and reuses them; `ls -l` after a delete is
  unchanged. Assert `SELECT COUNT(*)` (or `PRAGMA freelist_count`), never file size, or the test will look
  broken while the code is correct — and do not "fix" it with `VACUUM`.
- **Dropping refs does not free disk either.** The objects survive until the user's own `git gc` runs.
  Saying "deleted" in a UI toast that means "unpinned" is a lie the runbook must pre-empt.
- **Blobs are the shared surface.** One SHA can back a PR snapshot and a local snapshot at once
  (`blobs.ts:188-197` collapses paths to SHAs precisely because they are shared). A blob prune bug shows up
  in a review nobody touched. Prune blobs last, over surviving immutables only, and keep the immutable prune
  independently shippable.
- **Do not add a delete-shaped audit method.** `store.test.ts:405-414` filters store keys for `audit` and
  pins the surface to `['appendAudit','listAudit']`. Beyond the test, it is the D4 promise: journaled writes
  to the client repo are permanent.
- **`archived_pr` is not a tombstone.** D1 makes a superseded review read-only and *preserved*. Wiring
  archive → delete would destroy exactly the training history the milestone exists to keep.
- **Deleting the review while a draft has unsubmitted text** is the one place this ticket can violate
  "drafts survive everything" (`memories/hard-constraints.md`). Whatever the answer, it must be deliberate —
  see Open questions.

## Open questions

1. **Is the blob prune on by default?** `LOCAL_REVIEWS.md §8` case 23 says "leaving content-addressed blobs
   alone or pruning them under the same rule" and picks neither. Immutable halves are the bulk of the churn
   (files + patches + commits per compare) and are safe to reclaim; blobs are the shared, sometimes
   irrecoverable ones. Recommendation is to ship the walk plus the prune, default **off**, and turn it on
   once the immutable prune has run in anger — but the owner should choose, because "we grew a GC that
   doesn't collect the big thing" is a legitimate objection.
2. **When does the prune run?** Candidates: only inside `deleteLocalReview`; after every successful local
   sync (bounds churn continuously, but sits closest to the in-flight-sync window); at boot (fast, quiet,
   but a fail-closed prune then turns a corrupt row into a failed startup, `index.ts:170-171`); or a manual
   operator command. The design doc says only "bound the growth introduced by re-sync churn and document the
   policy". Whatever is chosen becomes the growth bound, so it is a policy decision, not an implementation
   detail.
3. **What happens when the review being deleted has a non-empty draft?** Silently delete, refuse unless an
   explicit `force` flag is set, or delete but return the discarded draft count so the UI can warn first?
   The hard constraint about drafts is written for *submit* flows and does not settle an explicit
   user-initiated review delete. M8.6/M8.7 need the answer to render the confirm dialog.
4. **Id reuse vs a high-water mark** — inherited from M8.2's open question 3 and now load-bearing. If M8.2
   ships `MAX(id)+1`, this ticket must prove exhaustive deletion (including pinned refs) or a recycled id
   adopts stale rows. If M8.2 ships a `meta` high-water mark, the whole class disappears. **This ticket
   should not be started until that is settled.**
5. ~~**The ref encoding, and M8.8 ordering.**~~ **Answered by M8.8.1**, which requires `<localId>` and
   `<pinKey>` to be **directories, never refs** — a ref at `refs/revu/reviews/<id>` makes every child
   unwritable, verified — so a flat scheme is not available to M8.8 and `refs/revu/reviews/<id>/` always
   names a directory. Prefix discovery is therefore correct under every encoding M8.8 may pick and correct
   before M8.8 lands. M8.8.1 also exports **no** delete: ref deletion is wholly this ticket's, which is what
   keeps the two tickets from shipping the same function twice.
6. **Does `deleteLocalReview` refuse on an archived review?** D1 preserves archived reviews as history; an
   explicit user delete arguably still applies. Only "archiving must not *auto*-delete" is settled.
7. **Should live compareKeys include the ones recorded on drafts** (`types.ts:441`)? Nothing in revud reads
   `draft.compareKey` as a store key today, so the answer is probably no — but a future "reconcile against
   the compare I wrote this against" feature would make it yes, and adding it later means the rows are
   already gone. Cheap to include, so the question is whether the extra retention is worth the confusion.
8. **What does `deleteLocalReview` return on the wire?** M8.1 declares the method; the counts this ticket
   produces (rows, refs, immutables, blobs) are useful operator evidence but may not belong in the contract
   response. Confirm with M8.1's frozen shape before designing around them.
9. **Is there anything for M8.11's conformance leg to assert?** The mock has no `immutables` table at all
   (`packages/app/src/api/mock/store.ts`), so orphaning cannot exist there and the prune is unobservable
   through `RevuApi`. That suggests retention is proven by revud-internal tests only, and the conformance
   matrix covers `deleteLocalReview`'s *visible* semantics (the review disappears from the list) and nothing
   more. Confirm with M8.11's owner so the gap is deliberate.
