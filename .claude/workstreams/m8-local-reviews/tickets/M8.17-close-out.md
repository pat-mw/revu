## Goal

**M8 exists on a branch and nowhere else.** Fifteen pull requests are open and none is merged; `main` and
`origin/main` are both still `177068a`, and the stack tip is 205 commits and **zero merge commits** ahead of
it. Every exit criterion in [`MILESTONE.md`](../MILESTONE.md) has a green run *on the stack tip* and an
**unchecked box**, because the boxes were always going to tick when the chain merged
(`MILESTONE.md:88-95`). This ticket is that day.

It exists as a ticket rather than a paragraph in the handover because the merge is the one operation in this
workstream that **cannot be re-run**. A squash instead of a merge commit cannot be undone by pressing merge
again; a PR merged before its predecessor lands on the wrong branch; a PR whose base is never retargeted
merges into a branch that is no longer anyone's history. The landing audit of 2026-09-02 read the whole chain
and found **nothing blocking the merge and five procedural facts that will bite the merger** — no
auto-retarget, three allowed merge methods with only one correct, an admin-only merge path, no required
status check, and two stale worktrees holding branches in the middle of the chain. Those five are this
ticket's first unit.

What follows the merge is the part a milestone is actually judged on: **the runs that make the ticks true**
(the full gate, the conformance matrix and the e2e suite, on `main`, with their numbers recorded), the exit
criteria ticked one at a time **each naming the run that proves it**, and the six records — `MILESTONE.md`,
`BOARD.md`, every ticket's `State`, `docs/agent/MILESTONES.md`, the repo memories, and `gh pr list` — brought
into agreement and read back once, together, by one agent.

**This ticket writes no code.** Its whole diff is the board, `MILESTONE.md`, `docs/agent/MILESTONES.md` and
`.claude/skills/revu/memories/`. If a unit here finds itself editing `packages/`, it has found a defect that
belongs to another ticket, not a close-out step.

**The close rule, stated once and enforced by M8.17.8:** M8.17 cannot move to `Done` while any unit in
M8.13–M8.16 is open. Closing a milestone over four tickets carrying the audit's surviving majors would make
the ticked boxes claim something the tree does not do.

**And M8.17 cannot mark itself `Done` either.** `Done` needs a *merged* PR, every board edit rides a PR, and
this ticket's record rides `m8.17/close-out` — so while .1–.8 are being written that PR is open and M8.17 is
`In Review` by construction. M8.17.9 is the way out: the owner merges this ticket's PR, then a one-line
`board/m8-sealed` PR flips the `State` row and `BOARD.md` together. Every "all seventeen are `Done`"
assertion belongs there, and nowhere earlier.

## Binding constraints

- **The owner merges. An agent never does.** `.claude/skills/revu/memories/pr-cadence.md:7-8` — "Merging
  stays out of bounds… Never merge, never commit to `main`, never retarget." Every checklist step that
  presses a button on github.com is the owner's. The agent derives the order, verifies the preconditions,
  watches CI and records what happened. Open question 3 is the only place that line could move, and only the
  owner can move it.
- **Merge commits, never squash, never rebase.** All three are enabled on the repo and allowed by the
  ruleset, so nothing but this sentence prevents the wrong one.
- **A ticket is `Done` only when its `## Verify` was actually run green *and* its PR is merged** —
  `../README.md:72` (rule 5) and `../BOARD.md:245-247`. Verify alone has never been sufficient in this
  workstream and must not become sufficient on the last day.
- **Do not close a workstream with unchecked exit criteria** (`../README.md:74`, rule 6) — and do not tick a
  box without naming the run that proves it. A tick with no run beside it is the failure mode this ticket
  exists to prevent.
- **`BOARD.md` wins, and it changes in the same edit as the ticket `State` it disagrees with**
  (`../README.md:62`, rule 1).
- **The doc and the board never drift** — `docs/agent/MILESTONES.md:5` and
  `.claude/skills/revu/memories/tracking-coordinates.md:29-30` ("if scope changes, update the doc and the
  board in the same PR/session"; `:31-32` is a different rule — the board is admin tracking, not
  documentation). M8.12 already broke this rule once; M8.17 closes it for M8.12 **and** for M8.13–M8.17 in
  the same edit.
- **Board edits ride a PR** (`../README.md:66`, rule 3); committing to `main` stays forbidden, including on
  the day `main` finally moves.
- **Audit ids live in this file and in commit messages only.** Nothing this ticket writes into `docs/` or
  `packages/` may name a ticket, a PR number, a phase, a session, an agent or an audit (`AGENTS.md`). The
  board is admin tracking and may; `docs/agent/MILESTONES.md` is a seed document and names milestones and
  issues, which is its own vocabulary, not a tracking reference.

other step below is the owner's on the day.

*The checklist.*

**Before the first merge**

1. **`git worktree prune`** in the main clone. `m8.3/local-snapshot-builder` and `m8.4/local-write-sink` are
   checked out in two prunable scratchpad worktrees, and `git branch` marks both with `+`. Nothing is pending
   on them, so this blocks no merge — but it will refuse a `checkout` or `rebase` of exactly those two
   branches from the main clone, which is the middle of the chain. Prune first, before anything touches them.
   Afterwards `git worktree list | grep -c prunable` prints `0` and the `+` markers are gone.
2. **Re-derive the live chain.** `gh pr list --state open --limit 40 --json number,baseRefName,headRefName`,
   then walk from the PR whose base is `main`, following base → head. The recorded order (2026-09-02, still
   true at the time of writing) is **#69 → #70 → #71 → #72 → #73 → #74 → #75 → #76 → #77 → #78 → #79 → #80 →
   #82 → #83 → #84**, plus whatever M8.13–M8.16 and this ticket add above #84. **There is no #81** — the
   numbering skips it and nothing is missing. **#77 is a stowaway** (`prefs/lost-update`, a pre-existing store
   fix the board itself labels "not M8"); it sits inside the line and merges with it. The list is a chain only
   if every base equals the previous head; if it is not, stop and reconcile before merging anything.
3. **Confirm `main` has not moved.** `git rev-parse main origin/main` — both `177068a…` — and
   `git merge-base main <chain tip>` equal to that same SHA. The audit's "every retargeted PR merges cleanly
   by construction" holds *only* while `main` is the merge base. If `main` moved, the chain needs rebasing and
   this checklist is void.
4. **Read the merge path out loud** before the first click: the admin's bypass is the only way any of these
   merge (every PR is `BLOCKED` / `REVIEW_REQUIRED` and no review exists on any of them), and **GitHub will
   not check CI for you** — there is no `required_status_checks` rule, which is a recorded deferral, not an
   oversight. Both consequences are per-PR steps below.

**Per PR, bottom-up, one at a time**

5. **Eyeball CI before pressing anything** — `gh pr checks <n>`: `check`, `conformance-matrix` and `e2e` must
   all pass. `docs-build` appears only on #80 and #82 because `.github/workflows/docs.yml:11-17` path-filters
   it to `packages/docs/**`; its absence elsewhere is correct. **A green run on a stale head is not
   evidence** — compare `gh pr view <n> --json headRefOid` against the run's head SHA.
6. **Merge with a MERGE COMMIT.** Not squash, not rebase. Squash or rebase gives `main` a new SHA that is
   **not an ancestor** of the next branch: after retargeting, the next PR shows its predecessors' commits and
   a three-dot diff carrying their files, and the per-unit SHAs that every ticket `## Log`, `LOG.md` and
   `HANDOVER.md` cite stop resolving. It stays `MERGEABLE` — the wrongness is invisible at the merge button
   and permanent afterwards.
7. **Immediately restore the next PR's base.** `delete_branch_on_merge` is `false`, so nothing happens on its
   own and the next PR still points at a branch that is now merged history. Two ways, both the owner's, both
   needing the admin (the ruleset's `deletion` rule covers `~ALL`): **delete the just-merged head branch** and
   let GitHub retarget its children onto `main`, or **retarget the next PR's base to `main` by hand**. Open
   question 2 chooses between them; doing neither merges the next PR into a branch instead of into `main`.
8. **Re-check before moving up:** `gh pr view <n+1> --json baseRefName,mergeable,mergeStateStatus` → base
   `main`, `MERGEABLE`. Then back to step 5 for the next PR.

**After the last merge**

9. `git fetch origin`, then assert the chain is history: `git merge-base --is-ancestor <head SHA> origin/main`
   exits `0` for **every** recorded head SHA. This is the assertion a squash or rebase breaks, and the reason
   step 6 is capitalised.
10. `git log --first-parent origin/main --merges` shows **one merge commit per merged PR** and no more.
11. Hand over to M8.17.2 (the record of the walk) and M8.17.3 (the runs).

**Files:** this ticket file (the checklist above, corrected against the live re-derivation);
`.claude/workstreams/m8-local-reviews/HANDOVER.md` (a merge-day entry at the top, so the owner can act from

## Landmines

- **Ticket line pointers rot.** Every anchor above was true on this tip and will drift — and this ticket's
  anchors point at files that *other* close-out units edit, so they drift **during** the ticket. Read the seam
  before editing; a wrong anchor is worse than none.
- **A guard comparing two quantities that move together asserts nothing.** Every Check above pins an
  **independent literal** for exactly this reason: `false` and the three rule names from the API, `177068a`,
  the pinned chain order `69 … 84`, `2` then `0` prunable worktrees, `0`/`6` boxes, `17` tickets (`16`/`1`
  before the seal), and gate/copy-suite floors **re-pinned on the post-M8.16 tip, each carrying the commit it
  was measured on**. Two traps in particular. A check that compares the live `gh pr list` walk against a step
  this ticket has just rewritten *from that same walk* passes forever — which is why drift is a
  stop-and-reconcile with a `## Log` entry, and why M8.17.1's comparison is against a literal in the Check and
  never against step 2's prose. And a floor carried forward from 2026-09-02 (`3348` passes, `154` in the copy
  suite) is not independent of M8.14, which is allowed to delete vacuous tests: those two numbers are history
  recorded in the `## Log`, not the assertion.
- **A fix landing in the same edit as its test has no observed red** — and a *process* step has no test at
  all, so its control is the only thing that separates it from a claim. Every unit above names one: swap two
  numbers in a pinned literal, assert a wrong API value, leave a box unchecked, move a run off its box line,
  delete a seed, delete the `Active workstream` bullet, flip a `State`, break a required leg, append a banned
  word to a swept sentence. Restore, confirm `git diff` is empty for the file, re-run, and put **both**
  observations in the `## Log`. **A control is only a control if the named test can detect it:** *removing*
  words from a sentence can never trip a vocabulary **ban**, so a control written that way produces a recorded
  red that nobody observed. M8.17.4's mutation is an *addition* for exactly that reason.
- **The owner merges; an agent never merges, commits to `main`, or retargets a base**
  (`pr-cadence.md:7-8`). This is the one ticket where that rule is under pressure, because merge day is
  exactly when an agent could "help". It may not. See open question 3.
- **A green CI run on a stale head SHA is not evidence.** With no required status check, the merge button will
  not notice; the merger must compare the run's head against `gh pr view <n> --json headRefOid` per PR.
- **The gate is not deterministic under load.** A red on merge day is far more likely to be the known flake
  than a regression — **the discriminator is the test count**, and the flake *loses* tests while timing out a

## Open questions

Each carries **both answers written as alternative units**. **The owner decides before that unit starts.**

1. **Does the chain merge in one wave or two?**
   M8.13–M8.16 carry the audit's surviving majors and are not yet branched, while fifteen PRs are ready now.
   - **(a) One wave.** Stack M8.13–M8.16 (and M8.17) on top of the existing chain and merge everything
     bottom-up on one day — *M8.17.1 and M8.17.2 as written*. The exit criteria then tick against a `main`
     that already has the majors, and the close rule in M8.17.8 is satisfied by construction. Cost: the
     fifteen finished PRs sit unmerged for however long M8.13–M8.16 take, and every day `main` might move is
     a day the "merges cleanly by construction" argument could expire.
   - **(b) Two waves.** Merge the fifteen now, then land M8.13–M8.16 as ordinary PRs on `main` and close the
     milestone afterwards — *alternative unit: split M8.17.2 into "walk the recorded fifteen" and "merge the
     audit tickets", with M8.17.5's ticks deferred to after the second wave.* Cheaper and safer against
     `main` moving; the cost is that `MILESTONE.md` stays `ACTIVE` with a fully merged chain underneath it,
     which is exactly the state that produces a stale board.

2. **After each merge: delete the head branch, or retarget the next PR?**
   Both close PRCHAIN-g1 and both need the admin (the `deletion` rule covers `~ALL`).
   - **(a) Delete the merged head.** GitHub retargets the children onto `main` for you, so there is one
     action per PR instead of two and no window in which the next PR points at a merged branch. Cost: the
     chain's branch names stop existing, so `git log --oneline m8.7/app-local-chrome` and every handover
     sentence naming a branch resolve only through the merge commits.
   - **(b) Retarget by hand.** `gh pr edit <n+1> --base main` after each merge — *alternative unit: add an
     explicit retarget-and-verify step between checklist steps 6 and 8, with `gh pr view <n+1> --json
     baseRefName` as its assertion.* The branches survive as history. Cost: two actions per PR and a real
     window where forgetting one merges the next PR into a dead branch.

3. **Does merge day carve an exception to "an agent never merges or retargets"?**
   `pr-cadence.md:7-8` is unambiguous today, and M8.17.2 is written to obey it.
   - **(a) No exception.** The owner presses every button; the agent verifies CI, checks bases, and records —
     *M8.17.2 as written*. Cost: the walk is as fast as the owner is, and fifteen-plus PRs is a long sitting.
   - **(b) A narrow, recorded exception** — *alternative unit: amend `pr-cadence.md:7-8` to permit an agent to
     **retarget** (never merge) during a recorded close-out walk, and add the amendment to M8.17.7's files.*
     Halves the owner's actions and keeps the irreversible one (merge) in human hands. Cost: it weakens a
     memory that exists because retargeting a stack wrongly is how a chain gets scrambled, and a rule with one
     exception is a rule that will grow more.

4. **Does close-out lift the required-status-check deferral?**
   Ruleset `19094308` has no `required_status_checks` rule, so GitHub would allow a merge with a red or
   absent `check` run. **The recorded position is that this is deferred deliberately** — merge-gating is
   admin-only by design — so (a) is the default and (b) needs an explicit owner decision.
   - **(a) Leave it deferred and say so.** *M8.17.1's checklist step 5 as written*: the merger eyeballs
     `check`, `conformance-matrix` and `e2e` per PR against the current head SHA, and the deferral is
     restated in `BOARD.md`'s close-out entry so the next milestone does not rediscover it. Cost: the guard is
     a human habit, and merge day is exactly when habits slip.
   - **(b) Add the rule as the last act of the milestone** — *alternative unit: add a
     `required_status_checks` rule naming `check`, `conformance-matrix` and `e2e` to ruleset 19094308 after
     the chain merges, and delete the deferral from the memory.* Cheapest moment to do it: the chain is in,
     so no open PR is retroactively blocked by a check it never ran. Cost: it changes repository policy from
     inside a close-out ticket, and `docs-build` — path-filtered and deliberately not required — must not be
     named or every non-docs PR blocks forever.

5. **What gets pruned?**
   `git worktree list` shows the two prunable scratchpad worktrees holding `m8.3` and `m8.4`, and a long tail
   of `.claude/worktrees/agent-*` worktrees from delegated sessions.
   - **(a) Prune only what blocks the chain.** *Checklist step 1 as written* — plain `git worktree prune`
     removes exactly the worktrees whose directories are gone (the two scratchpad ones) and leaves every
     `agent-*` entry alone. Cost: the agent worktree list keeps growing, and `.claude/worktrees/` is a
     known staging hazard (`known-landmines.md:104`).
   - **(b) Sweep the agent worktrees too** — *alternative unit: after the chain merges, remove the
     `.claude/worktrees/agent-*` worktrees and their branches, recording the count removed.* Leaves one clean
     clone behind a closed milestone. Cost: it is destructive on branches nothing else references, it is
     unrelated to M8's product, and it must not run while any delegated session is live.
