## Goal

The landing audit of 2026-09-02 ([`AUDIT-2026-09-02.md`](../AUDIT-2026-09-02.md)) found the feature landed and
the exit criteria holding on the tip, and found **twelve questions that need a decision before code** — three
of them the critic's "an owner ruling with no implementing unit" class the board has now warned about three
times, the rest open questions that were recorded, never asked, and survived close-out as open text. None is a
defect in the day-to-day loop. Every one is a place where two agents could land opposite behaviour with nothing
going red, because the behaviour was never decided.

This ticket holds **the decisions, written as alternative units**. For each question: what it is, the two
answers, what each costs, and one unit per answer with a Do / Files / Check a cold agent can execute. **The
owner strikes one unit of each pair before the other starts** — nothing in this ticket is startable until its
question is ruled, and the units are deliberately written so that neither is a recommendation. Where the
audit's refuters or the handover already offered a closer, it is folded into the unit that matches it and
cited.

Two conventions specific to this ticket. **Unit numbering pairs the alternatives:** `M8.15.(2k-1)` is answer
A of question *k*, `M8.15.2k` is answer B. Numbering is append-only, so a struck unit keeps its number and is
marked `~~struck — ruled <date>~~` in place. **The audit ids are claimed once, by the question — never by its
units.** Each question heading carries a `**Closes:**` line with the same ids as the at-a-glance table, and a
unit says only that it closes *the question's* ids if it is the answer kept. So a count over the ticket lists
every id exactly once: one claimer before the ruling, one closer after it, and the struck unit closes nothing.

### Question 1 — M8.9 OQ10: should a draft stay writable on an archived review?

**Closes:** D3-g4 · D7-g2 · D8B-g3 · D9-g6 — with whichever of M8.15.1 / M8.15.2 the owner keeps.

**Owner decides before either unit starts.** The four write verbs refuse on an archived review, the bar's
composer and verdict picker are withheld, and the guide and design both say "read-only" — but the inline gutter

### Question 2 — Owner ruling 4: what bounds a live review's pin set?

**Closes:** critic `missing` #1 (ruling 4 with no implementing unit — no gap id) — with whichever of
M8.15.3 / M8.15.4 the owner keeps.

**Owner decides before either unit starts.** Ruling 4 ("keep every pin — unbounded only until retention ships",
M8.8 OQ4) was conditioned on M8.10 arriving, and M8.10 arrived — but it bounds immutables and (dark) blobs and
never a live review's pins. The facts: `pinSnapshotObjects` (`local-pins.ts:143-181`) writes **two** refs per
compare (`refs/revu/reviews/<id>/<mergeBase>-<head>/{base,head}`) on every non-frozen sync
(`local-surface.ts:723-728`); the only drop is `dropPinnedRefs` (`retention.ts:196-230`) and its only caller is
the review's delete (`direct-api.ts:1031`); `pruneImmutables(store, gate)` (`retention.ts:409-425`) takes no
runner and cannot touch a ref. A weekly-rebased branch therefore grows two refs per sync forever, `git gc`
reclaims nothing under them, and the runbook's "what grows" paragraph (`operator-runbook.md:201-210`) names
blobs only. `§8` #23 (`LOCAL_REVIEWS.md:336-339`) scopes pin-dropping to deleted reviews. Nothing records the
live growth as accepted, and nothing tests it either way.

**A costs:** disk and ref-list noise that never comes back until the review is deleted; the documentation has
to say so honestly. **B costs:** a ref delete on the common path (ruling 5 put the prune there deliberately),
and a reference set that is easy to get wrong — the Landmines name the trap.

### M8.15.3 — Accept the growth, document it, and pin it as accepted *(answer A)*
**Do:** (1) **Runbook:** a paragraph after the blob one (`operator-runbook.md:201-210`): pins under

## Constraints that bind this ticket

- **Nothing starts before its ruling.** A unit whose sibling is not yet struck is not startable; a session that
  cannot reach the owner records that and stops. Do not pick a side to make progress.
- **The mock is the specification.** Every behaviour change lands in the mock first, then the daemon conforms;

  Audit ids live in this file and in commit messages.

## Landmines

- **Ticket line pointers rot.** Every `path:line` above was read on the 2026-09-02 tip; the units land on top
  of a chain of fifteen PRs that may rebase. Read the seam before editing — a wrong anchor sends the next agent
  to the wrong place with false confidence.
- **A guard comparing two quantities that move together asserts nothing.** The refusal sentence in 1-A must
  be matched against independent literals, not `toBe(refusal)`; the pin counts in 2-A/2-B are the literals
  `4` and `2`, never "previous ± 2"; the hint in 10-A is asserted as the component's literal, never as
  equality with the guide.
- **A fix landing in the same edit as its test has no observed red.** Where today's code already passes the
  new assertion (2-A, 5-A, 7-B, 12-A), obtain the red by control: restore or introduce the defect, watch the
  named test fail, revert, verify the revert byte-for-byte, and log both.
- **2-B's reference set is the whole ruling.** `store.listLiveCompareKeys()` is the **immutable** prune's set —
  snapshots only. A pin prune keyed on it alone strands exactly the older draft's objects ruling 4 refused to
  strand; the drafts' own `compareKey`s are the second half, and the draft case in the Check is the only
  thing that proves it.
- **The pin encoding is not invertible** (`local-pins.ts:104-108`): never parse a ref name back into a compare
  key; build the keepable names forward with `pinRefsFor` and compare full ref names.
- **The delete is the only pin drop today** (`direct-api.ts:1031`). 3-B closes it for archived reviews, which
  makes their pins permanent — decide questions 2 and 3 together.
- **`LocalArchiveApi` is a mapped type.** Adding a key (3-A/3-B) obliges every runner's `makeApi` to satisfy
  it; E/F return a full `RevuApi` and G a `DirectApi`, so it compiles — but the red it produces first is a
  `tsc` red, not a behavioural one; the behavioural red is obtained by control.
- **On E and F the first sync of a covered pair archives it** (`mock/conformance-local.test.ts:38-45`). A
  "delete then recreate the pair" case re-archives on the new review's first sync — assert the new id and the
  fresh archive, not a live review.
- **The mock resets `dirty` on every sync** (`local.ts:544`). A fixture-seeded `true` is cleared by the first
  re-sync, which is why 7-A's source of truth is a runtime toggle the sync consults, not a literal.
- **`-uno` means a tracked modification.** G's dirty hook (7-A) must modify a tracked file; an untracked
  scratch file is `clean` by M8.3 R-B.
- **The parity test reads git itself.** `local-parity.test.ts:316-339` runs its own `git diff --raw` /
  `--numstat` with `-M` only, so it is a **fourth** argv site for 12-B. A flag added to the three production
  reads and not to those two changes nothing the test can see, and the five-letter literal (`:399-401`) stays
  five while looking like a passing assertion.
- **`-C` does not detect a copy of an untouched file.** git reports `C` only when the source path is modified
  in the same range; otherwise the destination is plain `A`. A fixture that seeds a copy without touching its
  source (12-B) proves nothing, and `--find-copies-harder` is the flag that changes it — at the cost of a
  full-tree scan on every read.
- **`local-reviews-serve.test.ts:187-192` scrubs a fixed env list.** A new boot variable (8-A) that is not
  added there leaks a developer's shell into the spawned daemon and passes or fails for the wrong reason.
- **The direct list ETag hashes compare keys plus the archived state — not titles** (M8.9.5). 10-B must fold
  the title in or the inbox never learns the rename; the mock's ETag moves for free and would hide it.
- **`performLocalReviewDelete` maps only `unprocessable` to `refused`** (`state/local-reviews.ts:256`). A
