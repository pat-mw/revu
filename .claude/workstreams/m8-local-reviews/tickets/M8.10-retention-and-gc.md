## Goal

Give the direct-mode store its first eviction path: delete a local review completely (rows, snapshots,
pinned git refs) and prune the immutable halves and blob bytes that no live snapshot references any more.
This exists because of `LOCAL_REVIEWS.md §8` case 23 — the store has exactly one `DELETE` today
(`store.ts:464`, `deleteDraft`), the `immutables` and `blobs` tables are explicitly cache-forever with no
TTL, and a constantly rebased local branch mints a fresh `compareKey` on **every** sync and orphans the
previous immutable half forever. It also completes **D4** (`LOCAL_REVIEWS.md §3`): local state lives in its
own tables, so its deletion is scoped to those tables and must never reach into `snapshots`, `audit_log`, or
`pr_author`; and it discharges the retention half of `§5.1`'s object pinning — pinning objects under
`refs/revu/reviews/…` is only safe if something eventually drops those refs, so "retention becomes an
explicit delete rather than an accident of `git gc`". The danger this ticket is designed against is
**over-deletion**: removing an immutable half a live snapshot still points at does not degrade gracefully,
it turns `getSnapshot` into a 500 `persist_failed` (`store.ts:341-352` → `direct-router.ts:186-188`) and the
review becomes unopenable.

## Units

Default execution order. **M8.10.1, M8.10.2 and M8.10.3 are mutually independent** and can run in parallel:
the first is pure SQL on the local tables, the second is pure git via the injected `CommandRunner`, the
third is a read-only computation over existing tables. **M8.10.4 depends on M8.10.3**; **M8.10.5 depends on
M8.10.3 and M8.10.4** (it prunes over the *surviving* immutables, so the ordering is load-bearing);
**M8.10.7 depends on M8.10.4 and lands before M8.10.6**, because it is the guard every prune call site has
to be routed through, and a guard written after its callers encodes what they do rather than what they must
never do; **M8.10.6 depends on all six.** The shared edit across 1, 3, 4 and 5 is the append to the
`DirectStore` interface (`store.ts:172-249`) — expect a trivial conflict there and nowhere else.

Inside every unit the assertion is written and observed **red** before the code that greens it, and each
unit's **Do** names which assertion goes first and what its red must look like. A red that only says
"`deleteLocalReview` is not a function" proves the test file loaded; it does not prove the assertion can
catch the bug it exists for. Three units here can do materially better than that and are required to:
M8.10.1 greens a `local_reviews`-only delete first and watches the five other per-table counts stay
non-zero; M8.10.4 greens a prune whose live set reads `local_snapshots` only and watches the over-deletion
sweep fail on a PR snapshot; M8.10.7 runs its interleave against an unguarded prune and watches the
in-flight blobs disappear. Each is one of this ticket's real failure modes, reproduced once, on purpose.

**Why M8.5 is a dependency.** M8.10.6 puts `deleteLocalReview` on the api surface (`direct-api.ts`) — the
surface M8.5.1 builds and the local dispatch M8.5.1 defines — and it **takes over serving**
`DELETE /api/local-reviews/:n`, which M8.5.2 deliberately leaves on the honest known-route 501 because the
store method behind it is M8.10.1's. Without the dependency the two tickets were unordered and each assumed
the other had the route: M8.5.2 would have had to invent a bare row delete colliding with M8.10.1's
transactional counts contract, or leave the route failing its own check. M8.5.2's route table now pins the
501 explicitly, and this ticket rewrites that case rather than adding one.

### M8.10.1 — `deleteLocalReview`: the store's second `DELETE`
**Do:** Add `deleteLocalReview(localId: number): { … counts }` to `DirectStore`, removing the review's rows
from all six `local_*` tables in **one** `db.transaction` inside the existing `write()` wrapper
(`store.ts:291-297`) so a partial delete is impossible and a failed persist is a `StoreWriteError`, never a
silent success. Model it statement-for-statement on `purgeWorkingState` (`collector/host-store.ts:467-484`)
— the only other transactional delete in the repo — including returning per-table `.changes` counts, which
are what makes the unit's assertions evidence rather than hope. It deletes `local_drafts` / `local_viewed`
rows for **every** human, not just the session's, because the row key is the review (see Landmines and Open
questions). It touches no PR-keyed table, no `immutables` row, and no `blobs` row: those are M8.10.4 and
M8.10.5, under a reference rule, not a cascade.
**Test first:** write the per-table `SELECT COUNT(*)` assertions and the second-review-untouched assertion
before the delete exists, then green only the `local_reviews` row removal — the five remaining counts stay
non-zero, which is the partial-delete / id-reuse hazard from Landmines reproduced rather than an
absent-symbol red. Complete the transaction and watch them go green.
**Negative control, and it is not optional.** The containment leg asserts an absence (not one trigger
fires), so prove it can fail: point one of the six deletes at `snapshots` instead of its `local_*` table,
run `-t 'local writes never touch'`, observe it red naming the trigger, revert. M8.2.7's three armed
assertions are the permanent control that the tripwires still fire on every future gate; this one-time
observation is what proves *this* delete sits inside their reach. Record the red and the restored green in
the **Log**.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** `bun test packages/revud/src/direct/store.test.ts` with cases asserting: after a delete,
`getLocalReview` / `getLocalSnapshot` / `getLocalDraft` / `getLocalViewed` / `listLocalThreads` /
`listLocalSubmittedReviews` all read back empty-or-null for that id, and a raw
`SELECT COUNT(*) FROM local_drafts WHERE local_id = ?` (repeated per local table) is `0`; a second, unrelated
local review's rows are untouched; the returned counts equal the rows that existed; deleting an id that was
never created is a no-op returning all-zero counts (idempotent, never a throw); and the delete extends
M8.2.6's trigger-guarded containment test — with `RAISE(ABORT)` triggers installed on
`snapshots`/`audit_log`/`pr_author`, the whole delete runs without firing one.

### M8.10.2 — Drop a deleted review's pinned refs
**Do:** Add a local-only retention module `packages/revud/src/direct/retention.ts` exporting
`dropPinnedRefs({ runner, cwd }, localId)`. **This unit is the milestone's only ref-deletion path** — M8.8.1
writes and lists pins and deliberately exports no delete, so there is exactly one implementation and it is
this one. **Discover** the refs — `git for-each-ref --format='%(refname)'
refs/revu/reviews/<id>/` — and delete each with `git update-ref -d <refname>`; do **not** reconstruct the
ref name from `<id>/<compareKey>`, because the compareKey contains `...` and a name with two consecutive
dots is rejected by git outright (see Landmines: verified). The prefix is safe under any encoding M8.8 picks:
M8.8.1's `pinRefsFor` keeps `<localId>` and `<pinKey>` in **directory** position (a ref *at*
`refs/revu/reviews/<id>` would make every child unwritable), so `refs/revu/reviews/<id>/` always names a
directory and never a ref. Every argument goes through the argv-array
`CommandRunner` (`command-runner.ts:31-33`) — no shell — and the id is stringified from a validated integer
so nothing user-supplied reaches an argv slot. Report a count and the refnames dropped. The function must be
correct **before M8.8 lands**: an empty namespace makes `for-each-ref` exit 0 with no output and
`update-ref -d` on an absent ref also exits 0, so "no refs pinned yet" is a clean zero, not an error. Do not
run `git gc` — reclaiming the objects is the user's or git's own call, and this module never mutates the
user's working tree.
**Test first:** leg (a)'s exact-argv assertion is written and observed red before `dropPinnedRefs` exists;
leg (b) is written against the empty new file and its own self-check goes red on "source read back empty",
which is the scanner proving itself before it guards anything.
**Fixture hygiene for the real-repo legs:** setup commands run with `GIT_CONFIG_GLOBAL` and
`GIT_CONFIG_SYSTEM` pointed at a nonexistent path and with `-c user.email=… -c user.name=…
-c commit.gpgsign=false`, under an explicit `git init -b`, so a developer's global signing key, hook path
or default branch name cannot decide whether the gate is green (see Landmines). Every command carries the
temp dir as `cwd`; nothing runs against the revu clone.
**Files:** `packages/revud/src/direct/retention.ts`, `packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts`, four durable legs.
(a) **Fake `CommandRunner`** — with discovery returning two refnames, the fake records exactly
`['git','for-each-ref','--format=%(refname)','refs/revu/reviews/1000000001/']` followed by one
`['git','update-ref','-d',<refname>]` per ref, in that order, each carrying `cwd`; with discovery returning
empty stdout the recorded list has **length 1** — nothing beyond discovery is spawned. The two-ref case is
the standing control for the empty one: it is what proves the recorder can count past one, so "nothing was
spawned" is a fact rather than a broken sink.
(b) **Structural, and it is the durable form of the D7 and no-`VACUUM` clauses in Constraints** (otherwise
prose). Read `retention.ts`'s own source, extract only the `import … from '<spec>'` specifiers, and assert
**every** one is drawn from `['./store', './command-runner']`, type-only imports included — a subset rule,
not an exact set, because the module gains its `./store` import only when M8.10.4 lands and an exact-set
assertion would be red for the two units in between for no reason. Nothing resolves to `./github-client`
and nothing has a basename containing `github`. Assert the module body contains no `Bun.spawn`, no `fetch(`, no
`https://`, and no tracking id (`/\bM\d+(\.\d+)+\b/`, the AGENTS.md ban made executable). Assert neither
`retention.ts` nor `store.ts` contains a `VACUUM` inside a quoted SQL string — matching the *statement*
form, not the bare word, so a docstring explaining why `VACUUM` is banned does not trip its own scan, the

go quietly vacuous: every scanned source read back non-empty, and the specifier extractor, run over an
inline fixture that imports `./github-client`, reports that specifier.
(c) **Real temp repo** — `mkdtempSync` + `git init`, two empty commits, refs created under
`refs/revu/reviews/1000000001/` and `refs/revu/reviews/1000000002/`, then the drop through a real
`createBunCommandRunner()`: afterwards `git for-each-ref refs/revu/reviews/1000000001/` prints nothing and
the ref under the other local id survives. Run the drop twice; the second call is a zero-count no-op that
spawns only the discovery command.
(d) **The retention story end to end**, which is what makes this ticket's pinning claim falsifiable. In the
same repo, reset the branch so the second commit is unreachable, run `git reflog expire --expire=now --all`
then `git gc --prune=now`, and assert `git cat-file -e <doomed sha>` still exits **0** — the pin kept the
object. Drop the refs, expire and gc again, and assert `git cat-file -e <doomed sha>` now exits non-zero.
That is "retention becomes an explicit delete rather than an accident of `git gc`" as an assertion instead
of a sentence, and it replaces the manual clone smoke this ticket used to lean on. The whole sequence was
run against git 2.50 before this was written: a pinned ref survives `--prune=now`, `for-each-ref` over an
empty namespace exits 0 with no output, and `update-ref -d` on an absent ref exits 0.

### M8.10.3 — The live `compareKey` set, computed fail-closed
**Do:** Add a store read that returns every `compareKey` referenced by a live snapshot — both
`snapshots` (PR) and `local_snapshots` — and a matching `listImmutableKeys()`. The key is **not a column**:
it lives inside the stored envelope JSON (`StoredSnapshotEnvelope.compareKey`, `store.ts:144`), so the read
either uses SQLite's `json_extract(data, '$.compareKey')` (verified available under `bun:sqlite`) or parses
each row through `parseRow` (`store.ts:252-258`). Whichever is chosen, the rule is **fail closed**: a row
whose JSON will not parse, or whose extracted key is null/empty, throws `StoreUnreadableError` and aborts
the caller — it is never silently skipped, because a skipped row reads as "references nothing" and every
immutable it pointed at becomes prune bait. Under `json_extract` the two corruption shapes differ and both
have to be handled: a malformed document raises a driver error that aborts the whole query, so the read
wraps and maps it, or an unmapped `SQLiteError` reaches `direct-router.ts:186-188` as a generic 500 instead
of `persist_failed`; a valid document missing the key yields `null` and one holding `""` yields the empty
string (see Landmines, verified). This unit adds no delete.
**Test first:** the malformed-row case goes first, asserting the **class** `StoreUnreadableError`, and is
observed red on the raw driver error before the mapping exists — that red is the bug, not a missing symbol.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** `bun test packages/revud/src/direct/store.test.ts`: a store holding one PR snapshot and one local
snapshot on distinct compares returns exactly those two keys; two snapshots sharing one compareKey return it
once; `listImmutableKeys()` returns every `immutables` row's key **including the orphans no snapshot names**
(without that, M8.10.4 prunes against a set nothing asserts). Corrupting a `snapshots.data` row with
`UPDATE snapshots SET data = 'not json'` makes the read throw `StoreUnreadableError` — assert the error
class, not merely that it throws, since the honest failure and the leaked-driver-error failure both throw
and only one answers `persist_failed` (mirroring `store.test.ts:236-249`); same case for `local_snapshots`.
An envelope that is valid JSON but whose `compareKey` is absent, and one where it is `""`, each throw rather
than returning a short set.

### M8.10.4 — Prune unreferenced immutable halves
**Do:** Add `deleteImmutables(keys: string[])` to the store and `pruneImmutables(store)` to
`retention.ts`. The rule is **reference-based, never age-based**: an immutable row is deletable iff its
`compare_key` appears in `listImmutableKeys()` and not in the live set from M8.10.3. Compute the set and
issue the deletes inside **one** `db.transaction`, so a snapshot written between the read and the delete
cannot be stranded. Return the count and the keys removed. Nothing here reads a timestamp, and no
`last_synced_at`, `updated_at` or row age may enter the predicate — "no TTL on the immutable store" is a
hard constraint, and reference-counting is what lets this ticket bound growth without breaking it.
**Test first:** the over-deletion sweep is written before `pruneImmutables` and greened first against a live
set that reads `local_snapshots` **only** — the sweep goes red on the seeded PR snapshot with exactly the
`StoreUnreadableError` from `store.ts:341-352`, this ticket's catastrophic bug reproduced on purpose. Widen
the live set to both tables and watch it go green. Extract the sweep as a helper
(`expectEverySnapshotStillReadable(store)`) in the first prune test that needs it and call it at the end of
**every** prune-shaped test in the file, so the invariant is a property of the suite rather than of one case.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/retention.ts`,
`packages/revud/src/direct/store.test.ts`, `packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts`: seed a store with a PR snapshot on
`A...B`, a local snapshot on `C...D`, and two orphans (`A...old`, `C...old`) written via `putImmutable`;
after the prune, `SELECT COUNT(*) FROM immutables` is 2 and the two live keys are the survivors. The
load-bearing assertion is the sweep: **for every `pr_number` in `snapshots` and every `local_id` in
`local_snapshots`, `getSnapshot`/`getLocalSnapshot` still returns a snapshot and throws nothing** — that is
the direct test for the over-deletion failure at `store.ts:341-352`. Plus: a prune over a store with a
corrupt snapshot row deletes **nothing** (assert `SELECT COUNT(*) FROM immutables` unchanged, not just that
it threw) and propagates `StoreUnreadableError`; a prune on an already-pruned store removes 0 rows. Plus the
hard constraint made executable: an immutable that is **live but stale** — its snapshot's `syncedAt` and its
review's `last_synced_at` both years in the past — survives, while an orphan written moments ago is removed.
Reference, never age: that pair goes red the moment a `created_at` / `last_synced_at` / row-age predicate
enters, and it is the only durable way to hold "no TTL on the immutable store" against a future editor.

### M8.10.5 — Blob retention under the same reference rule
**Do:** Add `listBlobShas()` + `deleteBlobs(shas: string[])` to the store and `pruneBlobs(store)` to
`retention.ts`, running **after** `pruneImmutables` and walking only the surviving immutables' `blobIndex`
(both sides per path — the same walk `collectShas` does at `blobs.ts:188-197`, and the same one the mock's
seed already performs at `packages/app/src/api/mock/store.ts:134-142`). A SHA referenced by no surviving
immutable is deletable; everything else stays. Blobs are content-addressed and **shared between PR and local
snapshots**, so this is strictly riskier than pruning immutables: one over-deletion breaks a review that has
nothing to do with the one being cleaned up. Encode the recovery asymmetry in the docstring — a PR's blob is
re-fetchable from GitHub on the next sync, a local review's blob may be the **only** copy once the branch is
rewritten and its pinned refs are gone. Ship the blob prune behind an explicit caller-supplied policy flag
rather than folding it into `pruneImmutables`, so the immutable prune (the one that actually bounds growth)
can land and run without carrying the blob risk (see Open questions).
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/retention.ts`,
`packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts`: a blob referenced only by an orphaned
immutable is removed; a blob referenced by a **live PR** snapshot survives a local-review delete + full
prune; a blob shared by a live PR snapshot and an orphaned local immutable survives; after any prune,
`store.getBlob(sha)` is non-null for every sha in every surviving immutable's `blobIndex` (the mirror of
M8.10.4's sweep, and the exact precondition `direct-api.ts:257-269` and `reconcile.ts:78-82` depend on).
Assert removal by `SELECT COUNT(*) FROM blobs`, never by file size. Plus the policy flag itself, as one
assertion pair that is its own control: a full prune called **without** the blob policy leaves the blob
count unchanged even with an orphan-only blob present, and the same prune **with** it removes exactly that
blob — so "the blob prune is off by default" cannot quietly decay into "the blob prune never worked", and
whichever way Open question 1 is answered the answer lives in a test rather than in prose.

### M8.10.7 — The in-flight-sync gate (lands before M8.10.6 wires a caller)
**Do:** Own the Landmine no other unit owns, because it is the one that costs bytes that cannot be refetched.
`syncPull` writes the immutable half at `sync.ts:450` and the blobs at `blobs.ts:299`, but the envelope only
at `sync.ts:506`, with network `await`s in between — so a prune running in that window sees a fresh
immutable and its fresh blobs as unreferenced. The immutable damage self-heals when `putSnapshot` rewrites
the row (`store.ts:403`); the blob damage does not, and the sync completes with bytes missing. Add the
smallest honest fix to `retention.ts`: a process-local in-flight counter plus a
`withSyncInFlight(gate, fn)` wrapper, entered around the whole `runSyncPull` call in `direct-api.ts:235-247`
(and around the local sync M8.5 adds) with the exit in a `finally`, so a rejected sync cannot leave the
counter pinned. While the counter is non-zero, `pruneImmutables` and `pruneBlobs` are a **reported no-op** —
a returned "skipped, N syncs in flight", never a throw and never a partial prune. The wrapper, not the call
site, holds the try/finally, so there is one tested path rather than one per caller. Scope honestly in the
docstring: this protects one daemon's concurrent requests, not two daemons on one data dir (see Testing
exceptions). No change to `sync.ts` — the gate sits at the api seam, which keeps this ticket's diff to the
files `Verify` already lists.
**Test first:** the interleave test is written and observed red against an unguarded prune, which deletes
the in-flight blobs — the exact loss the gate exists to prevent, not an absent-symbol red.
**Files:** `packages/revud/src/direct/retention.ts`, `packages/revud/src/direct/direct-api.ts`,
`packages/revud/src/direct/retention.test.ts`
**Check:** `bun test packages/revud/src/direct/retention.test.ts`, deterministic — no timers, no sleeps, no
racing. (1) **The real interleave**: build a `createDirectApi` over a `:memory:` store with a fake
`GithubClient` whose compare call returns a promise the test resolves by hand (the shape
`conformance-reads.test.ts:21-28` already builds), start `syncPull` without awaiting it, run the full prune
while it is pending, and assert `SELECT COUNT(*) FROM immutables` and `FROM blobs` are both unchanged and
the result reports the skip; resolve, await the sync, run the same prune and assert the genuinely-orphaned
rows are now removed. (2) **A rejected sync releases the gate**: a client that rejects leaves the counter at
zero and the next prune is *not* skipped — a leaked counter is a prune that silently never runs again, which
from the outside looks exactly like a working prune, so this is the assertion that tells the two apart.
(3) **Nesting**: two overlapping entries skip until *both* exit.
**Negative control, recorded:** remove the gate check from `pruneImmutables`, re-run (1), observe the
in-flight blobs deleted and the assertion red, revert. Put both observations in the **Log**.

## Constraints that bind this ticket

- **No TTL on the immutable store** (`memories/hard-constraints.md`; restated in the store's own docstring
  at `store.ts:27-34`). Eviction here is **reference-based only**. A `WHERE created_at < …` or
  `last_synced_at`-driven sweep would be a TTL by another name and is a defect even if every test passes.
  Nothing in the schema even records when an immutable row was written, which is the constraint made
  physical.
- **Drafts survive everything — a draft is deleted only on confirmed submit success**
  (`memories/hard-constraints.md`). The prune must therefore never delete a draft, and the review delete
  must be an explicit user act with a clear consequence, never a background sweep. This is the sharpest
  tension in the ticket: deleting a review deletes its drafts.
- **D4 — the local path never touches PR-keyed tables** (`LOCAL_REVIEWS.md §3`). `snapshots`, `audit_log`
  and `pr_author` are read by the host collector, the broker poll loop and the out-of-band-write detector
  as facts about the client repo. Deleting from them is worse than writing to them: `audit_log` has no
  delete counterpart *by design* (`store.ts:206-212`, `store.test.ts:405-414`) and must not grow one.
- **D1 — archiving is read-only, never destructive** (`LOCAL_REVIEWS.md §3`, `§8` case 22). A review that a
  PR superseded keeps its threads, drafts and history. Nothing in this ticket may auto-delete an archived
  review; `archived_pr` being set is not a retention signal.
- **D7 — no GitHub client in scope** (`LOCAL_REVIEWS.md §3`). The retention module's only dependencies are
  the store and the `CommandRunner`. Structural absence, not a conditional — and asserted as one by
  M8.10.2's specifier scan, so it stops being a promise the reviewer has to check by eye.
- **Absent ≠ unreadable** (`store.ts:56-61`). For reads this means a missing row is `null`; for the prune it
  means **fail closed** — an unparseable snapshot envelope aborts the whole operation, because the
  alternative (skip it) silently reclassifies everything it referenced as garbage.
- **No swallowed write failures** (`store.ts:85-100`, `:291-297`). Every delete goes through `write()` and
  surfaces `StoreWriteError`.
- **Migration doctrine: no table rebuilt** (`store.ts:616-630`). This ticket adds no schema and must not
  `VACUUM` — a `VACUUM` rewrites the entire database file, cannot run inside a transaction, and takes an
  exclusive lock on the file that holds every draft. There is no `VACUUM` anywhere in `packages/revud/src`
  today; M8.10.2's scan is what keeps it that way after this ticket makes deletion routine.
- **Two-half caching stays intact** (`memories/hard-constraints.md`). The prune may remove an immutable half
  only when no snapshot names its key; it may never remove one to "force a refresh", and it may never
  short-circuit the mutable fetch.
- **The frozen contract is read-only here.** `deleteLocalReview` as an API method and route belongs to M8.1
  and M8.5; this ticket owns the store semantics behind it. If the wire shape looks wrong, report it rather
  than editing `packages/shared/src/api/*`.
- **Ref-name hardening** (`LOCAL_REVIEWS.md §8` case 7). Even though this ticket only handles ids it minted
  itself, the ref path is still built and passed to git: argv array, no interpolation into a single string,
  ids validated as integers.
- **AGENTS.md code style**: self-contained comments — no ticket ids, no milestone numbers, no "phase" in any
  line of code, SQL, or docstring. `import type` for types; no unused bindings; no stubs or TODOs.

## Landmines

- **The pinning path from `§5.1` is not a legal git ref name.** `compareKey` is
  `<mergeBase>...<head>`, and git rejects any ref whose name contains two consecutive dots. Verified
  directly: `git check-ref-format refs/revu/reviews/1000000001/<sha>...<sha>` exits 1, and `git update-ref`
  answers `fatal: … refusing to update ref with bad name`. So M8.8 must encode the key (a single separator,
  or a hash) and **this ticket must not reconstruct ref names from the compareKey** — discover them with
  `for-each-ref` under the `refs/revu/reviews/<id>/` prefix. Miss it and the drop silently deletes nothing
  while reporting success, and every object stays pinned forever.
- **The in-flight-sync window.** `syncPull` writes the immutable half at `sync.ts:450` and the blobs at
  `blobs.ts:299`, but the snapshot envelope only at `sync.ts:506`, with network `await`s in between. A
  prune triggered by another request during that window sees the fresh immutable and its fresh blobs as
  unreferenced. The immutable damage self-heals (`putSnapshot` rewrites the row at `store.ts:403`); the
  **blob** damage does not — `putBlobs` already ran, so the sync completes with bytes missing and the file
  viewer 404s until a re-sync. Guard the prune against a concurrent sync (an in-flight counter is the
  honest fix) or accept and document the recovery.
- **Over-deleting an immutable is not a cache miss.** `getSnapshot` throws (`store.ts:341-352`) → the router
  answers 500 `persist_failed` (`direct-router.ts:186-188`). The review becomes unopenable, and because the
  immutable half is *derived* data the instinct is to assume a re-sync fixes it — for a local review whose
  branch was rewritten, it does not.
- **A corrupt snapshot row read as "references nothing" is the catastrophic bug**, and the two corruption
  shapes do NOT behave alike. Verified directly under `bun:sqlite` (SQLite 3.51): `json_extract` over a
  **malformed** document raises `SQLiteError: malformed JSON` and aborts the entire `.all()` — so the read
  must catch and map it to `StoreUnreadableError`, or an unmapped driver error reaches
  `direct-router.ts:186-188` as a generic 500 instead of `persist_failed`. Over a **valid** document that
  lacks the key it returns `null`, and over `compareKey: ""` it returns `''`. Null and empty are both fatal.
  One unreadable row must abort the prune, never shrink the live set.
- **This is the repo's first test that spawns a real `git`.** Nothing under `packages/**` runs a git command
  today — every existing test injects a fake `CommandRunner` (`repo.test.ts:12-19` is the pattern) — so the
  temp-repo legs inherit no harness and must isolate themselves: `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`
  pointed at a nonexistent path, identity and `commit.gpgsign=false` passed with `-c`, an explicit
  `git init -b`, and the temp dir as `cwd` on every command. Otherwise a developer's global signing key,
  hook path or default branch name decides whether the gate is green.
- **`MAX(id)+1` re-mints a deleted review's id** (M8.2's open question 3). If any row survives the delete —
  another human's `local_viewed`, a stray `local_threads` row, a pinned ref — the next review created for a
  different branch pair silently adopts it. Either the delete provably removes every dependent row across
  every human, or M8.2 must switch to a monotonic high-water mark. Decide before writing the delete, not
  after.
- **`local_drafts` / `local_viewed` are keyed `(human_id, local_id)`**, so a delete by review id deletes
  **every** human's draft on that review and scans the table to do it (the PK indexes `human_id` first).
  One workspace has one human today, so this is latent — but it is a real cross-human deletion path and the
  docstring must say so plainly rather than letting a reader assume session scoping.
- **The database file does not shrink.** SQLite marks pages free and reuses them; `ls -l` after a delete is
  unchanged. Assert `SELECT COUNT(*)` (or `PRAGMA freelist_count`), never file size, or the test will look
  broken while the code is correct — and do not "fix" it with `VACUUM`.
- **Dropping refs does not free disk either.** The objects survive until the user's own `git gc` runs.
  Saying "deleted" in a UI toast that means "unpinned" is a lie the runbook must pre-empt.
- **Blobs are the shared surface.** One SHA can back a PR snapshot and a local snapshot at once
  (`blobs.ts:188-197` collapses paths to SHAs precisely because they are shared). A blob prune bug shows up
  in a review nobody touched. Prune blobs last, over surviving immutables only, and keep the immutable prune
  independently shippable.
- **Do not add a delete-shaped audit method.** `store.test.ts:405-414` filters store keys for `audit` and
  pins the surface to `['appendAudit','listAudit']`. Beyond the test, it is the D4 promise: journaled writes
  to the client repo are permanent.
- **`archived_pr` is not a tombstone.** D1 makes a superseded review read-only and *preserved*. Wiring
  archive → delete would destroy exactly the training history the milestone exists to keep.
- **Deleting the review while a draft has unsubmitted text** is the one place this ticket can violate
  "drafts survive everything" (`memories/hard-constraints.md`). Whatever the answer, it must be deliberate —
  see Open questions.

## Testing exceptions

Two things here cannot carry a behavioral assertion. Both are named so a later reader does not mistake the
gap for coverage.

1. **The `docs/operator-runbook.md` retention subsection and the `store.ts` docstring inventory
   (M8.10.6).** Prose is not executable and nothing in this repo reads the runbook mechanically. The
   compensating assertions are the ones the prose describes, and each of its falsifiable claims has one:
   "a delete never removes an `audit_log`, `pr_author` or PR-keyed row" is held by M8.10.1's trigger leg and
   by `audit-integrity.test.ts`'s source scan over `store.ts`; "revu never runs `git gc`" is held by
   M8.10.2 leg (a)'s exact-argv assertions plus leg (b)'s specifier scan; "nothing here reclaims disk by
   rewriting the database" is held by leg (b)'s `VACUUM` ban. The remaining sentence — that the SQLite file
   does not shrink on delete — is deliberately left as prose: the only direct assertion for it is on file
   size or page counts, which Landmines bans as flake-prone, and the constraint it protects (do not reach
   for `VACUUM`) is already pinned structurally.
2. **Two daemons sharing one `REVU_DATA_DIR` (M8.10.7).** The in-flight gate is process-local, so a second
   daemon's sync is invisible to it and no in-process test can assert otherwise. The compensating measures
   are the scope stated plainly in the gate's docstring, the fact that the immutable half of that window
   self-heals on the next `putSnapshot`, and keeping the blob prune — the half that does not self-heal —
   default off (Open question 1). This residual is the strongest argument for that default and should be
   read together with it.

## Open questions

1. ~~**Is the blob prune on by default?**~~ **Answered by the owner, 2026-08-19: off by default, behind an
   explicit caller-supplied policy flag.** Ship the walk and the prune; do not run it unless asked. The
   immutable prune (M8.10.4) runs live and is what bounds the churn this ticket exists for.
   **The cost was stated and accepted, so record it rather than re-deriving it later:** `blobs` then grows
   monotonically and is the largest table — every re-sync of a rebased branch mints a fresh compareKey and
   stores its file contents again, and nothing shrinks it. That growth is visible in the data directory's
   size and recoverable by turning the flag on; a wrong delete is neither. The decisive asymmetry is
   recovery, not size: a PR's blob is re-fetchable from GitHub on the next sync, while a local review's blob
   can be the **only** copy in existence once its branch is rewritten and its pinned refs are dropped.
   M8.10.5's Check already pins **both** behaviours as one assertion pair that is its own control — a full
   prune without the policy leaves an orphan-only blob in place, the same prune with it removes exactly that
   blob — so "off by default" cannot decay into "the blob prune never worked". That pair is now load-bearing
   and must not be reduced to the off case.
2. ~~**When does the prune run?**~~ **Answered by the owner, 2026-08-20: after every successful local
   sync.** That is the growth bound, and it is deliberately the tightest of the four candidates: it prunes
   exactly where the churn is *created*, since every re-sync of a rebased branch mints a fresh compareKey.
   The standing objection to this candidate — that it sits closest to the in-flight-sync window — is spent,
   because M8.10.7's gate closes that window at every call site; the choice was therefore made on growth
   bound and blast radius alone, as that unit's text anticipated.
   **Record the accepted cost rather than re-deriving it later:** a prune bug now touches the common path
   rather than a teardown path, so M8.10.6's Check must drive the prune **at its own trigger point** — a
   real local sync, not a direct call to the prune function — or the wiring is untested and the trigger is
   the only thing this ruling actually decided. The three rejected candidates and why: `deleteLocalReview`
   only bounds nothing (a long-lived weekly-rebased branch accumulates immutables forever and is reclaimed
   only if someone deletes the review); **at boot** turns one corrupt row into a failed daemon startup under
   a fail-closed prune (`index.ts:170-171`), making a retention bug an inability to launch; **manual
   operator command** leaves ruling 4's unbounded pin set without a working collector, since for a
   single-user local daemon "whenever an operator remembers" is effectively never.
3. ~~**What happens when the review being deleted has a non-empty draft?**~~ **Answered by the owner,
   2026-08-19: the server refuses while a draft exists.** `deleteLocalReview` is server-authoritative — it
   refuses the delete outright when any human holds a non-empty draft on that review, and the client must
   discard the draft explicitly and then delete. Deleting a draft becomes its own deliberate act, which is
   what keeps "drafts survive everything" true for a user-initiated delete as well as for submit flows.
   **This needs no contract change and none may be made.** The frozen route
   `DELETE /api/local-reviews/:n` has no body and no query parameter, so a `force` flag has nowhere to live;
   adding one is a §5.2 stop condition and was explicitly declined. The refusal therefore rides the existing
   typed-error path, not a new parameter.
   **Two things this ruling binds elsewhere.** M8.10.1's delete stays a pure transactional row removal — the
   refusal is a precondition checked *before* it, never a partial delete — and it must still delete
   `local_drafts` rows for **every** human once the precondition passes, since the row key is the review.
   M8.12 renders the two-step flow (discard, then delete) against this refusal rather than guessing at it;
   see that ticket's Open question 1, answered in the same ruling.
4. ~~**Id reuse vs a high-water mark**~~ **Resolved from the repo, 2026-08-20 — no owner input needed.**
   M8.2 shipped the **high-water mark**, not `MAX(id) + 1`: `store.ts:1621` defines
   `LOCAL_REVIEW_ID_META_KEY = 'local_review_id_high_water'` and the surrounding doc
   (`store.ts:1605-1619`) states the distinction explicitly — "A HIGH-WATER MARK, not a row count and not
   `MAX(id) + 1`. The difference only shows up after a delete: `MAX(id) + 1` re-issues the id of the review
   that was removed." **So the whole id-reuse class disappears**, exactly as this question's second branch
   predicted, and the "should not be started until that is settled" hold on this ticket is lifted. This
   ticket therefore does **not** owe a proof of exhaustive deletion-for-id-safety; exhaustive deletion is
   still owed for its own sake (leaked refs and orphaned rows are their own defect), but a recycled id
   adopting stale rows is now unreachable rather than merely unlikely.
5. ~~**The ref encoding, and M8.8 ordering.**~~ **Answered by M8.8.1**, which requires `<localId>` and
   `<pinKey>` to be **directories, never refs** — a ref at `refs/revu/reviews/<id>` makes every child
   unwritable, verified — so a flat scheme is not available to M8.8 and `refs/revu/reviews/<id>/` always
   names a directory. Prefix discovery is therefore correct under every encoding M8.8 may pick and correct

signature takes keys, but the unit also requires the live-set read and the deletes to share one
