## Goal

Grow the direct-mode SQLite store a parallel, repo-scoped keyspace for local reviews — six `local_*`
tables plus the store methods that read and write them — as a purely additive v3 → v4 step in the
existing migration ladder. This exists because of **D4** (`LOCAL_REVIEWS.md §3`): the reserved id band
is a *contract-level* convenience only, and no synthetic id may ever be written to `snapshots.pr_number`,
`audit_log.pr`, or `pr_author.pr`, because the host-side collector and the broker poll loop read those
columns as real GitHub PR numbers. It also carries the repo-scoping decision from `LOCAL_REVIEWS.md §4.2`:
the store is repo-blind today, and while two repos sharing a `REVU_DATA_DIR` only collide on PR numbers
when the same number exists in both, `main` and `feature/x` collide across *every* repo — so `repo` is
part of the local key from day one. Stable-across-restart local ids (`LOCAL_REVIEWS.md §3.1`) are a store
property, delivered here via the unique key plus a **monotonic high-water mark in `meta`** — see **R-A** and
**R-B** in `## Rulings`, which override `§3.1`'s `MAX(id)+1` and widen the unique key with a `generation`
discriminator. Where a ruling and this ticket's prose disagree, the ruling wins. This ticket adds
**no** `RevuApi` method and touches **no** route — the contract surface is M8.1's, the dispatch is M8.5's.

**This ticket owns the `repo` identity rule**, because it is the ticket that bakes the value into a `UNIQUE`
constraint and it lands before every consumer. The rule, recorded once here and referenced (never re-decided)
by M8.3, M8.5 and M8.9:

> `repo` is `owner/name` whenever `git remote get-url origin` resolves to a parseable GitHub-shaped remote —
> i.e. whenever `resolveRepo` (`repo.ts`) succeeds — and otherwise the absolute path
> `git rev-parse --show-toplevel` prints. It is never the empty string, and it is never a hash (M8.9's
> detection compares it against a GitHub `owner/name`, and a hash could never match).

The store is **told** the value; M8.3.1 exposes the function that computes it and M8.5.5 resolves it once at
boot. Two consequences are deliberate and must be stated wherever they surface: a workspace that gains an
`origin` after its first local review keeps the old path-shaped identity (the row is keyed on it), and archive
detection (M8.9) is therefore live exactly in the workspaces that had an origin at creation time.

## Units

Unit numbers are identity, not execution order. **M8.2.7 lands first**: it is the D4 guard rail, it needs
no local table and no store change, and a guard rail belongs in an earlier wave than the code it constrains
— written afterwards it would encode what the local writes do rather than what they must never do.
**M8.2.1 lands second** — nothing after it has tables to talk to, and it shares `store.test.ts` with M8.2.7
so the two serialize. After it, **M8.2.2, M8.2.3, M8.2.4 and M8.2.5 are mutually independent** and can run
in parallel: each adds a disjoint set of methods and its own `describe` block. Their one shared edit is the
append to the `DirectStore` interface (`store.ts:172`), so expect a trivial merge conflict there and nowhere
else. **M8.2.6 depends on all five** and on M8.2.7's harness.

Inside every unit the assertion is written and observed **red** before the code that greens it; each unit's
**Do** names the assertion that goes first and what its red looks like, because a red that only says
"function is not defined" proves less than one that reproduces the bug the assertion exists to catch.

### M8.2.1 — v4 schema: six tables, one guarded ladder step
**Do:** Bump `STORE_VERSION` 3 → 4. Add six `CREATE TABLE IF NOT EXISTS` statement constants beside
`CREATE_AUDIT_LOG` (`store.ts:599`) and `CREATE_PR_AUTHOR` (`store.ts:612`), one per table in the
`LOCAL_REVIEWS.md §4.2` DDL — `local_reviews`, `local_snapshots`, `local_threads`,
`local_reviews_submitted`, `local_drafts`, `local_viewed`. Run each in the fresh-file shape section of
`migrate` (after `store.ts:663`) **and** again inside a new `if (current < 4) { … }` guarded step (after
`store.ts:704`), exactly as v2 and v3 each do — one statement constant, two call sites, so the fresh-file
shape and the in-place step can never drift. Carry `archived_pr INTEGER` (D1) and
`dirty INTEGER NOT NULL DEFAULT 0` (D3) now even though nothing writes them until M8.9 / M8.3.

**Two rulings bind this DDL and override any `§4.2` text that disagrees.** **R-A**: the unique key is
`UNIQUE(repo, base_ref, head_ref, generation)` — the discriminator is a no-migration escape hatch, and an
archived triple is a one-way door that mints no successor, so `generation` is written once and never advanced
by this milestone. **R-B**: ids come from monotonic high-water marks in `meta`, never `MAX(id)+1`, so this
step seeds **two** `meta` rows, not one — a **review-id** high-water mark (default `LOCAL_REVIEW_ID_BASE - 1`,
read and bumped by M8.2.2's `createLocalReview`) and an **entity-id** high-water mark (default
`LOCAL_ENTITY_ID_BASE - 1`, read and bumped by `nextLocalEntityId`). The entity-id row exists because:
M8.4.2 needs a persisted, monotonic-across-restart entity-id source, comment ids live *inside* the stored
`ReviewThread` documents rather than in a column (so a `MAX(id)` scan would mean parsing every thread row),
and `meta` is the table that already carries `store_version`. Seeding it here is what keeps M8.4's minter from
becoming an unowned schema addition after v4 has shipped. No `DirectStore` surface change in this unit — the
allocator that reads and bumps the row is M8.2.2's. **Test first:** write Checks (1) and (2) below before a
single `CREATE TABLE`, and observe them red on `no such table: local_reviews`.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** Four durable tests in `store.test.ts`, in one `describe` beside the migration block at
`store.test.ts:265`.
(1) **v3 → v4 in place**, modelled line-for-line on the v2 → v3 test at `store.test.ts:473`: write a draft,
a viewed row, an audit row and a `pr_author` row; close; `DROP TABLE` all six local tables, `DELETE` **both**
seeded high-water `meta` rows, `UPDATE meta SET value = '3'`; reopen — assert the draft body reads back
verbatim, `getViewed` still reports the file viewed, `listAudit()` still has its row, `getPrAuthor` still
returns the recorded driver, `meta.store_version` equals `STORE_VERSION`,
`SELECT name FROM sqlite_master WHERE type='table'` contains all six local names, **and both high-water
`meta` rows are present again — the review-id one at `LOCAL_REVIEW_ID_BASE - 1` and the entity-id one at
`LOCAL_ENTITY_ID_BASE - 1`** — the guarded step re-seeds them, not only the fresh-file path, or every migrated
workspace hits M8.2.2's minter and allocator with no row to bump. Assert each row **separately**: one
assertion covering "the high-water rows exist" would stay green with either row missing.
(2) **The column shape is pinned, not incidental**: `PRAGMA table_info(<t>)` for each of the six tables
yields exactly the expected column names in order, with `local_reviews.dirty` `notnull` and defaulting `0`,
`local_reviews.archived_pr` nullable with no default, `local_reviews.generation` present and `notnull` (R-A's
escape hatch is worthless if the column is silently absent, and no behavioral assertion in this milestone
touches it), and `local_reviews_submitted.review_id` declared
`INTEGER` (never `REAL` — a 9e12 id round-tripped through a float loses its low bits). This is what makes a
later column rename, a dropped default, or a drift from M8.1's `LocalReviewSummary` fail loudly instead of
silently, and it is the only durable assertion the two dead-until-M8.9/M8.3 columns can carry.
(3) **No v1–v3 table is rebuilt**: capture
`SELECT name, sql FROM sqlite_master WHERE type='table' AND name IN ('immutables','snapshots','blobs','drafts','viewed','prefs','audit_log','pr_author') ORDER BY name`
from (1)'s reconstructed v3 file **before** the reopen, capture it again after, and assert `toEqual` — no PK
altered, no table rebuilt.
(4) **The ladder step exists**: read `store.ts`'s own source
(`readFileSync(new URL('./store.ts', import.meta.url), 'utf8')`, exactly as `audit-integrity.test.ts:110-113`
already reads this file) and assert that for every `n` from `2` to `STORE_VERSION` the source contains a
`current < n` guard. Structural rather than behavioral on purpose: the fresh-file `CREATE TABLE IF NOT
EXISTS` block makes a missing ladder step behaviorally invisible (Landmines), so no runtime assertion can
catch it — and expressing it as a loop to `STORE_VERSION` means v5 inherits the guard without rewriting it.

### M8.2.2 — `local_reviews`: mint, read, list
**Do:** Add `createLocalReview`, `getLocalReview`, `listLocalReviews`, and a narrow sync-state patch
(`base_sha` / `merge_base_sha` / `head_sha` / `dirty` / `last_synced_at` / `updated_at`) to `DirectStore`.
**Minting reads and bumps the review-id high-water `meta` row M8.2.1 seeds — never `MAX(id)+1`** (ruling
**R-B**; `LOCAL_REVIEW_ID_BASE` imported from `@revu/shared`, added by M8.1), read-and-bump-and-insert
**inside one `db.transaction`**; a duplicate `(repo, base_ref, head_ref, generation)` returns the existing
**non-archived** row instead of minting a second (`LOCAL_REVIEWS.md §8` case 6, ruling **R-A**). The
high-water mark is what makes a deleted review's id unreissuable, so M8.10 cannot silently re-attach an
orphaned dependent row to an unrelated new review. Also add `nextLocalEntityId()` — read-and-bump the `meta` high-water row
M8.2.1 seeded, inside one `db.transaction`, returning a value `>= LOCAL_ENTITY_ID_BASE` that is strictly
increasing across `close()` + reopen. This is the allocator M8.4.2's port takes as an injected function and
M8.5 wires; keeping the counter durable is what makes "never re-issues a prior id" true across a daemon
restart. Every write goes through the existing `write()` wrapper (`store.ts:291`)
so a failure is a `StoreWriteError`, never swallowed. State `listLocalReviews`'s order in its docstring, as
M8.2.5 does for threads and for the same reason. **Test first:** the `>= LOCAL_REVIEW_ID_BASE` assertion is
the guard against the rowid landmine below — write it, then write the naive `INSERT` that omits `id`, and
observe it red as `1 !== 1000000000`. That red is the point; a red that only says `createLocalReview is not
a function` would not have proven the assertion catches the bug.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** `bun test packages/revud/src/direct/store.test.ts` with new cases asserting: the first mint is
`>= LOCAL_REVIEW_ID_BASE` (never 1 — an auto-assigned rowid would land inside GitHub's PR-number range);
creating the same `(repo, base, head)` twice yields the same id and exactly one row; the same
`(base, head)` under two different `repo` values yields two distinct ids; ids survive `close()` +
reopen of the same data dir; `createLocalReview` against a closed database throws `StoreWriteError`. Plus:
**two independently opened stores over the same data dir** (`openDirectStore` twice, both live) creating the
same triple yield the same id and leave `SELECT COUNT(*) FROM local_reviews` at 1 — the two-process claim
the `db.transaction` + `UNIQUE` serializer makes, exercised the only way one test process can, and the case
that goes red if the mint is computed outside the transaction. Plus: the sync-state patch writes **exactly**
its named fields — `repo`, `base_ref`, `head_ref`, `title` and `created_at` read back byte-identical after
it while `updated_at` moves — and a patch against a closed database throws `StoreWriteError`. Plus:
`listLocalReviews` returns each created review exactly once in its documented order, and that order holds
across `close()` + reopen.

**Plus the one assertion that distinguishes R-B from what it overrules, and it is not optional.** Every other
assertion in this Check passes *identically* under `MAX(id)+1` and under a high-water mark, so without this one
the ruling lands unguarded: create two reviews, raw-`DELETE` the newer row straight out of `local_reviews`,
then create a **third** review with a different triple and assert its id is **strictly greater than the deleted
id** — never equal to it. A `MAX(id)+1` mint reissues the deleted id here and goes red; the high-water mark
does not. Pair it with a raw read of the high-water `meta` row showing it did **not** move backwards when the
row was deleted. This is the assertion that makes M8.10's id-reuse hazard structurally dead rather than
merely ruled against.

Plus, for the entity allocator: the first value is `>= LOCAL_ENTITY_ID_BASE`,
1000 successive calls are strictly increasing and all `Number.isSafeInteger`, and a `close()` + reopen
continues above the last issued value rather than restarting at the base.

## Constraints that bind this ticket

- **Migration doctrine: additive only, no PK altered, no table rebuilt** (`store.ts:616-630`,
  `LOCAL_REVIEWS.md §4.2`). SQLite cannot alter a primary key without rebuilding the table, and a rebuild
  is exactly what the doctrine forbids — this is *the* reason the design rejected widening
  `snapshots(pr_number)` into `(repo, id)` and grew parallel tables instead.
- **Drafts survive everything** (`memories/hard-constraints.md`). The v3 → v4 step reads no row and
  rewrites no row; `drafts` and `viewed` must be provably untouched by the open.
- **Absent ≠ unreadable** (`store.ts:56-61`). A missing local row is `null` (the correct empty answer);
  a present row whose JSON will not parse throws `StoreUnreadableError` and is never reseeded over.
- **No swallowed write failures** (`store.ts:85-100`, `:291`). Durability is a daemon concern — a local
  write that did not reach disk surfaces as `StoreWriteError` so the daemon can answer `persist_failed`
  rather than a 200 the client trusts as saved (`durable-flush.test.ts:105-132` is that contract at the
  router).
- **D4 — the reserved band is contract-level only.** Nothing in this ticket may write `snapshots`,
  `audit_log`, or `pr_author`. Their three readers are anchored above; all three would silently
  misinterpret a synthetic id as a GitHub PR number.
- **Two-half caching** (`memories/hard-constraints.md`): local snapshots reuse `immutables` keyed by
  `compareKey = merge_base…head`, never by head SHA alone, and with no TTL.
- **Identity**: `human_id` stays the lowercase git-config email, supplied by the session and overwritten
  on write (`direct-api.ts:197`, `:275-281`). It is a store key and never a path parameter — the route
  invariant at `draft-isolation.test.ts:117` must stay green untouched.
- **The frozen contract is not touched here.** `RevuApi` and the wire types are M8.1's surface; this
  ticket is internal to revud. If a local table seems to demand a contract change, that is a signal the
  boundary was drawn wrong — report it rather than editing `packages/shared/src/api/*`.
- **AGENTS.md code style**: comments and docstrings are self-contained. No `M8.2`, no ticket id, no
  "phase" in any line of code or SQL comment. `import type` for types; no unused bindings.
- WAL + `synchronous = FULL` are already set once at open (`store.ts:285-287`); new tables inherit them.
  Do not add per-table pragmas.

## Landmines

- **`id INTEGER PRIMARY KEY` is a rowid alias.** Insert a `NULL` (or omit the column) and SQLite
  auto-assigns `1` — a value squarely inside GitHub's PR-number range, in the one table whose entire
  purpose is to stay out of it. Always supplying the id from the high-water mark (R-B), plus a test
  asserting the first mint is `>= LOCAL_REVIEW_ID_BASE`, are the guard. Miss it and D2's band argument is
  void from the first review ever created.
- **The mint races outside a transaction**, whether it reads `MAX(id)` or the high-water row. `bun:sqlite` is
  synchronous, but two `revud` processes can share one `REVU_DATA_DIR`. Read-bump-and-insert inside one
  `db.transaction`, and let `UNIQUE(repo, base_ref, head_ref, generation)` be the real serializer via
  `ON CONFLICT … DO NOTHING` followed by a `SELECT`. Miss it and duplicate creation mints a second review for
  the same branch pair — breaking the "creating the same review twice returns the existing one" claim in
  `LOCAL_REVIEWS.md §3.1`. Note the high-water mark makes this **worse** if botched, not better: two racing
  readers of the same row both bump to the same value, so the read and the bump must be one statement or one
  transaction, never a `SELECT` followed by an `UPDATE`.
- **Bumping `STORE_VERSION` without adding the guarded step still appears to work**, because the
  fresh-file `CREATE TABLE IF NOT EXISTS` block at the top of `migrate` runs on every open and the stamp
  at `store.ts:706` moves the version forward regardless. The ladder step is what documents intent and
  what survives someone reordering `migrate`. Skipping it leaves a silent hole for the next migration.
- **Do not reach for `snapshots` "because the id is an integer anyway."** It is the single most natural
  wrong move in this ticket — the column accepts the value, the tests pass, and the damage surfaces
  months later in the host collector's PR attribution. The M8.2.6 trigger test exists precisely because
  this mistake is invisible to ordinary assertions.
- **`putSnapshot`'s immutable-`partial` preservation is not boilerplate** (`store.ts:375-397`). A
  simplified `putLocalSnapshot` that writes the merged `partial` onto the immutable row will resurrect a
  stale "blobs missing" reason on the next warm `compareKey` hit, after those blobs were provisioned.
- **`getSnapshot` throws on a missing immutable half** (`store.ts:341-352`). `LOCAL_REVIEWS.md §8` case 15
  wants a graceful "objects missing, re-sync to rebuild" state — that is **M8.8's** job, at a layer above.
  Do not soften the store's error here to get there early; a corrupt store must stay loud.
- **Id reuse after deletion — CLOSED by R-B, and the reason it was closed.** `MAX(id)+1` re-mints a deleted
  review's id, so any `local_drafts` / `local_viewed` / pinned-ref row that outlived M8.10's delete would be
  silently adopted by an unrelated new review. The high-water mark makes that impossible regardless of how
  thorough the delete turns out to be. This does **not** close M8.10's open question 4 (what
  `deleteLocalReview` must prove it removes) — that is still open and still gates M8.10, but it no longer
  gates this ticket.
- **Composite PK index direction.** `PRIMARY KEY (human_id, local_id)` indexes `human_id` first, so
  M8.10's "delete everything for local id N" is a full scan on `local_drafts` / `local_viewed`. Small
  today; note it in the docstring rather than adding an index nobody has measured a need for.
- **Test hygiene**: `store.test.ts` gives every test a fresh `mkdtempSync` data dir
  (`store.test.ts:30-38`). Local-table tests must do the same. (The shared-mock-`localStorage` hazard in
  `memories/known-landmines.md` does not apply here — this suite is disk-local and network-free — but
  reusing one dir across tests reintroduces the same class of order-dependent flake.)
- **`local_reviews_submitted.review_id` will carry ids from the `LOCAL_ENTITY_ID_BASE` band (9e12).**
  Well inside JS's safe-integer range and inside SQLite's 64-bit INTEGER, so no precision hazard — but
  the column must be `INTEGER`, never `REAL`, or a round-trip through a float loses the low bits.

## Rulings — settled, and what they close

Recorded here rather than by rewriting the questions below, so each override stays auditable against the text
it replaces. **Where a ruling and this ticket's text disagree, the ruling wins.**

`(repo, base_ref, head_ref)` does **not** mint a successor; the archived review stays the review for that
triple. This is what the mock does today, so it costs **zero mock change** — and the mock is the specification.

> in the unique key** (`UNIQUE(repo, base_ref, head_ref, generation)`) as a no-migration escape hatch for a
> later milestone, so M8.2.1's DDL carries it.
> M8.9's open question 6 is closed by reference rather than reopened.
>
> ⚠️ **CORRECTION (2026-08-17, found while implementing M8.2.2): this ruling used to end "and M8.2.2's mint
> returns the existing *non-archived* row", which contradicts its own first sentence.** If the mint skipped an
> archived row it would mint a *successor* for that triple — exactly what a one-way door forbids. It also

**R-C — the builder lives in `direct/`, and dirty is `git status --porcelain -uno`.** Both are M8.3's

## Open questions

1. **Does a create on an archived `(repo, base_ref, head_ref)` triple mint a new review?** `§8` case 22 says
   "a new local review can be created" after a PR supersedes one; `§4.2`'s `UNIQUE(repo, base_ref, head_ref)`
   plus `§3.1`'s "creating the same triple returns the existing one" says it cannot. M8.9's open question 6
   raises this and states plainly that it must be **decided before M8.2 ships** — which is this ticket, three
   merges before anyone reads M8.9. The resolutions and their cost here: widen the unique key with a
   generation or archived discriminator (a schema decision that is free now and a migration later); let a
   create on an archived triple mint a successor and re-key the old row (no schema change, but the mint path
   grows a branch); or accept the design amendment that an archived branch pair is a one-way door. Whichever
   is chosen, M8.2.1's DDL and M8.2.2's mint must both reflect it, and M8.9's open question 6 is closed by
   reference rather than re-opened.
2. **Does the local surface belong on `DirectStore`, or on a sibling `LocalStore` returned from the same
   `openDirectStore`?** Adding ~14 methods roughly doubles an interface that five modules already type
   against. A separate slice sharing the one `Database` handle would also give M8.4 a natural place to
   depend on *only* the local surface, which serves D7's structural-absence argument. The design doc does
   not address the surface shape at all.
3. **Id reuse after delete.** `MAX(id)+1` (per `§3.1`) versus a monotonic high-water mark in `meta`.
   `§8` case 23 introduces deletion but the two sections are not reconciled. Deciding for the high-water
   mark now costs one `meta` row — and M8.2.1 already seeds one for entity ids, so the marginal cost is a
   second row in a table this ticket is touching anyway — and removes a whole class of M8.10 bug; deciding
   for `MAX(id)+1` means M8.10 must prove it deletes every dependent row, including pinned refs. M8.10's open
   question 4 says plainly that it "should not be started until that is settled".
4. **Ship `archived_pr` and `dirty` in v4, or add them when M8.9 / M8.3 need them?** The `§4.2` DDL
   includes both, so v4 carrying them matches the design — but they are dead schema until those tickets
   land. An `ALTER TABLE … ADD COLUMN` later is equally additive and legal; the tradeoff is one migration
   step now versus two later. Recommendation is to ship them now (the DDL is the spec); flagging it so the
   choice is deliberate.
5. **Repo-scoping the existing PR-keyed tables** is explicitly raised and explicitly not answered by
   `§4.2` ("a separate question this milestone raises but does not answer"). Nothing in M8.2 depends on it;
   recorded so a later reader does not mistake the omission for an oversight.

1. **Two claims in one test body meant one of them was never observed failing.** The first draft had both halves

   assertion fired and **the id claim itself was never seen to fail**. Split into two tests, with a code comment
   saying the split is load-bearing rather than stylistic. This is the memory's one-absence-per-test rule showing
   up on ordinary assertions, not just absences.

  docstring and asserted across close + reopen. **Honest residual, in a code comment:** `ORDER BY id DESC` is red,
  but *deleting* the clause stays green — `id INTEGER PRIMARY KEY` is the rowid alias, so a scan already yields id
  order and no data arrangement can separate the two. The clause pins the contract, not the mechanism.
- **`nextLocalEntityId` has no explicit `db.transaction`**, contrary to the letter of the unit text: the
  allocation is one `UPDATE … RETURNING`, already atomic under the row's write lock, with no second statement to

- **`write()` became generic** (`write<T>(table, fn: () => T): T`) so the mint reports its row *through* the

- **`patchLocalReviewSync` on an unknown id is a silent no-op** (an `UPDATE` matching no row). Documented and

### ⚠️ A live pre-existing defect on the PULL-REQUEST path, found and fixed here

Factoring the subtle `partial` rule into one `writeSnapshotRows` helper with two call sites — rather than
duplicating it, which would have planted a second copy of the exact rule the Landmines say drifts silently —
exposed that **`putSnapshot`'s preservation read sat OUTSIDE the `write()` wrapper.**

**Reachability, asked and answered.** The *closed-database* `RangeError` that first exposed it is **test-only**:
production closes the store solely in the `SIGTERM`/`SIGINT` handler (`index.ts:191-199`), whose
`try { store.close() } finally { server.stop(true); process.exit(0) }` is one synchronous block, and
single-threaded JS means no request handler can interleave. **But the hole it exposed was genuinely reachable.**
*Any* read fault on `immutables` during a snapshot write escaped `putSnapshot` as a raw, untyped driver error —
a disk I/O error, a corrupt page, or `SQLITE_BUSY`, and this codebase explicitly contemplates two `revud`
processes sharing one `REVU_DATA_DIR`. Such an error misses the `instanceof` check at `direct-router.ts:187`
entirely and falls through to a **generic 500 instead of `persist_failed`** — breaking the "never answer a 200
the client trusts as saved, and always say which failure it was" contract this store exists to uphold. Fixed for
**both** paths, since both now go through `writeSnapshotRows`, with the read inside `write()` **and** inside the
transaction (which additionally closes a read-then-write race on the immutable row). A `putSnapshot`
closed-database test was added — it did not exist before, so the hole now has its own guard rather than being
covered only incidentally.

### The `StoreUnreadableError` pass-through — and a correction to the reasoning that asked for it

The first pass of this unit re-wrapped a corrupt-immutable-row failure as `StoreWriteError`. That was sent back,
because **absent ≠ unreadable is a hard constraint**: a missing row is `null`, and a present-but-unreadable row
throws `StoreUnreadableError` and is never reseeded over. `write()` now re-throws `StoreUnreadableError`
unchanged and wraps everything else, with the discriminating red observed **before** the change
(`Expected constructor: StoreUnreadableError / Received constructor: StoreWriteError`).

**Proved inert elsewhere by enumeration, not assertion.** `StoreUnreadableError` is constructed at exactly three
sites (`parseRow`, and the two missing-immutable-half throws). `parseRow` has ten call sites; nine are in
getters, and **no `write()` callback calls any getter**. The tenth is `ownImmutablePartial`, called only from
`writeSnapshotRows` inside `write()` — **the single reachable path, and the one the fix targets**.
`setPreferences` is the only write method that calls a getter at all, and it does so one line *before* its
`write()`, so a corrupt `prefs` row already threw unwrapped and is unaffected. Empirically: removing the
pass-through failed **exactly 2 of 1656 tests**, both the corrupt-row tests, zero others.

> ⚠️ **CORRECTION to the rationale given when this change was requested.** The retryability argument — a failed
> write is retryable and answers `persist_failed`, a corrupt row is not — is right about the *store's* contract
> but **wrong about the wire today**. `direct-router.ts:187` maps `StoreWriteError` **and**
> `StoreUnreadableError` to the same `persist_failed` (500), and its docstring at `:181` says so deliberately.
> **Verified in the main tree.** So restoring the type changes nothing a client can observe; what it does is keep
> the store's own contract honest and preserve the distinction for in-process callers. **If the retryability
> distinction should be real end to end, the router needs a separate error code — that is a ticket of its own,
> for the owner, and is deliberately not smuggled into this unit.** Recorded here and in the handover rather
> than acted on.

**Also strengthened while in there:** both corrupt-row tests now assert the corrupt bytes read back **unchanged**
afterwards (the local-path one previously proved only that the envelope did not land), and the pull-request test
pins `err.table === 'immutables'` and the row key — so the error names the row that is *actually* corrupt rather
than the table the caller thought it was writing.
