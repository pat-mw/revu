## Goal

Implement **D1** (`LOCAL_REVIEWS.md §3`): when a pull request appears for the same repo + head ref + base
ref that a local review covers, that local review goes **read-only and links to the PR**, and nothing is ever
copied across. D1 is the decision that makes the whole feature safe — a publish path would reintroduce
exactly the leak the feature exists to prevent — so this ticket is **detection + read-only archival + a
link, and nothing else**. Three properties carry the weight: detection compares `head.repo.full_name` as
well as the two ref names, because a fork can have an identically named branch (`§8` case 20); archiving is
**non-destructive** — threads, drafts, submitted reviews and history all stay readable, and the only
`DELETE` in this store remains `deleteDraft` (`§8` case 22, and `hard-constraints.md`'s "drafts survive
everything"); and a PR **closed without merging does not un-archive**, so `archived_pr` is sticky once set.
The practical obstacle this ticket has to solve first is `§8` case 21: direct mode's `listPulls` is a 501
today, and M8.5's local list is a *local* listing, not the **GitHub** pull listing detection needs — so the
detection input does not exist yet and has to be built.

### M8.9.1 — The supersede predicate, pure and ref-shape-aware
**Do:** A standalone, I/O-free module exporting one predicate: given a local review's
`{ repo, baseRef, headRef }` and a `PullSummary`, answer whether that PR supersedes that review. Three
comparisons, all required: `pull.head.repo.full_name` equals the local review's repo identity (`§8` case 20
— a fork's `feature/x` is not this workspace's `feature/x`), `pull.head.ref` equals the local head ref, and
`pull.base.ref` equals the local base ref. Every comparison runs over **normalized** ref names, because the
two sides spell refs differently: M8.3 normalizes local refs to `refs/heads/…`, a base may legitimately be
a remote-tracking ref like `origin/main` (`§8` case 3), and GitHub reports bare `feature/x` / `main` on
`GhRef.ref` (`shared/src/api/types.ts:60-65`). Normalize both sides to the bare short name before
comparing. **Never compare SHAs** — under D8 a local review's merge base is computed against the live base
tip while GitHub's `pull.base.sha` only refreshes on a `synchronize` event, so the two legitimately
disagree about the same branch pair. Reject empty-string repo identities explicitly: the summary mapper
turns an absent `head.repo` (a deleted fork) into `full_name: ''` (`github-client.ts:862-875`), and an
empty local repo identity would otherwise match it. **Write `local-archive.test.ts` first** and observe it
red on the missing module — it is also the file M8.9.3, M8.9.4 and M8.9.7 extend, so it exists before any of
them.
**Files:** `packages/revud/src/direct/local-archive.ts` (new), `packages/revud/src/direct/local-archive.test.ts` (new)
**Check:** `bun test packages/revud/src/direct/local-archive.test.ts`, table-driven, one row per case, each
asserting exactly one comparison is load-bearing: same repo + same head + same base → supersedes; **fork
with the identical head ref** (`head.repo.full_name` differs, `head.ref` identical) → does **not**;
different base ref, same head → does **not**; local base `origin/main` vs PR base `main` → **does**; local
head `refs/heads/feature/x` vs PR head `feature/x` → **does**; `head.repo.full_name: ''` against a local
repo identity of `''` → does **not** (both blank never matches).

Plus the **module-purity assertion**, in the same file and built so it cannot go vacuous: read
`local-archive.ts`'s own source, extract its import specifiers, and assert the set contains neither
`./github-client` nor `./store` at any depth. The listing seam M8.9.3 adds and the store port M8.9.4 needs
are **locally declared interfaces**, never imports, so this assertion stays green through both units — that
is what makes the purity structural rather than a snapshot of this unit. Two self-assertions keep it honest,
in the shape M8.4.6 establishes: the source read is asserted non-empty (a renamed or moved file would
otherwise pass by scanning nothing), and the specifier extractor is run over an **inline fixture source**
importing `./github-client` and asserted to report that specifier, so a regex that stops matching fails here
instead of silently permitting everything.
**Negative control, recorded:** add `import type { GithubClient } from './github-client'` to
`local-archive.ts`, observe a **red** run naming the banned specifier, revert, observe green. Both
observations go in the `## Log`.

### M8.9.2 — Sticky `archived_pr` on the store's local slice
**Do:** Add the archive read/write to M8.2's local-review store slice over the existing
`archived_pr INTEGER` column (`§4.2`): a `markLocalReviewArchived(localId, prNumber)` that is **write-once**
(`… SET archived_pr = ? WHERE id = ? AND archived_pr IS NULL`, following the first-write-wins shape
`recordPrAuthor` already uses at `store.ts:561`) and a read that surfaces it on the local review row. There
is **no un-archive method** — that is `§8` case 22 stated as an absent capability rather than a guarded one.
Archiving writes exactly one column: no row in `local_threads`, `local_drafts`, `local_reviews_submitted`
or `local_viewed` is touched, and `immutables` / `blobs` are untouched. Write failures surface as
`StoreWriteError` like every other durable write (`store.ts:91-100`). **The store cases are written before
`markLocalReviewArchived` exists** and observed red.
**Files:** `packages/revud/src/direct/store.ts`, `packages/revud/src/direct/store.test.ts`
**Check:** `bun test packages/revud/src/direct/store.test.ts`. New cases: marking twice with two different
PR numbers leaves the **first** number standing; marking a review that already carries drafts, threads and a
submitted review leaves `SELECT count(*)` on `local_drafts`, `local_threads` and `local_reviews_submitted`
**unchanged** *and* the draft read back byte-identical to the seeded one
(`JSON.stringify(after) === JSON.stringify(seeded)`, so a silently rewritten draft fails as loudly as a
deleted one — "drafts survive everything" is the product); `expect(STORE_VERSION).toBe(4)` — M8.2's value,
pinned as an assertion rather than left to review, because the column already exists and this ticket adds no
migration step (`store.ts:65`); and a durable write failure surfaces as `StoreWriteError`, driven the way
`store.test.ts` already drives its write-failure cases.

The "no second `DELETE`" property becomes a **durable allowlist** rather than a `grep`: in the same file,
read `store.ts`'s source, extract every `DELETE FROM <table>` occurrence, and assert the sorted table list
equals an explicit literal — `drafts` today, plus whatever M8.2/M8.10 have already added by the time this
lands. A `DELETE` introduced later then fails in-gate until someone names it, which is the only form of
"archiving added no delete" that survives past this branch. Same two anti-vacuity self-assertions as M8.9.1:
the source read is asserted non-empty, and the extractor is proven on an inline fixture containing a
`DELETE FROM x`.
**Negative control, recorded:** make `markLocalReviewArchived` also call `deleteDraft`, observe **both** the
untouched-rows case and the allowlist go red, revert, observe green. Log both.

### M8.9.3 — A GitHub pull listing direct mode does not have
**Do:** `§8` case 21 in one unit. `createGithubClient` already returns `GithubClient & PullListClient`
(`github-client.ts:924`), but `DirectContext.github` is typed as the narrower `GithubClient`
(`context.ts:25-34`), and `mainDirect` builds no poll loop at all (`index.ts:172-181`) — so no direct-mode
code path can list pull requests today. Introduce a **narrow one-method read seam** for archive detection,

it in both mains — direct from `context`, broker from the already-built `pollClient` (`index.ts:284-292`)
rather than a second client. The seam must be **optional and absent-tolerant**: a workspace with no origin
and no token has no PR listing and must keep working, which is the milestone's headline exit criterion.
Declare the seam **locally in `local-archive.ts`** — a one-method interface, not an import of
`PullListClient` — so M8.9.1's purity assertion stays green. **Write the absent-source case first**, red,
before the seam is wired: a seam built first gets a default source and that case can never have been red.

### M8.9.4 — The sweep: detect → archive → refuse writes
**Do:** Join M8.9.1–M8.9.3. For each non-archived local review in the repo, ask the listing seam, run the
predicate, and on a match call `markLocalReviewArchived`. Then make the archived review **read-only at the
daemon**: all four local write verbs refuse before mutating anything. `submitReview` answers the contract's
200-level `{ status: 'forbidden', reason }` (`shared/src/api/types.ts:495-498`); `replyToThread`,
`resolveThread` and `addReaction` throw a typed `ApiError('forbidden', …)`, which
`envelopeForError` already serializes to its own status (`direct-router.ts:192-195`). The `reason` string
names the PR and says the review is archived — it must not read like the self-approval refusal (see
Landmines). **Reads stay fully open**: snapshot, threads, drafts, viewed, reconcile and blobs all continue
to serve. The archived check the write sink consults is a **plain store read of `archived_pr`** — the
detector, which holds a GitHub listing seam, must not enter the write sink's import graph (D7).
Decide and document what triggers the sweep (Open question 2), and assert the chosen trigger — a sweep
nothing calls is the failure mode the Landmines already name for direct mode.
**Files:** `packages/revud/src/direct/local-archive.ts`, the local write sink module M8.4 created
(`packages/revud/src/direct/local-writes.ts`), `packages/revud/src/direct/local-archive.test.ts`,
`packages/revud/src/direct/local-write-isolation.test.ts`
**Check:** `bun test packages/revud/src/direct/local-archive.test.ts`, over M8.4.8's
`createFakeLocalStore()` harness:

- **Detection.** A fake listing carrying one matching PR and one fork PR with the same head ref archives
  **exactly one** review and leaves the other's `archived_pr` null.
- **The refusals refuse before mutating.** After archiving, each of the four writes refuses (submit → a 200
  `forbidden` value, never a throw; the other three → an `ApiError('forbidden', …)`), and after each one the
  whole persisted local state is **byte-identical** to a `JSON.stringify` snapshot taken before the call —
  so "refuses before mutating anything" is asserted rather than described. The `reason` string names the PR
  number and matches none of the self-approval vocabulary (see Landmines).
- **Reads stay open.** `getSnapshot`, `getDraft`, `getFileViewed` and the thread read all answer with the
  same values they answered before the archive, asserted with `toEqual` against the pre-archive results.
- **Closed-without-merge is a no-op, with a positive control in the same test.** Re-run the sweep with the
  PR now `closed` and `merged: false` → `archived_pr` unchanged and no write becomes possible again; in that
  same sweep a **second**, not-yet-archived review whose PR is open **does** archive, so the "unchanged"
  assertion cannot pass because the sweep did nothing at all.
- **The trigger fires.** Whatever Open question 2 settles on, one assertion drives that trigger end-to-end
  and observes the archive land — if it is on `syncPull` or `GET /api/pulls`, the case lives in
  `packages/revud/src/direct/direct-api.test.ts` or `packages/revud/src/direct-router.test.ts` respectively
  and asserts `archived_pr` set afterwards. Its companion: with the listing seam **absent**, the same trigger
  fires, archives nothing, and issues zero requests under M8.9.3's `fetch` double.

And **D7 as a gate, not a courtesy**: `bun test packages/revud/src/direct/local-write-isolation.test.ts`
green with `./local-archive` **added to its banned-specifier list** — the detector legitimately holds a
listing seam, so the write sink must not import it either, and the archived guard is a plain store read.
That specifier lands green (nothing imports the detector yet), so its **negative control is the only

### M8.9.5 — Serving the archived state, with an ETag that actually moves
**Do:** Put the archived state on the wire, and make the list surface **reachable**. This is the unit with
the trap: `brokerEtag` composes the upstream list ETag with a hash of a fixed annotation projection
(`poll-loop.ts:141-155`, `:168-170`) that does not include `pull.state`, and `§4.1` specifies the *local*
list's ETag as a hash of the local reviews' `compareKey`s — neither of which moves when a review is
archived. Archiving changes no compare key and no annotation, so a client holding the prior ETag would 304
forever and **never learn the review was superseded**. Fold the archived state into whatever the list ETag
hashes, exactly as the CI rollup was folded in for the same reason (`poll-loop.ts:132-139` states the
argument). Then decide and implement how the archived PR number reaches the app (Open question 3) and what
`pull.state` reads as on an archived local review (Open question 4). Mirror the whole thing in the mock —
D6 makes the mock the spec, so the archived shape is defined there and revud conforms.
**Test first:** the ETag-composition case is written against today's ETag and observed **red** — archiving
leaves it byte-identical — before the fold is implemented. That red run is the landmine reproduced, and it
is what distinguishes this suite from one that encodes whatever the code ended up doing.
**Files:** `packages/revud/src/direct/direct-api.ts`, `packages/revud/src/direct/local-archive.ts`,
`packages/app/src/api/mock/adapter.ts`, `packages/app/src/api/mock/store.ts`,
`packages/revud/src/direct/direct-api.test.ts` (M8.5.1's file),
`packages/revud/src/direct-router.test.ts`, `packages/app/src/api/mock/store.test.ts`
Note what is **not** open here: the archived PR number's wire path is settled by M8.1's decision **D-c** — it
rides `LocalReviewSummary.archivedPr` through `listLocalReviews`, which M8.5.2 already serves and M8.6.2
already queries for the dirty badge, so no field is added to the frozen `BrokerPullMeta`. What this unit still
owes is the **ETag**, because the app's only *live* surface is `listPulls`: if archiving moves nothing the
client polls, the annotation query is the only thing that can notice, and it must not be given a long

**Check:** three legs, modelled on `checks-rollup.test.ts:98-136` and `:182-220` — the suite that exists

### M8.9.7 — Whether an archived review still re-syncs, decided and pinned
**Do:** Open question 9 is the one behavior this ticket creates that no unit asserts. M8.9.4 makes the four
**writes** refuse and is deliberately silent about `syncPull`, so today an archived review syncs or does not
sync purely as a side effect of M8.5.1's dispatch — and a later agent can flip it in either direction with
nothing going red. Decide it (freeze at the last synced `compareKey`, or keep syncing), record the decision
and its reason in Open question 9, then pin it. What does **not** reopen here: the archived review's
existing threads, submitted reviews and drafts stay readable and untouched either way — that is M8.9.2's
constraint. Nor does the decision reach the write refusals: a review that keeps syncing is still read-only
to the four write verbs.

`packages/revud/src/direct/direct-api.test.ts`

## Constraints that bind this ticket

- **D1 is the whole ticket, and it is a prohibition.** No code path may copy a local comment, thread, review
  summary or reaction to a pull request. Detection is a **read** of GitHub; archival is a **write to the
  local store**. If a unit starts needing a GitHub write client, the design has been reversed.
- **D7 — no GitHub client in the local write path, structurally.** The archive **detector** legitimately
  holds a GitHub listing seam; the local **write sink** must not. The archived guard M8.9.4 adds to the
  write path is a plain store read of `archived_pr`, so the detector never enters that module's import
  graph. M8.4's "the local write module imports no GitHub client" assertion must still pass after this
  branch — re-run it as a gate, not as a courtesy.
- **D4 — the real PR number stays out of the PR-keyed tables.** `archived_pr` holds a genuine GitHub PR
  number, and it lives **only** in `local_reviews`. Nothing here writes `snapshots.pr_number`,
  `audit_log.pr` (`store.ts:212-219`) or `pr_author.pr` (`store.ts:236-245`) — the collector's and poll
  loop's reading of "PR #N" stays truthful, and a local review remains invisible to the audit trail by
  design (`§8` case 25).
- **D8 — compare refs, never SHAs.** A local review's merge base comes from the live base tip; a PR's
  `base.sha` is refreshed only on a `synchronize` event. The two legitimately disagree for the same branch
  pair, so a SHA comparison would both false-negative and false-positive.
- **Archiving is non-destructive** (`§8` case 22, `hard-constraints.md`): threads, submitted reviews,
  history **and drafts** stay. "Drafts survive everything — that is the product." An archive that clears a
  draft is a product-level defect regardless of what the tests say.
- **The frozen contract is a read-only input.** `packages/shared/src/api/client.ts` and `types.ts` belong to
  M8.1 (AGENTS.md ownership). If surfacing the archived state seems to require a new field on
  `BrokerPullMeta`, that is a boundary question to raise (Open question 3), not an edit to make.
- **`CONDITIONAL_LIST_304_RULE`** (`http.ts:113-114`): `listPulls` stays the only conditional surface and a
  304 carries no body. Any state the app must observe rides through that ETag or it is unobservable.
- **The three transport semantics survive** (`hard-constraints.md`): an archived review's `getSnapshot`
  still returns `null`-not-404 for a never-synced review, and `submitReview` still returns its refusal as a
  **200-level value**, never an HTTP error.
- **D6 — the mock is the spec.** The archived shape is defined in the mock first and revud conforms; the
  conformance suite runs against the mock, and M8.11's local leg will hold both to it.
- **Identity**: the synthesized local `GhUser` keeps the git-config **name**, never the email (`§4.1`,
  `§8` case 26). Archival adds no identity field and must not smuggle one into the banner copy.
- **AGENTS.md code style**: no M-ID, phase, ticket or tracking reference in any comment or docstring;
  `import type` for types; no unused bindings; no raw hex in components (`globals.css` tokens only); every
  interactive element keyboard-reachable with a visible focus ring.

## Landmines

- **The served ETag does not move when a review is archived, so the app never finds out.** `brokerEtag`
  hashes the list ETag plus a fixed annotation projection (`poll-loop.ts:141-155`) that excludes
  `pull.state`; `§4.1` defines the local list's ETag as a hash of the **compareKeys**, and archiving changes
  neither. `usePullList` (`queries.ts:52-75`) keeps its cached items on a 304 — so the inbox shows the
  review as live indefinitely and the reviewer keeps writing comments into a review that is supposed to be
  read-only. This is the highest-value trap in the ticket, and `checks-rollup.test.ts:98-136` exists because
  the identical bug was already found once for the CI rollup.
- **`§4.2`'s `UNIQUE(repo, base_ref, head_ref)` contradicts `§8` case 22's "a new local review can be
  created".** Creating the same triple returns the existing (now archived) row (`§3.1`), so after an archive
  the user cannot start a fresh local review on the same branch pair at all. One of the two statements has to
  give, and **M8.2's open question 1 owns the answer** because it shapes the unique key — read what M8.2
  settled before assuming this ticket is a one-way door on that branch pair.
- **`pull.state: 'closed'` makes the review disappear from the inbox.** `inbox.tsx:122` and `:175` both
  filter `state === 'open'` before any section or tree is built, and `pr-layout.tsx:377-381` paints a closed
  pull's badge **danger-red**. `§4.1` says the archived local review's state is `'closed'`; `§8` case 22
  says it stays visible. Both cannot be true without a change at one end.
- **A missing list row lands the archived review on the GitHub-installation 404.** `usePullItem`
  (`queries.ts:175-181`) → `PrLayout`'s `!item` branch (`pr-layout.tsx:337-360`) renders "isn't in this
  installation", the exact screen `§7` names as the worst possible outcome for a local review. If archiving
  drops the review from `listPulls` for any reason, that is the screen the user gets.
- **The fork case is not hypothetical and the naive check misses it.** Comparing only `head.ref` + `base.ref`
  archives a local review because *someone else's fork* opened a PR from their `feature/x`. Compare
  `head.repo.full_name`. The related trap: a same-repo PR has `head.repo.full_name === base.repo.full_name`,
  so a "heads differ from base ⇒ fork" test (the `branchPair` shape at `pull-tooltip.ts:157`) is the **wrong**
  predicate here — the comparison is head-repo against the **local review's** repo identity.
- **A blank repo identity matches a deleted fork.** `github-client.ts:862-875` maps an absent `head.repo` to
  `full_name: ''`. M8.2's recorded rule forbids a blank local identity for exactly this reason — but the
  predicate must still reject the pair explicitly (M8.9.1's last table row), because the rule is enforced by a
  different ticket in a different package and a future no-origin path that produced `''` would otherwise
  archive every local review at once.
- **Ref spellings differ on the two sides.** M8.3 normalizes local refs to `refs/heads/…`; `§8` case 3 allows
  a base of `origin/main`; GitHub reports bare `main` / `feature/x`. A raw string compare silently never
  matches, and the failure mode is the *absence* of an archive — no error, no log, just a local review that
  quietly stays writable after the PR is open.
- **`listOpenPulls` is `state=open`, one page of 100** (`github-client.ts:1063-1096`). A PR opened and merged
  between two ticks is never observed, and a repo with more than 100 open pulls truncates. If detection is
  built on this list, both gaps are real and must be stated, not assumed away.
- **Direct mode has no tick at all.** `mainDirect` (`index.ts:172-181`) wires no poll loop, so "detection
  runs on the poll" quietly means "detection never runs in direct mode" — which is the mode the feature's
  primary user runs. Decide the trigger explicitly (Open question 2).
- **Detection spends the shared GitHub bucket, on a feature whose premise is "no token, no network".** A
  sweep that fires unconditionally either costs requests on every tick or hard-fails in the offline
  workspace the milestone exists to serve. The listing seam must be optional and its absence must be a
  no-op, never an error.
- **The `forbidden` submit branch tells the wrong story.** `review-bar.tsx:121-123` reacts to
  `{ status: 'forbidden' }` by silently switching the verdict to COMMENT and toasting the reason — copy
  written for the self-approval refusal. An archived review that surfaces only through that path reads as
  "you can't approve, use comment". Suppress the composer instead, and keep the server refusal as a
  backstop.
- **Archiving must not become the store's second `DELETE`.** `deleteDraft` (`store.ts:464`) is the only one
  today. "Read-only" means writes are refused, not that anything is removed; retention and pruning are
  M8.10's, and even there the rule is "prune unreferenced immutables", never "drop an archived review's
  threads".
- **`archived_pr` must be write-once in SQL, not in a read-then-write.** Two concurrent sweeps, or a sweep
  racing a manual archive, would otherwise last-writer-wins onto a different PR number. `recordPrAuthor`
  (`store.ts:561`) already shows the conditional-write shape.

## Open questions

1. **What GitHub call feeds detection?** Two candidates with different costs. (a) The existing
   `listOpenPulls` (`github-client.ts:1063-1096`) — one request per tick for the whole repo, but `state=open`
   only and capped at 100, so a PR opened-and-closed between ticks is never seen. (b) A **targeted** query
   per non-archived local review — `GET /pulls?head=<owner>:<branch>&base=<base>&state=all` — which is exact,
   catches closed and merged PRs, and costs one request per live local review. A workspace typically has few
   local reviews, which argues for (b); (a) reuses machinery that already exists in broker mode. `§8` case 21
   names the gap but not the fix. **Decide before M8.9.3** — it is the shape of the seam.
2. **What triggers the sweep?** The broker poll tick (`poll-loop.ts:642`) exists only in broker mode; direct
   mode has no periodic anything (`index.ts:172-181`). Candidates: on each local `syncPull`, on
   `GET /api/pulls`, on daemon boot, or on an explicit user action. Detection-on-sync is cheapest and most
   intuitive but means a branch nobody re-syncs stays un-archived indefinitely — the user keeps writing local
   comments while the PR is already open, which is precisely the confusion D1 exists to prevent. Whichever
   is chosen, M8.9.4's Check drives that trigger end-to-end — a sweep nothing calls must fail in-gate, not
   in the field.
3. ~~**How does the archived PR number reach the app?**~~ **Settled by M8.1's decision D-c**: it rides
   `LocalReviewSummary.archivedPr` through `listLocalReviews`, alongside `dirty`, queried under its own key by
   M8.6.2 and read only for badges and banners. `BrokerPullMeta` (`types.ts:278-301`) gains no field, the
   frozen contract is untouched, and `listPulls` remains the row source (D-a). If this ticket's owner wants
   the number on the list item instead, that is a contract change and it goes back to M8.1 — not a unilateral
   edit here, and not a `PullSummary` field smuggled in the `body` (`§7` warns against exactly that).
4. **Does an archived local review's `pull.state` read `'closed'`?** `§4.1` says yes; `inbox.tsx:122`/`:175`
   filter closed pulls out of every section and every tree, and `pr-layout.tsx:377-381` paints them
   danger-red. Either `§4.1` is amended for local reviews (state stays `'open'`, archival is carried
   elsewhere) or the inbox filters and the badge learn about the archived state. Both are real changes; the
   design does not pick one.
5. **What exactly is the link, and where does its host come from?** `PullSummary` carries no `html_url`
   (`types.ts:68-84`), the store keeps only `archived_pr INTEGER` (`§4.2`), and the app has no
   PR-link construction anywhere today. Constructing `https://github.com/<owner>/<name>/pull/<n>` needs the
   repo identity **and** assumes github.com — wrong on a GitHub Enterprise host. Consider storing the
   detected PR's URL alongside the number, which makes the link a fact rather than a guess. Whichever way it
   lands, M8.9.6's `archivedPrUrl` returns `null` rather than a guess when no URL is derivable, and the
   banner renders the PR number as text in that case — a path-shaped repo identity (Open question 7) must
   never produce `https://github.com//Users/…/pull/7`.
6. ~~**What happens when the user wants a fresh local review on an archived branch pair?**~~ **Owned by
   M8.2** (its open question 1), because the resolution shapes `UNIQUE(repo, base_ref, head_ref)` and
   changing that after v4 ships is a migration. This ticket consumes whatever M8.2 settled; it does not
   re-open it. The three candidates remain as M8.2 records them: widen the key with a generation or archived
   discriminator, let a create on an archived triple mint a successor and re-key the old row, or amend `§8`
   case 22. If M8.2 shipped without answering it, that is a defect in M8.2, and it is a migration to fix.
7. ~~**What is the repo identity string, and can it ever equal `head.repo.full_name`?**~~ **Settled by M8.2**:
   `repo` is `owner/name` whenever an origin parses, and the absolute toplevel path otherwise — never a hash,
   never blank. So detection is live in exactly the workspaces that had an origin when the review was created,
   and inert (correctly, not silently) in the offline workspaces the milestone exists to serve. Two
   consequences to carry into M8.9.1's table: a path-shaped identity can never equal a GitHub `owner/name`, so
   those reviews never archive and that is the intended behaviour, not a bug to work around; and a workspace
   that gains an `origin` *after* its first local review keeps the path-shaped identity on that row.
8. **A PR opened against a *different* base than the local review.** Local review is `main ← feature/x`; the
   PR is `develop ← feature/x`. `§8` case 20 requires the base to match, so no archive — the local review
   stays live and writable while the client repo already has a PR carrying that branch. That may be the
   intended behavior (the diffs genuinely differ), but it is the one shape where D1's guarantee and the
   user's mental model come apart, and it deserves a decision and a line of UI copy rather than silence.
9. **Does an archived local review still re-sync?** The branch can keep moving after the PR opens. Freezing
   at the last synced `compareKey` keeps the archived artifact stable and matches "read-only"; continuing to
   sync keeps the diff honest but means an archived review keeps changing under its own threads. The design
   says archival is read-only about **writes** and is silent about **syncs**. **M8.9.7 owns deciding this
   and pinning whichever answer lands**, because otherwise the behavior is a side effect of M8.5.1's
   dispatch that nothing asserts and anyone can flip.

## Testing exceptions

Two things in this ticket carry no automated assertion, and both are exceptions rather than oversights.

- **"The PR on github.com carries zero comments, zero reviews and zero reactions."** D1's headline
  observation needs a real PR on a real host with a real token — none of which the gate has, and none of
  which it may acquire. **Compensating assertions, both in-gate:** M8.4.6's
  `local-write-isolation.test.ts`, extended by M8.9.4 with `./local-archive`, proves the local write path
  cannot reach a GitHub client at any import depth; and M8.5.7's `no-network-preload.ts` fetch tripwire
  proves the local flow issues no outbound request at all. The github.com observation is recorded in the
  `## Log` as corroboration of those two — it is one observation of an absence, and on its own it guards
  nothing.
- **The rendered walk over `inbox.tsx`, `pr-layout.tsx` and `review-bar.tsx`.** All three read through hooks
  and providers (`usePullList`, `usePullItem`, the session context), so `renderToStaticMarkup` of them
  yields a throw or an empty shell; there is no RTL and no jsdom, and introducing one is not this ticket's
  call. **Compensating assertions:** the four legs of M8.9.6's Check — the banner as real HTML, the URL
  derivation, the three predicates, and `buildInboxSections` keeping an archived `closed` item in the
  `local` section — cover every *decision* those three files make about the archived state. What remains
  unasserted is wiring that reads a prop and passes it down, kept thin enough to read at a glance, with
  M8.11's e2e as the backstop.
