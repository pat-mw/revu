## Goal

Deliver the one genuinely net-new UI in the milestone: a way to *make* a local review, and a place in the
inbox where local reviews live. `LOCAL_REVIEWS.md §7` says it plainly — everything else in M8 is a variant of
something that already exists, but "a branch picker (local branches + remote-tracking refs for the base), a
base picker, and a create action" has no precedent to copy. This ticket implements the creation flow, the
`Local reviews` inbox section above `Waiting on you`, a row variant that reads `base ← head` instead of
`#number`, and the entry points (header button beside the List/Tree control, one command-palette entry in the
**Go** group, and — if a chord is taken — a `SHORTCUT_CATALOG` entry to document it).

It implements **D2** (`§3`): the reserved high-number identity is what lets all of this reuse the `/pr/:n`
route family, both `matchPrNumber` regexes, and every existing React Query key untouched. It also carries
`§8` edge case 6 into the UI — creating the same `(repo, base, head)` twice **returns the existing review**
rather than minting a second, so the app must treat a returned pre-existing id as success and navigate to it.

Because the mock is the spec (**D6**), this ticket is completable against **M8.1 alone**: no daemon, no git,
no network. `?mock=1` is the acceptance surface. Local-mode *chrome* inside `/pr/:n` — tab omission, header
seal, copy sweep — is **M8.7** and is deliberately out of scope here.

## Rulings — settled 2026-08-14, and what they override

Recorded here rather than by rewriting the units below, so each override stays auditable against the text it
replaces. **Where a ruling and a unit's text disagree, the ruling wins.** Full rationale is in
[`HANDOVER.md`](../HANDOVER.md)'s top entry.

**R1 — the `Local reviews` section renders iff `listLocalReviews()` returns anything**, archived and closed
rows included; it sits **above `Waiting on you` when it has open rows, below every other section when it is
empty**, and is absent entirely when the human has no local reviews at all. (Open question 2, owner.)

> **Overrides M8.6.4** in two places. Its *Do* says to prepend the section above `Waiting on you`
> unconditionally — that is now the has-rows case only. Its *Check* "**The local section is first** —
> `buildInboxSections(...).map((s) => s.id)[0] === 'local'`" becomes **conditional**, and the unit asserts all
> three states: first with open rows, **last** when empty-but-present, **absent** when there are no local
> reviews at all. Position is a property of the pure function in every state, so no state is left unasserted.
>
> **Extends M8.6.2** by one reader: section *presence* now reads the annotation query. This is deliberately
> **not** a two-truths violation — the annotation query supplies a boolean about existence and never a row, a
> title, a ref pair or a `broker.*` field, and `usePullList` remains the sole row source. Say so in the
> module's docstring, because the next reader will check that line specifically.
>
> **Sharpened 2026-08-14 by a finding from M8.6.2, and the correction matters.** The row source does **not**
> filter by state — `api/mock/adapter.ts:276-278` pushes every local review into `listPulls` regardless — so
> the open-only filter lives in the **caller**, at `inbox.tsx:122`. That means existence *could* be derived
> from the unfiltered list with no second query at all. It is still derived from the annotation query, for a
> better reason than the original one: **M8.9's open question 4 — whether an archived local review reaches the
> inbox at all — is unresolved**, so deriving presence from the row source would couple this section's
> existence to a decision nobody has made yet. The annotation query is robust to either answer. Any docstring
> here must say "callers filter it to open reviews", never "the row source filters", so it stays true once
> archival lands.

**R2 — the tree excludes local reviews** from `buildPullTree`'s input; they render as their own group above the
roots. (Open question 4, implementer call.) *Confirms M8.6.6's default reading — no override.*

**R3 — the chord is `g l`, registered shell-side**, catalog group `Global`. (Open question 5, implementer
call.) `g i`/`g f`/`g c` are the live `g` prefixes and `l` is free; the catalog's no-duplicate-keys assertion
catches a collision in-gate rather than by eye. Shell-side registration is what makes the chord work from a PR
page, matching the palette entry's global reach — so **M8.6.5 does lift the dialog into `app-shell.tsx`'s
existing overlay set** (palette, shortcut sheet, dev panel), and its Files line's conditional `app-shell.tsx`
entry is now unconditional.

**R4 — the title is not editable after creation.** (Open question 6.) M8.1 froze the route set at
`GET /api/branches`, `POST /api/local-reviews`, `GET /api/local-reviews`, `DELETE /api/local-reviews/:n`; there
is no update verb, so the title is chosen once, in the dialog, permanently. **M8.6.3's dialog docstring states
this** — it is a fact about the frozen contract, not a preference.

**R5 — open question 3 (the superseded badge) is answered by M8.9's OQ4 and is NOT decided here.** M8.6 renders
the **dirty** badge only. The superseded badge's reachability depends on whether an archived local review
survives the inbox's open-only filter, which M8.9 owns; building the badge now would be building against an
undecided filter.

## Units

Default execution order below, with one deviation the numbering does not show: **M8.6.7 lands first**. It is
the harness enabler every static-render and query-layer test in this ticket rests on — without it a test that
imports `@/state/queries`, `@/pages/inbox` or `@/components/palette` cannot even resolve its imports (see
Landmines), so the tests for .2, .3, .4 and .5 cannot be written, let alone observed red. Then **M8.6.1** —
every later unit imports its helpers. **M8.6.2 is independent of M8.6.1** and can run in parallel (it touches
only the query layer). **M8.6.3 and M8.6.4 are mutually independent** once .1 and .2 are in, and are the two
biggest commits. **M8.6.5 depends on .3** (it opens the dialog it wires). **M8.6.6 now depends on .1 and .4** —
.4 is where `matchesFilter` moves out of the component into the pure module .6 then edits, so .6 can no longer
land straight after .1.

Within every unit the test is written and **observed red before the code**, and every Check below names a file
and an assertion that runs on each future gate. `tsc -b`, `oxlint` and a `?mock=1` walk appear only as
corroboration, never as a unit's Check. Five assertions in this ticket claim an **absence** — .1's "the label
carries no digit of the id", .3's "the head picker offers no remote-tracking ref", .4's "the local review is in
no other section" and "the hover card claims no CI", .6's "no local node in the tree". Each names its
**positive control in the same file**, so a matcher that matches nothing, or a fixture whose collision never
existed, fails instead of passing silently. Verify step 4's DOM search gets its control at the keyboard.

### M8.6.1 — Pure view-model: identity, partition, label, validation
**Do:** A pure module the rest of the ticket derives from, so the UI holds no ad-hoc branching:
- `isLocalReviewItem(item)` and the raw `isLocal(n)` predicate — **the single app-side call to
  `isLocalReviewId`** (M8.1). Nothing else in the app compares a number to a base constant, and nothing else
  imports `isLocalReviewId` from `@revu/shared`. M8.7.1's `lib/review-mode.ts` derives `reviewMode(n)` by
  importing the predicate **from this module** rather than calling the shared one a second time; M8.7.4's grep
  check allows exactly this file. Say so in the docstring — the two tickets are parallel-eligible on paper and
  this is the sentence that keeps whichever lands second from growing a duplicate.
- `partitionInbox(items) → { local, github }` — preserves input order within each side.
- `localReviewLabel(pull) → { head, base }` — the `base ← head` pair the row and the palette render **instead
  of** `#{number}`. `§3.1`: "`#1000000001` is never rendered."
- `rowIdentity(item) → { kind: 'github'; text: string } | { kind: 'local'; head: string; base: string }` — the
  identity slot as **data**, so "the number is never rendered" is a property of a pure function rather than of
  a JSX branch nobody can assert on. M8.6.4's row renders this and nothing else in that slot.
- `createReviewIssue({ base, head }) → string | null` — the client-side pre-flight for `§8` edge cases 1 and 7:
  same base and head, an empty ref, and a ref beginning with `-`. It is a *fast fail for the user*, never the
  security boundary — the authoritative validation is `git check-ref-format` on the daemon side (M8.3) and the
  shared validator (M8.1). Say that in the docstring so nobody later deletes the server check.

**Files:** `packages/app/src/lib/local-reviews.ts` (new), `packages/app/src/lib/local-reviews.test.ts` (new).
**Check:** `bun test packages/app/src/lib/local-reviews.test.ts` green. It imports nothing from `@/api`, so it
runs as a pure-lib test in the `pull-tree.test.ts` style, over synthesized `PullListItem`s from a local `pr()`
helper. Assertions:
- `isLocalReviewItem` on an item at `LOCAL_REVIEW_ID_BASE` is `true` and on one at `482` is `false`; the module
  imports `LOCAL_REVIEW_ID_BASE` from `@revu/shared` rather than writing `1_000_000_000` as a literal, so
  raising the band moves the test with the code.
- `partitionInbox` is order-preserving **and total**: over a mixed input, `[...local, ...github]` sorted by
  number equals the input sorted by number, and `local.length + github.length === items.length` — so an item
  can be neither dropped nor double-counted.
- `rowIdentity` on a local item returns `kind: 'local'` and **neither** `head` nor `base` contains any

  when they are there. `localReviewLabel` returns exactly the two refs (`toEqual({ head: 'feature/x', base:

- `createReviewIssue` returns a **non-null** sentence for each rejected shape separately — `{ base: 'main',
  head: 'main' }`, `{ base: '', head: 'f' }`, `{ base: '--upload-pack=x', head: 'f' }` — **and `null` for a
  valid pair** (`{ base: 'main', head: 'feature/x' }`). The last assertion is the control that distinguishes a
  real pre-flight from one that rejects everything; without it a `() => 'no'` stub passes the other three.

Write the test first and observe it red — `bun test` will fail to resolve `./local-reviews` before the module

### M8.6.2 — Query layer: branches, create, and the list invalidation
**Do:** Add `qk.branches` **and** `qk.localReviews` to the key factory at `state/queries.ts:35-44` — never an
inline key. Add `packages/app/src/state/local-reviews.ts`
with `useBranches()` (`staleTime` in the seconds, refetched when the create dialog opens — branches change
under the user constantly), `useLocalReviewAnnotations()` over `listLocalReviews`, and
`useCreateLocalReview()`.

The two query sources have a strict, non-overlapping division of labour, fixed by M8.1's decision D-c:
**`usePullList` is the row source** for every rendered row (D-a merges local reviews into `listPulls`, and
`PrLayout` can resolve a review only from there), and `listLocalReviews` supplies **only** the two local-only
annotations `LocalReviewSummary` carries and `BrokerPullMeta` cannot — `dirty` (D3) and `archivedPr` (D1).
Nothing renders a row, a title, a ref pair or a `broker.*` field from the annotation query; that is the "two
truths" hazard, and keeping the annotation query keyed separately and read only for badges is what avoids it.
Invalidate `qk.localReviews` alongside `qk.pulls` on create.

The mutation's `onSuccess` must **refresh `qk.pulls` and await it before the caller navigates**.
`PrLayout` resolves its PR by searching `usePullList()` (`pr-layout.tsx:280-282`); navigating to `/pr/<newId>`
before the list carries it lands the user on the "isn't in this installation" empty state
(`pr-layout.tsx:349`) — the exact screen `§7` calls out as actively harmful copy. Return the created (or
pre-existing) review from the mutation so the caller navigates by its id rather than re-deriving it.

Factor that refresh into an exported **non-hook** helper — `refreshAfterLocalReviewCreate(qc): Promise<void>` —
that `onSuccess` awaits and the test drives directly; a hook body is not assertable without a renderer, and
this is the single behavior in the unit that a regression would silently reintroduce. Mind which verb it uses:
`invalidateQueries` defaults to `refetchType: 'active'`, so on a client with **no mounted observer** it marks
the entry stale and refetches nothing — the awaited call has to be one that actually refetches. The test below
is what distinguishes the two.

**Files:** `packages/app/src/state/queries.ts` (key factory only), `packages/app/src/state/local-reviews.ts` (new),
`packages/app/src/state/local-reviews.test.ts` (new).
**Check:** `bun test packages/app/src/state/local-reviews.test.ts`, driving `createMockApi()` with
`mockDev.reset()` + `setLatency('zero')` in `beforeAll` and `mockDev.reset()` in `afterAll` (the
shared-mock-store rule, per `components/review/failure-drills.test.ts:32-43`). Four assertions:
1. **Idempotent creation, consumed app-side.** Create `(main, feature/x)`, create it again — the **same id**
   both times, the returned id satisfies `isLocalReviewId`, and `listPulls()` contains **exactly one** item
   with that number.
2. **The refresh actually lands the row.** On a real `QueryClient`, `await qc.fetchQuery({ queryKey: qk.pulls,
   queryFn: () => api.listPulls() })` **before** creating; assert the cached items do **not** contain the new
   id (the pre-condition is the negative control — it proves the later assertion is sensitive to the refresh).
   Create, `await refreshAfterLocalReviewCreate(qc)`, then assert `qc.getQueryData(qk.pulls)!.items` **does**
   contain it. A helper that only marks the query stale leaves the stale items in place and fails here, which
   is exactly the "lands on the 404 screen" landmine caught in-gate.
3. **The ETag short-circuit does not hide it.** Capture `etag` from the pre-create `listPulls()`, create, then
   `api.listPulls({ etag })` — assert `notModified` is not `true` **and** the items contain the new id. `§4.1`
   makes the local ETag a hash of the local reviews' compare keys; this is the app-side pin on that promise,
   and it is what would go red if a transport ever answered 304 across a create.
4. **The keys are in the factory and distinct.** `qk.branches` and `qk.localReviews` exist, and
   `JSON.stringify` of each differs from `qk.pulls` and from the other — a collision would make the annotation
   query and the row source share a cache entry, which is the two-truths hazard in its cheapest form.

### M8.6.3 — The create dialog
**Do:** A Radix `Dialog` (`components/ui/dialog.tsx:30-54`) with a filterable head picker, a filterable base
picker, a title field, and a create action. Model the pickers on the palette's embedded `cmdk` list
(`components/ui/command.tsx:88`/`:115`) — a repo can have hundreds of branches and a bare `<select>` is
unusable at that size. The **base picker offers local branches *and* remote-tracking refs** (`§8` edge case 3:
`origin/main` is a legal base); the head picker offers local branches only.

Title defaults to the head branch name (`§4.1`) and is editable. A failed create **keeps the dialog open with
every field intact** — never discard user-written text on failure (hard-constraints). Surface M8.1's typed
errors as their own sentences: unrelated histories naming both refs (`§8` edge case 4), shallow clone
(edge case 5), ref not found, `base == head` (edge case 1). A duplicate is **not** an error path: it resolves,
and the dialog closes onto the existing review.

Split the file so the behavior is assertable, because a Radix `DialogContent` renders through a portal and
`renderToStaticMarkup` of it yields the **empty string** — a test against the dialog shell would assert on
`''` and pass forever (see Landmines). Three exports, one component tree:
- `CreateLocalReviewForm` — the portal-free body (both pickers, the title field, the error line, the create
  button). It takes its branches, values, pending flag and error sentence as **props** and owns no query. This
  is what the test renders.
- `describeCreateLocalReviewError(err) → string` — one honest sentence per typed error, in the shape
  `components/review/error-copy.ts:20-29` already establishes, so the copy has a single source a test can pin
  against the real function rather than a pasted literal.
- `reduceCreateLocalReview(state, event)` — the pure state machine over `{ base, head, title, error, pending }`.
  A `create_failed` event returns the previous `base`, `head` and `title` **unchanged**; a `created` event
  carries the id and closes, whether the id was newly minted or pre-existing.
`CreateLocalReviewDialog` is then the thin wiring: `Dialog` → `DialogContent` → `CreateLocalReviewForm`, with
the reducer and M8.6.2's mutation hooked up — thin enough to read at a glance, per the UI-testing doctrine.

**Files:** `packages/app/src/components/create-local-review.tsx` (new — flat beside `palette.tsx` and
`shortcut-sheet.tsx`, the app's other two global overlays),
`packages/app/src/components/create-local-review.test.ts` (new — **`.ts`, never `.test.tsx`**; it renders
through `createElement` + `renderToStaticMarkup`, exactly as `components/ui/markdown.test.ts:1-21` does).
**Check:** `bun test packages/app/src/components/create-local-review.test.ts`, asserting on real HTML and on

1. **The pickers offer the right refs.** Static-render the form with a `BranchRef[]` holding two local
   branches and one remote-tracking ref: the base picker's markup contains all three, the head picker's

## Landmines

- **An archived local review is `state: 'closed'` and the inbox only renders open items.** `§4.1` sets
  `pull.state` to `'closed'` once archived under D1, and `inbox.tsx:122` / `:175` / `:258` all filter on
  `pull.state === 'open'`. So the "superseded" badge M8.6's seed text asks for is, as the code stands,
  unreachable — the row is gone before it could carry it. Decide this with M8.9 rather than discovering it
  after building the badge (see **Open questions**).
- **Navigating before the list refetches lands on the 404 screen.** `PrLayout` resolves the review out of
  `usePullList()` (`pr-layout.tsx:280-282`); with no match it renders "PR #… isn't in this installation"
  (`:349`) — the exact copy `§7` flags as harmful, and the one a mis-keyed local review would hit. Await the
  invalidation, or seed the list cache from the create response.
- **The ETag short-circuit can hide a brand-new review.** `usePullList` holds the previous ETag in a ref
  (`queries.ts:54`, `:60`) and, on `notModified`, returns the **previous items** (`:63-71`). An invalidation
  that re-issues the same ETag and gets a 304 back leaves the new row invisible until something else changes
  the list. `§4.1` says the local ETag is a hash of the local reviews' compare keys, so it *should* move — but
  the app must not depend on that alone: assert the new row is present after create, not merely that a refetch
  fired.
- **`w-12` and a ten-digit number.** `inbox.tsx:543-545` reserves twelve units for `#482`. Restyling the slot
  is the wrong fix twice over — it would still render a number `§3.1` forbids.
- **A zero-total checks rollup reads as "Checks passed".** `pull-tooltip.ts:177-180` maps `total <= 0` to a
  countless phrasing per state, so `{ state:'success', total:0 }` claims CI passed on a branch that was never
  pushed. Only an **absent** `broker.checks` omits the line. Assert absence rather than trusting it.
- **`branchPair` will call a local review a fork** if the synthesized `head.repo.full_name` and
  `base.repo.full_name` differ (`pull-tooltip.ts:157`), rendering the `fork` badge at `inbox.tsx:626-630`.
  Nothing on GitHub is involved, so "fork" is meaningless there.
- **The tree can nest a real PR under a local review.** `pull-tree.ts:62-79` parents purely on
  `base.ref === parent.head.ref`, with no repo and no id-band awareness; `byHead` (`:51-55`) resolves ties by
  lowest number, which a ≥1e9 id always loses — so a local review never *steals* a parent, but it can *become*
  one. It also creates its own root (`:76-79`) and reorders the root list, which is sorted by subtree size
  (`:107-113`).
- **The inbox's bare keys fire behind a modal.** `inbox.tsx:216-221` registers `j`/`k`/`enter` with no
  `enabled` gate, and `isFromTextEntry` (`keyboard.tsx:176-181`) only exempts real text controls. Pressing
  `enter` on the dialog's create button while it is focused will *also* navigate the inbox behind it if the
  handler stack is not gated.
- **A catalog entry alone binds nothing, and a binding alone documents nothing.** `lib/shortcuts.ts:1-10` is
  explicit. And an entry whose `group` is not in `shortcut-sheet.tsx:16-22`'s `GROUP_ORDER` never renders in
  the `?` sheet at all — a silently invisible row.
- **The palette caps at ten open pulls** (`palette.tsx:88-97`). Local reviews merged into the same list either
  crowd PRs out or fall off themselves; and at `:146-151` each item renders `#{number}`. If local reviews are
  to be jumpable from the palette, they need their own rendering, not the PR item's.
- **The draft probe scales with the merged list.** `inbox.tsx:90-96` fires one `getDraft` per listed item. In
  HTTP mode, N local reviews are N more requests in the same burst — cheap, local, and journal-free, but not
  free, and worth watching if `§8` edge case 10's "very large" case ever means many reviews rather than many
  files.
- **The shared mock store leaks across `bun test` files** (memories/known-landmines.md). Green locally, red on
  a slower CI runner. `mockDev.reset()` in `beforeAll`, restore in `afterAll`, or avoid the mock entirely.
- **The e2e driver is a plain `bun run` script, never a `*.test.ts`** (memories/known-landmines.md) — the gate
  runs `bun test` before the app build, so a `*.test.ts` e2e would run with no `dist`. If this ticket adds an
  e2e step it belongs in `e2e/`, not beside the unit tests; the local-review e2e proper is **M8.11**.
- **`bun test` has no `window.location`.** `test/preload.ts:28-30` sets `window = globalThis`, and bun's
  `globalThis` carries no `location`, so `@/api`'s module-scope `selectApi(configuredBase(),
  forceMockFromLocation())` throws `TypeError: undefined is not an object (evaluating 'window.location.search')`
  the instant anything imports it — `@/state/queries`, `@/pages/inbox` and `@/components/palette` included. This
  is not a subtle failure; it is an unhandled error before the first test runs, and it is why M8.6.7 lands
  before every other unit whose Check renders or reads a query key. `@/lib/*`, `@/fixtures`, `@/api/mock/*` and
  `@/components/shortcut-sheet` are all clear of it.
- **A Radix dialog static-renders to the empty string.** `DialogContent` goes through `DialogPortal`, which
  emits nothing on the server; `renderToStaticMarkup(<Dialog open><DialogContent>…)` returns `""`. A test
  written against the dialog shell asserts on an empty string and passes forever. The form body has to be its
  own portal-free component (M8.6.3). `cmdk`'s list, `EmptyState`, `Badge`, `Input` and `Button` all render
  fine — the portal is the only wall.
- **`invalidateQueries` refetches nothing without a mounted observer.** Its default is
  `refetchType: 'active'`, so on a bare `QueryClient` — which is exactly what a test holds, and briefly what a
  freshly navigated app holds — it marks the entry stale and returns. Awaiting it therefore proves nothing
  about the list carrying the new review, which is precisely the 404-screen landmine two entries up.
- **A `.test.tsx` in `packages/app` is a new convention, not an existing one.** There is not one in the repo.
  Every render assertion here is a `.ts` file using `createElement`, per `components/ui/markdown.test.ts`.

1. ~~**Which call feeds the inbox's local section — `listPulls` or `listLocalReviews`?**~~ **Settled by M8.1's

3. **Can the superseded (D1) badge render at all?** Its *source* is settled — `LocalReviewSummary.archivedPr`

4. **Do local reviews appear in the Tree arrangement at all?** The seed text asks only that the tree "does not
   mis-parent" them. Excluding them and rendering a separate group is the safest reading; including them as
   their own roots is defensible (a local review *is* stacked on a base branch, and `§8` edge case 3 allows a
   remote-tracking base). Excluding them means the Tree arrangement shows strictly fewer rows than List, which
   `inbox.tsx:419` currently promises it does not ("Neither is a filter — both show the same PRs").
   **Implementer call, documented in `pull-tree` usage rather than in `pull-tree.ts` itself.**
5. **Which chord, and registered where?** `§7` calls the chord optional and the seed text says "if it gets a
   chord". `g` is already a prefix with `i`/`f`/`c` taken (`app-shell.tsx:225-233`). Registering shell-side

   (`app-shell.tsx:281-287`); registering inbox-side keeps the inbox self-contained but makes the key dead
   everywhere else. The two decisions are one decision. **Implementer call.**
6. **Is the title editable after creation?** `§4.1` allows "the head branch name (or a user-supplied title)",

   update verb, the title is set once at creation and the dialog is the only place it can ever be chosen.
   Worth knowing before designing the field. **Confirm against M8.1.**
7. **What does the base picker default to?** Nothing in the app knows the repo's default branch — `PullSummary`
   carries no such field, and `useRepoContext` (`app-shell.tsx:37-40`) reads a repo name off the first list
   item, which is empty in a repo with no PRs. With no `origin` there may be no `origin/HEAD` either. Options:
   no default (the user must pick), or `BranchRef` carries a `default` marker. That is a **wire-shape**
   question, so it is answered once in **M8.1's open question 3** (which fixes `BranchRef` for both
   transports); M8.3.7 reads `refs/remotes/origin/HEAD` to populate it and degrades to no marker in a repo
