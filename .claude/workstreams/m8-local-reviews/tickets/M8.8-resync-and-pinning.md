## Goal

Make re-sync survive the two things a local branch does constantly and a pull request almost never does:
being amended and being rebased. This ticket delivers the object pinning of `LOCAL_REVIEWS.md §5.1` (a git
ref per synced snapshot, so `git gc` can never take the objects the local blob tier is the *only* source
for), replaces the silently under-reporting author-date fallback with explicit rewrite detection
(`LOCAL_REVIEWS.md §8` case 12), turns "the content this snapshot references is gone" from a hard unreadable
error into an honest re-syncable state (case 15), keeps a deleted or renamed branch from costing a single
draft (case 14), fixes rather than reproduces the latent stale-`draft.headSha` bug a conflict-terminated
reconcile leaves behind (case 18), and states the **D8** base-advance behaviour honestly — a local `compareKey`
can change
with zero new head commits, because the merge base is recomputed against the live base tip. It implements
**D8** directly and is the enforcement arm of **D7**: with the GitHub blob tier structurally absent from the
local path (M8.3.6), a pruned object has no second source, so retention of git objects becomes a
correctness property rather than a convenience.

### M8.8.1 — The pin seam: a ref name git will actually accept

**Do:** Add `packages/revud/src/direct/local-pins.ts`, the only module that names or writes a pin ref. It
takes a `CommandRunner` and a repo root and **never** a `GithubClient` (D7 is structural here too). Exports:

- `pinKeyForCompare(compareKey)` — a pure function turning `${mergeBaseSha}...${headSha}` into a
  **ref-legal** path component. The design's literal `refs/revu/reviews/<id>/<compareKey>` **cannot be
  created**: `git check-ref-format` rejects any name containing `..`, and a compareKey contains three of
  them (verified: `git check-ref-format refs/revu/reviews/1000000001/aaaa...bbbb` exits **1**). Do the
  substitution in exactly one place — `...` → `-`, giving `<mergeBaseSha>-<headSha>` — and never re-derive
  the compareKey from a ref name (list refs, do not parse them).
- `pinRefsFor(localId, compareKey)` → the two ref names
  `refs/revu/reviews/<localId>/<pinKey>/base` and `.../head`. `<localId>` and `<pinKey>` must always be
  **directories, never refs**: a ref at `refs/revu/reviews/<id>` makes every child unwritable
  (verified: `fatal: update_ref failed … 'refs/revu/reviews/<id>/…/head' exists; cannot create
  'refs/revu/reviews/<id>'`).
- `pinSnapshotObjects(runner, cwd, localId, { mergeBaseSha, headSha })` — one `git update-ref --stdin`
  invocation writing both refs, so a crash cannot leave half a pin. Validate `localId` is a positive
  integer and each SHA matches `/^[0-9a-f]{40,64}$/` (40 for sha1, 64 for a sha256 repo) **before** it
  enters an argv; route the argv through M8.3.1's `runGit` so `--end-of-options` discipline is inherited.
  Idempotent: re-pinning the same compare rewrites the same two refs.
- `listPins(runner, cwd, localId?)` — `git for-each-ref --format='%(refname)%00%(objectname)'` over
  `refs/revu/reviews/` (optionally narrowed to one id). Always pass an explicit `--format`; the default
  output is not a parsing contract.

**This module writes and lists pins; it does not delete them.** An earlier shape of this ticket also exported
`unpinReview(runner, cwd, localId)` "as the primitive M8.10 consumes" — but M8.10.2 independently specifies
`dropPinnedRefs({runner, cwd}, localId)` in its own `retention.ts` with prefix discovery, M8.10 depends on
M8.2 and M8.5 rather than on this ticket, and its landmine correctly requires discovery over reconstruction.
Two agents would have built the same deletion twice and this one would be dead code. Ref deletion is
**wholly M8.10.2's**. What this unit owes M8.10 instead is the namespace *shape*, which is why `pinRefsFor`
puts `<localId>` and `<pinKey>` in directory position: every ref this module writes lives under the prefix
`refs/revu/reviews/<localId>/`, so M8.10.2's `for-each-ref` over that prefix is correct under any encoding of
the compare key this unit picks (M8.10's open question 5 asks exactly that, and this sentence is its answer).

**Files:** `packages/revud/src/direct/local-pins.ts` (new),
`packages/revud/src/direct/local-pins.test.ts` (new).

**Check:** `bun test packages/revud/src/direct/local-pins.test.ts` passes and contains (a) a test that runs
the **real** `git check-ref-format` over `pinRefsFor(1_000_000_001, 'aaaa...bbbb')` and asserts exit 0, plus
a companion assertion that `check-ref-format` on the design's literal `<id>/<compareKey>` form exits 1 — so
the substitution is documented as load-bearing, not cosmetic; (b) a test feeding `mergeBaseSha = '-x'` and
asserting a typed rejection with a **recording fake runner whose arg sink is empty**; (c) a fixture-repo
test asserting `pinSnapshotObjects` then `listPins` round-trips both ref names and both object ids.

### M8.8.2 — Pin **before** the first object read, on every local sync

**Do:** Call `pinSnapshotObjects` from the local sync path immediately after `resolveLocalRange`
(M8.3.2) returns and **before** the first `git diff --raw`, `--numstat`, `-U3`, `git log` or `git cat-file`.
Ordering is the whole point: a prune that lands between the diff (which produces the blob SHAs) and the
`cat-file` reads (which fetch their bytes) turns every one of those SHAs into a `missing` entry
(`blobs.ts:284`) with no API tier to recover them, and the snapshot persists `partial` with the content the
draft anchors against absent. Pinning first closes that window; pinning after it does not.

A pin failure is **not** a sync failure — a review whose objects are unpinned still works today, it just has
no retention guarantee — so record the outcome on the sync result rather than throwing. Do **not** fold it
into `Snapshot['partial']`: `partial` means "content is missing", and an unpinned-but-complete snapshot is
not missing anything (see Open questions for where it should surface instead).

**Files:** `packages/revud/src/direct/local-sync.ts`, `packages/revud/src/direct/local-sync.test.ts`.

**Check:** A test with a recording fake `CommandRunner` asserts the index of the first argv containing
`update-ref` is **lower** than the index of the first argv containing `diff` and the first containing
`cat-file` — an ordering assertion, not a "was it called" assertion. A second test makes `update-ref` exit
non-zero and asserts the sync still resolves with a complete snapshot and a recorded pin failure.

### M8.8.3 — Rewrite detection replaces the silent under-report (shared reconcile + mock, in lockstep)

**Do:** In `reconcile.ts:92-96`, when `commits.findIndex(c => c.sha === draft.headSha)` is `-1` the draft's
head is not in the current compare at all — the branch was rewritten. Today that falls to
`commits.filter(c => c.commit.author.date > draft.createdAt)`, which **under-reports by construction**: a
rebase rewrites committer date but preserves author date, so every rebased commit keeps a date older than
the draft and is filtered out. Replace the heuristic with the honest answer — when the draft head is absent,
every commit in the current compare is new relative to a head that no longer exists, so `newCommits` is the
**whole** `commits` list. Make the identical change in the mock (`adapter.ts:639-643`), which today is
line-for-line parallel including the comment; **D6** makes the mock the spec, so it changes first or the two
transports disagree. Rewrite the comment blocks in both to describe the new rule with no reference to any
ticket or phase (AGENTS.md code style).

This changes the GitHub PR path too — that is deliberate: `anchor.ts` / `reconcile.ts` are shared, not
duplicated (hard constraint), and a force-push on a PR has the identical defect. `reconcile.test.ts:428`
("falls back to author-date when the draft head fell out of the rewritten compare") pins the old behaviour
and must be rewritten, not deleted.

**Files:** `packages/revud/src/direct/reconcile.ts`, `packages/revud/src/direct/reconcile.test.ts`,
`packages/app/src/api/mock/adapter.ts`.

**Check:** `bun test packages/revud/src/direct/reconcile.test.ts` — the rewritten case asserts
`newCommits.map(c => c.sha)` is `['X0','X1','X2']` (all three), and a sibling assertion states the property
that catches a regression: the author-date subset would have been strictly smaller, so
`report.newCommits.length === snapshot.immutable.commits.length` whenever `draftHeadSha` is absent from
`commits`. Plus a parity test that runs the same fixture through the mock adapter and asserts identical
`newCommits`. `bun test packages/revud/src/direct/conformance-reconcile.test.ts` stays green unchanged (its
draft head is still in the list, at `:97`).

### M8.8.4 — "Objects missing, re-sync to rebuild" instead of a lie

**Do:** A blob the store cannot produce resolves to `null` at `anchor.ts:417`, which
`classifyAnchor` reads as "no content to match" and reports as `lost` / `line-deleted`
(`anchor.ts:283-285`) — a claim the human acts on by dropping a comment whose line is, in fact, still
there. Add a pre-flight to the reconcile path (local and PR alike): before classifying, walk the draft's
comments, select each anchor blob SHA through the shared `selectAnchorBlobSha` (`anchor.ts:94`, the same
selector the dialog uses at `reconcile-dialog.tsx:159-160`), and probe `store.hasBlob`
(`store.ts:417-420`). If any anchor blob is absent, do **not** classify: answer a typed, actionable
`ApiError('not_found', …)` naming the count of unavailable objects and instructing a re-sync. Never
re-implement the side selection — importing the shared selector is what keeps a preview and this report from
disagreeing.

Second half: `getLocalSnapshot` (M8.2.3) mirrors `getSnapshot` (`store.ts:341-352`), which throws
`StoreUnreadableError` when the envelope references a `compareKey` with no immutable row. That is right for
a corrupt store and wrong for a moved data dir, and the two are indistinguishable to the caller today. Keep
the store throwing (it must not report a present row as absent), and map it at the API edge to the same
re-syncable answer so a moved data dir renders "re-sync to rebuild" instead of a 500.

**Files:** `packages/revud/src/direct/reconcile.ts`, `packages/revud/src/direct/reconcile.test.ts`,
`packages/revud/src/direct/direct-api.ts`.

**Check:** A test builds the `forcePushFixture` store, deletes one anchor blob from the fake store, and
asserts `reconcileDraft` throws `ApiError` with `code === 'not_found'` and a message naming the re-sync —
and asserts it does **not** return a report containing a `lost` result with reason `line-deleted`. A second
test asserts the draft is still readable, byte-identical, after the throw (`toStrictEqual` against the
pre-call value).

### M8.8.5 — Deleted or renamed head/base: typed `not_found`, read-only, nothing discarded

**Do:** A head or base branch that has been deleted or renamed makes `git rev-parse --verify` exit 128,
which M8.3.2 already maps to a typed `ref_not_found` naming the ref. This unit makes that state *survivable*
rather than merely typed: the review goes read-only and **every** stored artifact stays readable. Concretely
— no code path may delete a `local_reviews` row, a `local_drafts` row, a `local_threads` row or a
`local_snapshots` row in response to a sync failure; the read methods must not consult git at all, so a
review whose branches are gone still opens, still renders its threads, and still shows its draft. Do not add
a schema column for the state (M8.2 owns v4 and this is derivable): the review is read-only exactly when its
last sync answered `ref_not_found`, which the daemon returns to the client as a typed error.

**Files:** `packages/revud/src/direct/local-sync.ts`, `packages/revud/src/direct/local-resync.test.ts` (new).

**Check:** A fixture-repo test: create a review, sync, write a draft with three comments and one thread,
`git branch -D <head>`, sync again → typed `ref_not_found` naming the head ref; then assert
`getLocalDraft(...)` `toStrictEqual`s the pre-delete draft, `listLocalThreads(...)` is unchanged, and
`getLocalSnapshot(...)` still returns the last good snapshot. Repeat for a renamed base ref
(`git branch -m`). A grep-style assertion that no `delete*` store method is reachable from the sync failure
path is acceptable as a second, cheaper guard.

### M8.8.6 — Base advance under D8, and the rewrite the UI must not miscount

**Do:** Two app-side surfaces, both derivations over data that already exists — no new query, no new route.

- **Rewrite.** `useStaleness` (`queries.ts:147`) derives `newCommits` as a count *difference*, which a
  rebase leaves at zero, so a rewritten branch already falls through to the third banner branch,
  "head moved since sync" (`pr-layout.tsx:205-215`) — that copy is correct for a rewrite and needs no
  change. What is wrong is the reconcile dialog's header, which reads "N new commits"
  (`reconcile-dialog.tsx:284-287`) over a list that, after M8.8.3, contains *every* commit in the compare.
  Derive `rewritten` in the dialog with the same test the server uses —
  `!snapshot.immutable.commits.some(c => c.sha === report.draftHeadSha)` — and say "the branch was
  rewritten — N commits, all new SHAs" instead of "N new commits". No contract change: both inputs are
  already on the loaded snapshot and the report.
- **Base advance (D8).** A local review recomputes its merge base against the **live** base tip on every
  sync, so committing on the base branch alone changes `compareKey` with head untouched. The existing copy
  is already correct — `pr-layout.tsx:187-204` ("base advanced — diff changed", with the three-dot compare
  explanation) and the dialog's zero-commit state, "The compare changed without new head commits — the base
  branch moved" (`reconcile-dialog.tsx:386-391`). This unit's job is to *prove* it fires for a local review
  and to state the D8 divergence in the tooltip: a PR reads GitHub's `pull.base.sha`, which only refreshes
  on a `synchronize` event, so the two paths genuinely disagree about what changed.

Note the ordering reality: `useStaleness` needs a live list row (`usePullItem`), which for a local review
arrives with M8.5's `listPulls` merge. Until then `useStaleness` returns `null` and no banner renders —
degrade, never crash. The dialog half of this unit has no such dependency.

**Files:** `packages/app/src/components/review/reconcile-dialog.tsx`,
`packages/app/src/pages/pr-layout.tsx`, plus their co-located tests.

**Check:** There is **no DOM test runner in `packages/app`** — no RTL, no jsdom, and all fourteen existing app
tests are pure-module or mock-adapter tests — so "the dialog header renders X" is not a runnable assertion.
Follow the pattern `error-copy.ts:1-12` establishes and M8.7 leans on throughout: extract the two derivations
into a pure module (`isRewritten(commits, draftHeadSha)` and the header copy function that takes it), and
assert them with `bun test` — rewrite phrasing when `draftHeadSha` is absent from the snapshot's commits, the
plain "N new commits" phrasing when it is present, and the `github`-mode string byte-identical to today's
literal. The rendered leg is a `?mock=1` manual walk recorded in the Log, or M8.11's e2e. Plus a fixture-repo
test (revud side, may live in `local-resync.test.ts`): commit on the base branch only and assert `headSha` is
unchanged while `compareKey` differs from the previous sync's.

### M8.8.7 — A conflict-terminated reconcile must not leave the draft's head stale

**Do:** `§8` edge case 18 — "a reconcile-apply that ends in `conflict` never updates `draft.headSha`, an
existing latent bug that makes the *next* reconcile compute new commits from a stale head. Local reviews
inherit it; **it should be fixed rather than reproduced**." No other unit in this milestone touches it, and it
sits directly on top of M8.8.3's rewrite-detection change: after M8.8.3, "the draft head is not in the current
compare" means *every* commit is reported new, so a stale `draft.headSha` no longer under-reports quietly —
it reports the whole branch as new on every subsequent reconcile, which is the loudest possible version of the
same bug.

The mechanism, verified: `draft.headSha` is written exactly once, at creation (`state/drafts.ts:210`, inside
`ensureDraft`), and nothing ever updates it. `reconcile-dialog.tsx`'s `apply()` (`:162-258`) re-anchors every
kept comment against the **freshly synced** snapshot and then submits with `expectedHeadSha:
live.currentHeadSha`. On `ok` the draft is deleted, so the staleness is invisible; on `head_moved` it re-syncs
and re-reconciles. But on a `conflict` — and on any other rejection that lands in the `catch` at `:249-256` —
the draft survives with comments anchored to the **new** head and a `headSha` recording the **old** one, and
the next `reconcileDraft` computes its commit delta from a head the comments no longer correspond to.

Fix it where the re-anchor happens: give `DraftActions` (`state/drafts.ts:153-165`) a narrow mutator that
rewrites `headSha` and `compareKey` together — they are one fact, and updating either alone re-creates the
same inconsistency on the other axis — and call it from `apply()` in the same pass that upserts the
re-anchored comments, **before** the submit, so the persisted draft is coherent no matter how the submit ends.
It must go through the ordinary debounced save path so the daemon's copy moves too (`saveDraft` rebuilds the
draft as `{ ...draft, humanId, updatedAt }`, so the client-supplied head survives and the human key does not).
Nothing here may delete or clear a draft: this unit makes a surviving draft *correct*, and "drafts survive
everything" is untouched.

**Files:** `packages/app/src/state/drafts.ts`, `packages/app/src/components/review/reconcile-dialog.tsx`,
plus their co-located tests.

**Check:** A pure test over the draft mutator: applying it moves `headSha` **and** `compareKey` together, and
leaves `comments`, `body`, `event` and `createdAt` untouched (`toStrictEqual` on the rest of the document).
Then the regression the ticket exists for, asserted at the store/api layer rather than through the DOM: seed a
draft whose `headSha` is the pre-rewrite head, run the reconcile-apply sequence to the point of the head
update, terminate the submit with a `conflict`, and assert the draft that survives reports the **new**
`headSha` and `compareKey` — and that a second `reconcileDraft` against the same snapshot therefore reports
**zero** new commits rather than the whole compare. Record the pre-fix behaviour (the whole compare reported
new on the second pass) in the Log, since this is the assertion that distinguishes the fix from a no-op.

## Verify

Additional to `bun run check`:

1. **Prune survival, with teeth.** `bun test packages/revud/src/direct/local-resync.test.ts` runs against a
   real seeded repo (M8.3.5's `local-fixture-repo.ts` harness) and performs, in order: create a local review
   → sync → write a draft with comments on three files → `git commit --amend` / `git rebase` the head →
   **`git reflog expire --expire=now --expire-unreachable=now --all`** → **`git gc --prune=now`**. Both
   commands are required: `git gc` alone keeps unreachable objects for two weeks by default and a test
   without the reflog expiry proves nothing (verified — the object survived `gc --prune=now` until the
   reflog was expired). Then assert:
   - `git cat-file -t <mergeBaseSha>` and `<headSha>` of the **stored** snapshot both still print `commit`;
   - `git cat-file -e <sha>` exits 0 for **every** SHA in the stored `immutable.blobIndex` (both sides);
   - after clearing the store's `blobs` table — which forces the local git tier to be the only producer,
     because the GitHub tier is structurally absent (M8.3.6) — a re-sync + reconcile classifies every
     comment `clean` or `drifted` and **zero** as `lost` with reason `line-deleted`.
2. **Control, so the test cannot pass vacuously.** The same scenario with pinning disabled must fail at
   least one of the assertions above. This control matters more than usual here: the store's `blobs` table
   is cache-forever with no eviction (`store.ts` has exactly one `DELETE`, in `deleteDraft`), so an
   already-provisioned blob survives any prune and a naive rebase-then-gc test passes with no pinning at all.
3. **Rewrite is not under-counted.** For the rebased fixture, `report.newCommits.length` equals the compare's
   full commit count, and a recorded assertion states that the old author-date filter would have returned
   strictly fewer — the regression this ticket exists to prevent.
4. **Nothing is discarded.** After a `git branch -D` of the head and a failed sync, the draft
   `toStrictEqual`s its pre-delete value and every thread still lists.
5. **A conflict-terminated reconcile leaves a coherent draft.** After the apply sequence ends in `conflict`,
   the surviving draft's `headSha` and `compareKey` are the ones its comments were re-anchored against, and a
   second `reconcileDraft` reports zero new commits rather than the whole compare.
6. **Ref legality against real git.** `git check-ref-format` exits 0 for every ref name `pinRefsFor`
   produces, and exits 1 for the design document's literal `<id>/<compareKey>` form.
7. **Mock parity.** The mock and revud return identical `newCommits` for the rewritten fixture — the
   conformance suite's reconcile leg is the enforcement point (`conformance-reconcile.test.ts`).

## Constraints that bind this ticket

- **Drafts survive everything — a draft is deleted only on confirmed submit success** (hard constraints).
  Three of this ticket's states are exactly the ones tempted to clean up: a rewritten branch, a deleted head
  ref, and an unreadable object set. None of them may delete a draft, a thread, or a snapshot row. This is
  the single most important invariant here, and edge case 14 states it as the product itself.
- **Reconcile logic is shared, not duplicated** (`anchor.ts` is pure; the server-side report must import the
  same module the UI previews with). M8.8.3's fix therefore lands in the shared path and changes the PR
  behaviour too; a local-only fork of the commit-delta rule would be the exact divergence the constraint
  forbids.
- **D6 — the mock is the spec.** Any semantic change to `reconcileDraft` lands in `adapter.ts` first; the
  conformance suite runs against the mock as oracle.
- **Two-half caching: the key is `compareKey = merge_base…head`, one string form.** The pin ref name is a
  derived encoding with a documented substitution in exactly one function; nothing may parse a compareKey
  back out of a ref name.
- **D7 — no GitHub client in the local path.** `local-pins.ts` takes a `CommandRunner` and a cwd. That it
  *could not* call GitHub is the guarantee; that it *does not* is not.
- **D8 — local reviews use the live base tip.** The merge base is recomputed on every sync, so a base
  advance changes `compareKey` with zero new head commits. This is a deliberate divergence from the PR path
  (which reads GitHub's `pull.base.sha`, refreshed only on `synchronize`) and must be stated in the UI, not
  smoothed over.
- **Frozen contract: `client.ts` + `types.ts` are read-only inputs** (AGENTS.md ownership). `ReconcileReport`,
  `AnchorResult` and `ApiErrorCode` are all in `types.ts`; this ticket must work within them or escalate (see
  Open questions), never edit them unilaterally.
- **Migration doctrine: additive only, no PK altered, no table rebuilt.** This ticket adds **no** schema —
  M8.2 owns v4 and already carries every column the local path needs. The read-only-after-branch-deletion
  state is derived, not stored.
- **Argv discipline (M8.3.1).** Every git invocation goes through `runGit` with `--end-of-options`; a local
  id and two SHAs are validated as integer / hex before they reach an argv, because nothing in the runner
  validates command arguments.
- **AGENTS.md code style.** No ticket id, phase, wave, or agent reference in any comment or docstring — the
  rewrite-detection comment blocks in `reconcile.ts` and `adapter.ts` are rewritten, so this is a live risk.

## Landmines

- **The design document's ref path cannot be created.** `refs/revu/reviews/<id>/<compareKey>` contains
  `...`; `git check-ref-format` rejects any name containing `..` (verified, exit 1). If pin failures are
  non-fatal (which M8.8.2 specifies), an implementer who copies the path verbatim gets a review that
  silently never pins and a Verify step that quietly fails only under the control case.
- **Directory/file conflict on the ref namespace.** Once `refs/revu/reviews/<id>/<key>/head` exists, git
  refuses to create a ref at `refs/revu/reviews/<id>` (verified error text in M8.8.1). Any scheme that pins
  a single commit directly at the id level and later wants two refs there is unwritable, and the failure
  arrives on a user's machine, not in CI.
- **`git gc` alone proves nothing.** Unreachable objects have a two-week default grace; the object in a
  hand-run experiment survived `git gc --prune=now` until
  `git reflog expire --expire=now --expire-unreachable=now --all` ran first. A prune-survival test without
  the reflog expiry is a test that always passes.
- **The blob store makes the naive test pass without any pinning.** `blobs` is content-addressed,
  cache-forever, and the only `DELETE` in the whole store is `deleteDraft`. A rebase that changes nothing in
  a file produces identical blob SHAs, which are already in SQLite — so "rebase, gc, reconcile, no losses"
  is true with the feature entirely absent. The control case in Verify step 2 is what gives the suite teeth;
  skip it and this ticket ships as a no-op.
- **Pinning after the diff leaves the window open.** The SHAs come from `git diff --raw`; the bytes come
  from `git cat-file` some milliseconds later. A prune in between converts the whole compare into `missing`
  blobs, and with tier 3 structurally absent there is no recovery. Order is the mitigation.
- **Changing the commit-delta rule changes the PR path.** `reconcile.test.ts:428` fails, the mock must move
  in lockstep, and the reconcile dialog's "N new commits" becomes a claim about a different set. Landing
  M8.8.3 without M8.8.6 leaves the UI saying "12 new commits" for a 12-commit rebase where nothing new
  happened.
- **`lost` / `line-deleted` is a lie the human acts on.** The dialog's only offers for a lost row are
  re-anchor and drop (`reconcile-dialog.tsx:552-557`), and re-anchor is unavailable when the blob will not
  load — so a missing object funnels a human straight to "drop" for a comment whose line never moved. Once
  dropped, the text is gone.
- **Pinned refs are real refs.** They are not fetched or pushed by any default refspec, but
  `git push --mirror` or an explicit `refs/*:refs/*` would carry them to a remote. Keeping the namespace
  under `refs/revu/` (never `refs/heads/`) is what keeps them out of every ordinary push; do not "helpfully"
  pin under a branch namespace.
- **Unbounded pin growth.** A branch rebased daily mints a fresh compareKey per sync, and every pin holds
  its objects alive forever — the retention debt of edge case 23, now with a second axis. Nothing in this
  ticket deletes a pin (deletion is M8.10.2's), so whatever bound M8.8.2 accumulates is the bound until M8.10
  lands: state it (see Open questions) rather than leaving an unbounded ref set undocumented.
- **Worktrees and bare repos.** Refs live in the common git dir, so a pin written from a linked worktree is
  visible to the main one — fine — but `git rev-parse --show-toplevel` fails in a bare repo, and pinning
  must degrade rather than throw there. `context.ts:167` still hands out a bare `process.cwd()`, so an
  implementer who reaches for the context's cwd instead of M8.3.1's discovered root will write refs into
  whichever repo the daemon happened to start in.
- **A binary blob and a missing blob are the same `null`** at `reconcile.ts:80`. M8.8.4's pre-flight must
  probe `hasBlob`, not "did `resolveBlobLines` return null" — otherwise every comment on a binary file
  triggers the objects-missing state.

## Open questions

1. **Where does "the branch was rewritten" live on the wire?** This ticket derives it client-side
   (`draftHeadSha` absent from `snapshot.immutable.commits`), which needs no contract change and no mock
   validator. The alternative is an additive optional `rewritten?: boolean` on `ReconcileReport`
   (`types.ts:526`), which is more honest about provenance but edits the frozen contract and therefore
   belongs to whoever owns `types.ts` (M8.1). Owner call; the derivation is reversible, the field is not.
2. **Should the author-date fallback change for GitHub PRs too?** This ticket says yes (shared reconcile,
   identical defect on a force-push) and rewrites `reconcile.test.ts:428` accordingly. The counter-argument
   is that it changes behaviour on the PR path for a milestone scoped to local reviews. Needs sign-off before
   M8.8.3 lands, because the test rewrite is the point of no return.
3. **Where does a failed pin surface?** It is deliberately not `Snapshot['partial']` (that means missing
   content). Options: a field on the local review row (schema — M8.2 territory), a daemon log line only, or a
   quiet inbox badge. Until answered, M8.8.2 records it on the sync result and nothing renders it.
4. **What bounds the pin set before M8.10 lands?** Two defensible policies: pin only the current compare and
   delete the previous one on each sync (small, but a stored older snapshot could then reference unpinned
   objects — and it would mean this module deletes refs after all, which the M8.8.1 boundary rules out unless
   this question resolves that way), or pin every compareKey any stored snapshot references (correct,
   unbounded until retention ships). This ticket does not choose; M8.10 owns per-review eviction, but M8.8
   chooses what accumulates.
5. **Should the objects-missing answer be a throw or a report?** A typed `not_found` means the human sees an
   error where they expected their comments; a fourth classification would render inline but has nowhere to
   live in the frozen `AnchorResult` union (`anchor.ts:34` / the `lost` reasons). The throw is chosen here as
   the smaller, reversible move.
6. **Edge case 15 across a genuine re-clone.** Pins are per-repository, so a fresh clone has neither the
   objects nor the refs, and a re-sync rebuilds only what the new clone can reach. Is "re-sync to rebuild"
   sufficient, or does a snapshot whose content is provably unrecoverable need a durable marker so the UI
   stops offering a re-sync that cannot help?
7. **Surface label vs. reality.** The header says `revu:revud`, but M8.8.3 must edit
   `packages/app/src/api/mock/adapter.ts` (D6 parity), and M8.8.6 and M8.8.7 are entirely app-side (the latter
   touching `state/drafts.ts` and `reconcile-dialog.tsx`, neither of which any other M8 ticket owns). Either
   the label becomes `revu:revud, revu:app` or those three units belong in a separate ticket; worth settling
   before assignment so file ownership is unambiguous.
