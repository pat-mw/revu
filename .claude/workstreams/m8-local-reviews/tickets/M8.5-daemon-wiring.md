## Goal

Join the three daemon-core pieces — the `local_*` store (M8.2), the git-only snapshot builder (M8.3), and
the local write sink (M8.4) — into a daemon that actually serves a local review over HTTP. This is where
**D5** (`LOCAL_REVIEWS.md §3`) is cashed in: `REVU_MODE` is a credential-custody + bind axis, not a
data-source axis, so local reviews arrive as a *capability inside* direct/broker mode, dispatched on the
reserved id band from **D2**, and `resolveMode` gains no fourth member. Three things change: every id-keyed
method on the direct surface branches on `isLocalReviewId(n)` before it can reach a `GithubClient`
(which is also how **D7**'s structural absence is enforced at the dispatch boundary); the create/list/delete
and branch-listing routes M8.1 added to `ROUTES` get served; and `listPulls`, a 501 in direct mode today,
returns local reviews with a `compareKey`-derived ETag and a synthetic `RateLimitInfo` per `§4.1`. The
subtle half is **boot relaxation**: `resolveDirectContext` today refuses to start without a parseable
github.com origin **and** an obtainable token **and** a successful `GET /user`, and a local-only review
needs none of the three — `buildBrokerSession` already proves a fully offline session is buildable, so the
relaxation follows an existing path rather than inventing one.

## Units

Default execution order. **M8.5.1 lands first** — it is the type every other unit dispatches through.
**M8.5.4 is fully independent of M8.5.1–M8.5.3** (it touches `direct/context.ts` + `direct/session.ts`,
they touch `direct-api.ts` + `direct-router.ts`) and can run in parallel from the start. After M8.5.1,
**M8.5.2 and M8.5.3 are independent of each other** — both append to the route-dispatch chain in
`direct-router.ts`, so expect a trivial merge there and nowhere else. **M8.5.5 needs M8.5.1 + M8.5.4**;
**M8.5.6 needs M8.5.5**; **M8.5.7 needs all six.**

depends on for the operations only, never on the store/runner lifecycle. In `createDirectApi`

### M8.5.2 — Create / list / branches routes (delete stays 501 here)

(`direct-router.ts:495-516`). Read
bodies through `readJsonBody` (`direct-router.ts:236`) and validate with M8.1's validators; normalize and
validate every ref with M8.3's shared `git check-ref-format` helper **before** any git command runs

`(repo, base, head)` returns the existing review as a 200, not a 409 (`§8` case 6). Extend

creation failures — `base == head`, unrelated histories, shallow clone, missing ref, bad ref name — carry

Map M8.3's builder error union onto whatever `ApiErrorCode` M8.1.2 settled (M8.1's open question 7).

Two boundaries are explicit, not incidental:
- **`GET /api/branches` is a git read, not a store read.** It serves M8.3.7's `listBranches` over the boot
  runner + discovered repo root. Nothing about branches is in any table, and `§8` edge case 3 requires
  remote-tracking refs the store has never seen.
- **`DELETE /api/local-reviews/:n` is deliberately left unserved by this ticket.** The store method behind it
  is M8.10.1's (`deleteLocalReview` — the store's second `DELETE`, with a transaction and per-table counts),
  and inventing a bare row delete here would collide with that contract. Until M8.10 lands the route answers
  the honest known-route **501** it already gets for free from `isKnownApiPath` (`direct-router.ts:157-175`,
  fall-through at `:495-516`) — the same mechanism that made M8.1's routes safe to add before this ticket.
  M8.10.6 takes over serving it. Exclude it from this unit's route table; a table row for a route this ticket
  does not serve is the failure mode to avoid.

### M8.5.3 — `listPulls` in direct mode, local reviews merged
**Do:** Replace the `mode === 'broker'` condition on the `listPulls` branch (`direct-router.ts:295-299`)
with a **capability** gate on the api — mirroring how the broker write routes gate on
`api.brokerWritesEnabled` (`direct-api.ts:64`, `direct-router.ts:273-287`) rather than on mode — so an api
with neither a poll loop nor a local surface still answers the honest 501 it answers today. In
`createDirectApi`'s `listPulls` (`direct-api.ts:218-233`), when `deps.pullList` is absent but the local
surface is present, build the list from the local reviews: a synthesized `PullSummary` per `§4.1`'s field
table and a **complete** `BrokerPullMeta` (`shared/src/api/types.ts:278-301`) — `authorHumanId: null`,
`canApprove: true` (`§6` — there is no self-review rule to enforce), `unresolvedThreads` counted from
`local_threads`, `compareKey` from the review row, `commitCount` from the snapshot's commits, and `checks`
**omitted** (the field is optional and its absence already means "nothing has reported"). That list is
exhaustive: `BrokerPullMeta` is frozen and carries **no** `dirty` and **no** archived field, and per M8.1's
decision D-c neither is smuggled in here — both ride `LocalReviewSummary` through `listLocalReviews`
(M8.5.2), which is also why archiving cannot move this ETag on its own (M8.9.5 owns that). ETag is a stable
hash of the local reviews' `compareKey`s (`§4.1`); `rateLimit` is the synthetic large-limit / `used: 0`
shape (`§4.1`) so the honest-error copy reads "not rate limited". Honor `CONDITIONAL_LIST_304_RULE`
(`shared/src/http.ts:113-114`) exactly as `poll-loop.ts:765-788` does — on an `If-None-Match` match return
`{ items: [], etag, notModified: true, rateLimit }` and let the router emit the bodiless 304 at
`direct-router.ts:302-306`. When a poll loop **is** wired (broker mode), merge both halves and derive the
ETag from both, so a change in either invalidates.

`packages/revud/src/direct-router.test.ts`

### M8.5.6 — Honest degradation of the GitHub-only surfaces

as stack-shaped 500s. `GET /api/rate-limit` currently goes `direct-router.ts:331-333` →
`direct-api.ts:249-251` → `deps.github.getRateLimit()`, which throws `NoTokenError` straight into

`POST /api/pulls/:n/sync`, the four writes, and `GET /api/pulls/:n/snapshot` on a **non-local** `:n` — each
answers a typed code whose message says this daemon has no GitHub repository configured. Every one of these
behaviors is unchanged when a repo and token **are** present.

## Constraints that bind this ticket

- **D5 — a capability, not a mode.** `resolveMode`/`BootMode` (`index.ts:52`, `:62-72`) stay as they are;
  the local surface reaches both mains through the single `createDirectApi` factory. If this branch adds a
  fourth `REVU_MODE` value, `mode-select.test.ts:36-48` turns red and the design has been reversed.
- **D7 — no GitHub client in the local write path**, structurally. `writeDeps` (`direct-api.ts:203-210`)
  always holds one, and `WriteDeps` (`writes.ts:45-53`) requires one, so the local branch must be taken
  *above* both. A conditional inside a shared write function does not satisfy D7.
- **D2 — the reserved band satisfies the existing gates.** `prNumberOf` (`direct-router.ts:148-151`) and
  `Number.isInteger(commentId) && commentId > 0` (`:467`) are unchanged. New routes reuse only the
  allowlisted `:n` param so `draft-isolation.test.ts:117-128` passes unamended.
- **D4 — no synthetic id in the PR-keyed tables.** Dispatch must land on M8.2's `local_*` methods; a local id
  reaching `store.getSnapshot`/`putSnapshot`, `audit_log`, or `pr_author` corrupts the host collector's and
  poll loop's reading of "PR #N".
- **The frozen contract is a read-only input.** `packages/shared/src/api/client.ts` and `types.ts` (and the
  `ROUTES` table in `http.ts`) belong to M8.1. If serving a route seems to require editing them, the boundary
  was drawn wrong — report it rather than editing (AGENTS.md ownership).
- **The three transport semantics survive on the local leg** (`hard-constraints.md`, `http.ts:226-233`):
  `getSnapshot` returns a JSON `null` at 200 for a never-synced **local** review; `syncPull` may resolve
  `partial` at 200; `submitReview` returns `head_moved` as a 200 **value** — and `§6` keeps `head_moved`
  live locally, where an amend moves head with no PR event to announce it.
- **`CONDITIONAL_LIST_304_RULE`** (`http.ts:113-114`): `listPulls` remains the only conditional surface, and
  a 304 carries no body.
- **Identity**: drafts and viewed state stay keyed by the session's `Human.id`
  (`direct-api.ts:197`, `:275-281`); no route gains an identity path param; the synthesized local `GhUser`
  carries the git-config **name**, never the email (`§4.1`, `§8` case 26).
- **Durable write failures are `persist_failed` (500)**, never a 200 the client trusts as saved
  (`direct-router.ts:187-189`). The local write routes inherit this unchanged.
- **`/api/dev` stays mock-only** (`api-router.ts:191-194`, `known-landmines.md`): no local-review analogue,
  no unauthenticated state-changing route.
- **Two-half caching**: a local snapshot's immutable half is keyed by `compareKey = merge_base...head` in the
  shared `immutables` table, with no TTL and no head-SHA short-circuit.
- **The gate runs `bun test` before `vite build`**, so `packages/app/dist` does not exist during tests: any
  test that starts `revud` points at a stub dist via `REVU_DIST_DIR` plus a temp `REVU_DATA_DIR`.
- **AGENTS.md code style**: no ticket id, phase, or tracking reference in any comment or docstring;
  `import type` for types; no unused bindings; complete files, no stubs.

## Landmines

- **The broker reads-only write gate silently swallows local writes.** `direct-router.ts:273-287` matches on
  the route template alone, so in broker mode without `REVU_BOT_LOGIN` a `POST /api/pulls/1000000001/review`
  answers 501 — "this broker has no bot identity" — for a write that never touches GitHub and needs no bot
  identity at all. The gate must skip local ids (or run after the band check). Miss it and local reviews are
  reads-only in exactly the deployment — a contractor's disposable workspace — the feature exists for, with an
  error message that sends the reader hunting for a GitHub App.
- **Dropping the `mode === 'broker'` guard on `listPulls` changes the answer for an api with no list source.**
  Today `GET /api/pulls` 501s in direct mode via the fall-through (`:495-516`); a naive removal routes it to
  `api.listPulls`, which throws `ApiError('not_found')` (`direct-api.ts:227-230`) → a **404**. Gate on a
  capability flag instead, the way `brokerWritesEnabled` does, so the honest 501 survives for a daemon that
  genuinely serves no list.
- **`envelopeForError` has no branch for the local errors.** `direct-router.ts:186-234` maps eight typed
  errors and then falls to `broker_unreachable`/500 at `:232-233`. A "shallow clone", "unrelated histories",
  or "bad ref name" that is not an `ApiError` renders in the UI as an unreachable-broker 500 — the single
  most confusing possible message for a feature whose entire premise is that there is no broker.
- **Widening `DirectContext.repo` to nullable ripples.** `createDirectApi({repo})`, `runSyncPull`,
  `provisionBlobs`, and the poll loop all take a `RepoRef`. Papering over the absence with
  `{ owner: '', repo: '' }` builds request paths like `/repos///pulls/204`, which 404 against GitHub with a
  message that blames the PR. Make the absence typed.
- **A relaxed boot must not relax the git-identity guard.** `MissingGitIdentityError` (`session.ts:39-48`)
  is what keys drafts and viewed state. Softening it so the daemon "starts anywhere" files every human's
  drafts under one blank id — and the store cannot tell them apart afterwards.
- **`bin/revu` refuses before `revud` is ever executed.** `detect_repo` (`bin/revu:60-76`) returns non-zero
  for a repo with no github.com origin and `cmd_open` / `start` / `restart` (`:189-191`, `:251`, `:255`) die
  on it; `start_daemon` (`:106-120`) additionally forces `REVU_MODE=broker` and passes `REVU_REPO`. The
  milestone's headline exit criterion is not reachable through the CLI on this branch — plan the drill
  against `revud` directly, and see Open questions.
- **`listPulls` merging local reviews is NOT the PR listing M8.9 needs.** `§8` case 21 says archive detection
  needs a **GitHub** pull listing that direct mode does not have; this ticket adds a **local** one. The board
  records M8.5 as blocking M8.9, and it does — but only for the routing, not for the detection input. Do not
  let a green `listPulls` here read as "M8.9's data source exists".
- **`listReviewThreads` must stay 501.** Local threads ride the snapshot's mutable half exactly as GitHub
  threads do, and no app component calls the method (it exists in the adapters only). Implementing it
  "because the data is local now" grows a second thread read that can disagree with the snapshot.
- **The `?pr=` reaction param is the band input.** `direct-router.ts:472-478` takes the owning review from
  the query or the body; if the dispatch reads a different value than the router validated, a local comment
  id arrives with a GitHub PR number and the write goes to the wrong sink — silently, since both are
  positive integers.
- **Locally minted entity ids sit at 9e12.** Well inside `Number.MAX_SAFE_INTEGER` (~9.007e15) and inside
  SQLite's 64-bit INTEGER, so no precision hazard today — but the router parses ids with `Number()`
  (`direct-router.ts:466`), so an id band that ever grows past the safe range silently rounds. Assert the
  ceiling rather than assuming it.
- **The 501 test at `direct-router.test.ts:361-371` will turn red**, correctly. Rewriting it to keep proving
  the threads route still 501s is the point; deleting the case lets the daemon grow a surface nobody asserts.
- **Boot must stay loud about a corrupt store.** `index.ts:167-171` opens and migrates before anything else,
  and its comment already promises a present-but-unreadable row fails startup rather than reseeding over
  drafts. Boot relaxation is about GitHub preconditions only — never about store errors.

## Open questions

1. **How is the local-only capability switched on?** A `--local-only` flag, an env var, or automatically
   (relax whenever repo/token resolution fails)? Automatic is friendliest and riskiest: a transient `gh`
   failure inside a genuine GitHub clone would silently boot a daemon that can only do local reviews and
   shows an empty inbox, which reads as data loss. An explicit switch is loud but adds a knob and a docs
   line. `§3` D5 says local reviews are a capability inside direct/broker but never says how the capability
   is enabled. **Owner or implementer decides before M8.5.4** — it determines the option's shape.
2. ~~**What string is `repo` with no origin?**~~ **Settled by M8.2**, which owns the rule because it bakes the
   value into `UNIQUE(repo, base_ref, head_ref)` and lands three merges earlier: `owner/name` when an origin
   parses, else the absolute `git rev-parse --show-toplevel` path. M8.3.1 exposes `repoIdentity(...)`; M8.5.5
   calls it once at boot. Nothing in this ticket re-decides it.
3. **What does `GET /api/rate-limit` answer on a local-only daemon?** `§4.1` pins a synthetic `rateLimit`
   *inside* `PullListResponse` so honest-error copy reads "not rate limited", but says nothing about the
   standalone route. 501 is more honest; the synthetic shape keeps the rate-chip code path uniform. M8.7
   suppresses the chip on a local review, but the chip is a global surface, not per-review — so the two are
   not the same decision.
4. **How do a poll loop's items and local reviews combine?** `§4.1` gives the local ETag as a hash of the
   local `compareKey`s and stops there. Ordering and ETag composition for the merged broker list are
   unspecified; getting the composition wrong yields an inbox that 304s forever and never shows a new PR.
5. **What is the module seam M8.5 dispatches into?** M8.3 and M8.4 name no module paths, and M8.2's Open
   question 2 asks whether the store's local surface hangs off `DirectStore` or a sibling. A single
   `LocalReviewSurface` assembled from the store slice + the git builder + the write sink would give D7 a
   clean structural home (the local write module receives a store slice and a `CommandRunner`, and there is
   no `GithubClient` in its import graph to receive). This is M8.5's central type — decide it before M8.5.1.
6. **Does `bin/revu` gain a local-only path?** Out of scope as the ticket is scoped (`Surface: revu:revud`),
   but the milestone exit criterion "a local review can be created … in a repo with no GitHub remote" is not
   reachable through the command a contractor actually types until it does. Either widen the scope here,
   open a follow-up, or state explicitly that the criterion is proven against `revud` directly.
7. ~~**Do local reviews belong in `listPulls` at all?**~~ **Settled by M8.1's decision D-a**: yes, and the mock
   is the spec for it. `PrLayout` resolves a review only out of that list (`pr-layout.tsx:280-282`), so the
   alternative renders the "isn't in this installation" screen on every local review. The real behavior change
   for existing direct-mode users — an inbox that is non-empty for the first time — is accepted deliberately;
   `listLocalReviews` stays for management surfaces and for the two local-only annotations (D-c).
