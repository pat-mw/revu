## Goal

The owner ruled that deleting a local review which holds an **unsubmitted draft** must not simply proceed: it
requires an explicit force. The API half of that — the force flag and its refusal — belongs to
[M8.10](./M8.10-retention-and-gc.md), which owns retention and the delete path. The **user-facing half has no
owner**: there is no confirmation UI anywhere in the app for this, and shipping the refusal without it would
make deletion simply fail with no way through.

This ticket exists because that dialog is net-new scope discovered while ruling on prune defaults, and it was
appended rather than absorbed into M8.10 (whose Surface is `revu:revud`) or M8.6 (whose Goal is creation, not
deletion).

**Note what this is *not* about.** Deletion orphans drafts and viewed state; it never destroys them, and the
never-recycled id makes those orphans permanently unreachable rather than dangerous. So this is a guard against
**surprise**, not against data loss — which is why a confirmation is the right shape and a hard refusal is not.
The copy must be honest about that: it says the draft becomes unreachable, not that text is destroyed.

## Units

### M8.12.1 — The refusal, surfaced honestly
**Do:** Map the typed refusal M8.10 returns for a delete-with-unsubmitted-draft onto its own sentence, in the
established one-honest-sentence-per-typed-error shape (`components/review/error-copy.ts:20-29`). The sentence
names what happens — the review record goes, the draft survives on disk but nothing can reach it again — and
offers the way through. It must not claim text is deleted, and it must not use the word "lost", which the
product reserves for the guarantee that nothing was.

**Files:** `packages/app/src/lib/mode-copy.ts`, `packages/app/src/lib/mode-copy.test.ts`.
**Check:** the copy function returns a non-empty sentence for the refusal code, matches `/unreachable/i`,
matches **none** of `/deleted/i` on the draft noun, and its positive control in the same test is a different
typed error returning a different sentence — so a function that returns one string for everything fails.

### M8.12.2 — The confirm dialog
**Do:** A portal-free `ConfirmDeleteLocalReviewBody` (props: the review's ref pair, whether a draft exists, a
pending flag) plus the thin `Dialog` wrapper around it, following the split
[M8.6](./M8.6-app-creation-flow.md).3 establishes — a Radix `DialogContent` static-renders to the empty string,
so the body must be its own component or the test asserts on `''` and passes forever. The destructive action
uses the red treatment (`globals.css` tokens only; red means destructive) and is **not** the default focus.
Confirming re-issues the delete with the force flag set.

**Files:** `packages/app/src/components/confirm-delete-local-review.tsx` (new) and its `.test.ts` (new — `.ts`,
never `.test.tsx`; `createElement` + `renderToStaticMarkup`, per `components/ui/markdown.test.ts`).
**Check:** static-render the body in both states and assert on real HTML — with a draft, the markup carries the
unreachable-draft sentence; without one, it **does not**, and the positive control in the same test is that the
with-draft render **does** carry it, so the absence assertion cannot pass on an empty render. Assert the
confirm control carries the destructive variant and that the review's `base ← head` pair renders (never its
number — the identity rule holds here as everywhere).

### M8.12.3 — Wiring and the force round-trip
**Do:** Wire the dialog to the delete mutation: first attempt unforced, and on the typed refusal open the
dialog rather than surfacing an error toast. Confirming retries with force. Dismissing changes nothing —
no partial delete is possible, because the refusal happens before any record is touched.

**Files:** `packages/app/src/state/local-reviews.ts`, `packages/app/src/state/local-reviews.test.ts`.
**Check:** drive `createMockApi()` (with `mockDev.reset()` in `beforeAll`, `setLatency('zero')`, restore in
`afterAll`): create a review, save a draft, delete unforced → the typed refusal comes back and the review is
**still listed**; delete forced → gone from `listPulls`, and the draft is still readable under its own key.
That last assertion is the one that proves the orphan-not-destroy rule holds through the UI's path, not only in
the store.

## Constraints that bind this ticket

- **Never discard user-written text on failure**, and never *say* text was discarded when it was not. The copy
  is the whole point of the ticket.
- **Red means destructive; violet is reserved for draft/pending state.** `globals.css` is a read-only shared
  input — compose existing tokens, no raw hex, no new class.
- **All data goes through `api` from `@/api`** — never `@/fixtures` or `@/api/mock`.
- **The identity rule holds:** the dialog names the review by its `base ← head` pair, never by its number.
- **Comments and docstrings are self-contained** — no reference to tickets, milestones, phases or any tracking
  artifact.
- **Test-first:** each unit's test is written and observed red first; every absence assertion carries a
  positive control in the same file, and both observations go in the `## Log`.

## Open questions

1. **Does the force flag belong on the wire, or is the confirmation purely client-side?** The frozen route set
   has `DELETE /api/local-reviews/:n` with no body and no query parameter. If the refusal is to be
   server-authoritative, the force needs somewhere to live — which is a frozen-contract question, not this
   ticket's to answer. The alternative is that the daemon always deletes and the confirmation is purely a
   client-side guard, which is weaker but needs no contract change. **This must be settled with M8.10 before
   either ticket dispatches**, and it may be a §5.2 stop.
